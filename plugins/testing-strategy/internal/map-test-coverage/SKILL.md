# テストカバレッジを品質リスクへ対応付ける

境界シナリオ、E2E シナリオ、探索計画の三つの入口は、同じ骨組みで進む。戦略資料を読み、既存テストが実際に保証していることと残るリスクを対応付け、残るリスクを最小の担当レベルへ配分し、資料にして保存する。この内部判断は、その共通の部分を一度だけ持つ。各入口の SKILL.md は、その入口に固有の判断だけを持つ。

## 戦略資料の定義に従い、作り直さない

最小の担当レベル、Small・Medium・Large、差し替えてよい境界は、`test_strategy_path` の戦略資料が定義している。最初に戦略資料を全文読み、品質リスク、レベルとサイズの定義、実物で確かめる協働先、重複を下位へ移す規則を取り出す。戦略を簡易に作り直したり、定義を書き直したりしない。戦略資料が品質リスクと配分を定義していなければ、止まって戦略を先に作るよう返す。

## テストがあるだけの状態と、実行済みの証拠を分ける

テストコードがあるだけでは、証拠にしない。対象のリスクに対する刺激、観測結果、使う依存を、コードか資料から説明できるときだけ、そのテストをリスクに対応付ける。実行した結果を確かめられなければ、「存在するが未実行」として分ける。

次のどれかに当たるリスクは、残余リスクとして扱う。主担当の証拠が見つからない。テストはあるが、刺激か観測結果が足りない。実行状態や不安定さが分からない。下位では再現できない接続として、意図して上位に残されている。

## 残るリスクを、最小の担当レベルへ置く

今回補う各リスクについて、戦略資料の規則に従い、同じ失敗を再現できる最小の担当レベルとサイズを選ぶ。上位にも同じ例を残すなら、下位と違う欠陥を確かめる理由を書く。書けなければ下位だけに置く。

## 三つの入口に共通する進め方

進める順は、各入口の `playbook.yml` の工程に従う。どの入口でも次の判断は同じである。

問うのは、調べても決まらず、答えで成果が変わることだけにする。観測した事実に基づく推奨と理由を添えて公開 playbook `grill` へ渡す。合意しなかった論点は、推奨を仮説として本文に置き、採らなかった案と見直す条件を書く。

本文の書き方は、`write-doc` の書くときの規範（`references/writing-norms.md`）に従う。シナリオや charter は一つずつ見出しを立て、何を確かめ、なぜそのレベルに置くのかを段落で書く。表は、入力の区分やシナリオごとのサイズのように、同じ属性を行で比べる箇所だけに使う。

保存は、本文を `material: [{kind: text, content: <本文>}]` として、`document_destination` と `references` とともに公開 playbook `write-doc` へ渡す。保存した資料を読み戻し、足りなければ直す。直せない不足は未決として残し、`status` を `unresolved` にする。

欠けた情報が成果を変えるときは止まり、確かめた事実と再開の条件を返す。必須のパスを特定できない、保存先が不正、外部環境へ許可なく接続しなければ成果に意味が無い、といった場合である。成果を変えない揺れでは止まらず、仮説を明示して進む。

テストコード、CI、探索は実行していないので、実装済み、実行済み、発見済みとは報告しない。
