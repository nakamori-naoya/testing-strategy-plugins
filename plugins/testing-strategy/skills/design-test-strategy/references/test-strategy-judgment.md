# テスト戦略の判断基準

このreferenceは、対象リポジトリ固有の品質リスクを、テストレベル、Small・Medium・Large、境界シナリオ、CIへ配分する判断を所有する。固定のテスト件数、層名、プログラミング言語、通信方式、永続化製品、テストツール、時間閾値は所有しない。

## 戦略の出発点

戦略は「どのテストを書くか」ではなく、「どの失敗を、どの境界で、どの速さで検出するか」を決める。機能一覧やファイル一覧からテストを一対一で作らない。

品質リスクは次の順で具体化する。

1. 利用者、業務、状態、連携、開発フィードバックに起きる失敗を書く。
2. その失敗を観測できる最小の境界を書く。
3. 誤りが混入する場所と、検出する場所を分ける。
4. 根拠となる要件、業務知識、モデル、インターフェース定義、コードへ戻れるようにする。
5. 上位へ残す場合は、下位では検出できない接続または協調を説明する。

## 基本とするテスト思想

古典派を既定にする。公開された振る舞いと観測可能な結果を確かめ、内部実装の呼び出し列を期待値にしない。対象リポジトリが制御でき、ローカルまたはCIで決定的に用意できるストレージ、キャッシュ、メッセージング、ファイルシステム、プロセス、サービスは実物を使う。

どの境界をテストで差し替えてよいかの具体は、対象リポジトリの実装言語のテスト規約が持つ。戦略はその規約を読み、戦略資料には規約の所在と、戦略として実物で確かめる協働先を書き、規約の一覧を書き写さない。規約が見つからなければ、観測した協働先から差し替えの境界を仮説として置き、規約の持ち主への提案として未決に残す。速度だけを理由に実物を代替せず、遅さを生む依存はサイズ分類とCI段階へ反映する。障害を確かめたいときも、実物を壊れた状態（閉じたport、書き込みの停止、接続できない先）にして起こせるなら、代替より実物を選ぶ。利用者またはリポジトリの明示規約が別の思想を要求する場合は、相違と影響をgrillで合意して戦略へ記録する。

## テストピラミッドの使い方

テストピラミッドはテスト数の割合ではない。同じ欠陥を、より小さく、決定的で、原因を特定しやすいテストへ移す判断規則である。

- 業務値の境界をE2Eへ列挙せず、業務判断を所有する境界へ置く。
- 保存制約、問い合わせ、原子性が本質なら、模倣した単体テストではなく実際の永続化境界で確かめる。
- 認証主体、通信への変換、エラー表現が本質なら、公開インターフェースの境界へ置く。
- 複数プロセスを通る接続と非同期協調だけをE2Eへ残す。
- 上位へ代表例を残す場合、下位は意味の網羅、上位は配線の成立を担当し、同じ失敗を二重に主張しない。

## Small・Medium・Large

サイズはテスト種別の別名ではなく、使う資源と隔離範囲で決める。

| サイズ | 判定 | 代表的な対象 |
|---|---|---|
| Small | 単一プロセス内で完結し、ネットワーク、外部ストレージ、外部ファイルシステムを使わない | 業務判断、純粋な変換、局所的な調停 |
| Medium | 単一マシン内で完結し、localhost、実ストレージ、実キャッシュ、エミュレーターを使える | 永続化アダプター、公開インターフェース、契約例、単一ワーカー |
| Large | 複数プロセス・サービスの協調、または制御できない境界が本質である | 主要E2E、非同期経路、外部連携 |

実行時間は結果として計測する。未計測の秒数をサイズ定義へ使わない。同じ公開インターフェースのテストでも、単一プロセス内ならSmallになり得て、localhost上の実ストレージを使えばMediumになる。名前だけで分類しない。

## テストレベルの責務

対象リポジトリの層名やアーキテクチャが違っても、観測する責務で対応させる。該当する責務が無ければ、表を埋めるためにレベルを作らない。

| レベル | 主に確かめること | 主担当にしないこと |
|---|---|---|
| 業務判断 | 成立条件、拒否理由、不変条件、状態遷移、値の境界 | 永続化方式、通信表現、フレームワーク配線 |
| 永続化 | 実ストレージの制約、変換、原子性、競合、主要な読み書き、読み戻し | 業務条件の全組み合わせ、通信表現 |
| 調停 | 複数判断の調停、処理順、原子性の境界、外部境界への依頼 | 製品固有の保存詳細、通信形式の全項目 |
| 公開インターフェース | 認証主体、入力変換、成功・失敗表現、冪等性、ページング | 業務条件の網羅、保存実装 |
| 契約 | 機械可読定義の互換性、提供者と利用者が共有する具体例の意味 | システム全体の配線、可用性 |
| E2E | 公開入口から実ストレージ、非同期処理、観測結果までの重要な接続 | 境界値の総当たり、全拒否理由 |
| 静的検査 | format、lint、型、生成差分、インターフェース互換性、禁止依存 | 実行時の意味 |

「業務判断」はドメインモデルを持つ設計に限定しない。関数、サービス、ルールエンジン、設定駆動の判断など、業務上の結果を所有する実際の境界へ対応させる。「永続化」もRDBに限定せず、ドキュメント、KVS、オブジェクト、ファイル、イベントログ、外部サービスを含む。

複数レベルが同じ例を持つ場合、それぞれが検出する別の欠陥を書けなければ下位へ統合する。

探索、運用、本番障害で高水準の操作から欠陥が見つかった場合も同じ規則を使う。発見時の画面操作、API列、E2E経路をそのまま回帰テストへ固定せず、同じ失敗を再現できる最小の依存範囲まで下げる。下げると欠陥が消える境界が、その欠陥に必要な接続を示す。複数構成の協調を外すと再現しない場合だけE2Eへ残す。

## 境界シナリオ

公開API、CLI、イベント、ジョブ、ライブラリ関数など、他の利用者またはコンポーネントが依存する境界がある場合、境界シナリオをテストコードや業務知識の再掲とは別の設計資料として扱える。対象にその境界が無ければ作成を要求しない。

境界シナリオ方針には、該当するものだけを含める。

- 操作またはメッセージを一意に識別する名前と、機械可読定義の所在
- 呼び出し主体と必要な事前状態
- 入力同値クラスと境界値
- 状態、再送、順序、競合で結果が変わる具体シナリオ
- 成功・失敗の表現と再試行可否
- 操作後に外部から観測できる結果
- 主担当のテストレベルと、上位へ重複させない項目
- 関連する要件、業務知識、モデル

「不正な値」「成立条件を満たさない入力」と書かず、外した条件と具体値を書く。同じ入力の最小、有効最大、上限超過のような区分は表へまとめる。複数操作で初めて差が出る再送、順序、競合はシナリオとして書く。

インターフェース定義から操作名、型、フィールドなどを機械生成できる場合だけ、生成可能な契約サマリと人が判断する意味を分ける。定義形式や生成機構が無い対象へ、特定のスキーマ言語や生成方式を要求しない。

## 設計資料の点検

| 資料 | テスト設計に必要な情報 | 混ぜない情報 |
|---|---|---|
| 要件 | 利用者が観測する結果、対象範囲、制約 | 層ごとのテストケース |
| ユーザージャーニー | 目的、開始、主要な場面、完了 | 通信境界値の一覧 |
| 業務知識 | 成立条件、拒否理由、不変条件、状態遷移 | 通信エラー、保存方式、網羅的テストカタログ |
| データモデル | 状態、履歴、関係、論理制約、競合時の意味 | 全境界シナリオ、全永続化テスト |
| インターフェース定義 | 操作、入力、出力、互換性 | 業務理由、状態系列の意味 |
| 境界シナリオ | 境界で観測する具体例、入力区分、状態系列、テスト配分 | 業務知識やモデルの全文複製 |

資料を書き換えてよいのは、その資料を作る入口だけである。戦略は業務知識やデータモデルを書き換えず、どの例がどのレベルで最も価値を持つかの仕分けを、資料の持ち主への提案として書く。規則の意味と条件差を理解する最小例は資料に残るべきものとして扱い、境界値や組み合わせの網羅が目的の例は、変更ごとのテスト設計へ送る提案にする。移動先が無い例を減らす提案はしない。

## 待機

テストは、固定の時間を待つのではなく、外部から観測できる条件（状態、event、応答、query）が成り立つまでを、期限を付けて待つ。固定のsleepは、待つべき条件を観測できないか、時刻の源を制御できないことの症状であり、テストの側で隠さず設計の不足として戦略に書く。制御できない外部の時計の境界そのものを確かめるテストだけは、待つ時間の上限と理由を書いたうえで残してよい。この原則は言語に依らず、各言語での形（試行ごとの期限、並行テストの順序の固定など）は実装言語のテスト規約が持つ。

## CIとローカルの完了判定

「手元で通った」と「CIで通った」は、同じ検査の集合を指さなければならない。指さなければ、baseは手元の完了判定より弱い検査で緑になり、手元で見つかるはずの欠陥がそのまま入る。

そのため、CIはローカルの完了判定の入口（`make verify` のような一つのcommand）をそのまま呼ぶ形を既定にする。順序や並列化のためにCIの工程を分けるときは、完了判定の構成要素とCIの工程の対応を戦略に書き、両者の集合が一致することを機械で検査する。秘密値や共有の外部環境が要る検査（外部サービスを使うE2Eなど）をCIから外すなら、外す理由と、その検査を代わりに実行する場所と時点を書く。外した検査は、黙って消えたのではなく、理由を持って別の場所にあると読めるようにする。外部の実物へ接続するテストは、利用者とrepositoryが定める接続の許可の規則に従うので、戦略にはその許可が置かれている場所を書き、許可が無ければ誰がいつ実行するかを書く。

この一致は、入口の構成要素と、CIが呼ぶ入口の集合から真偽が一意に決まるので、機械検査に向く。戦略資料には、何を基準資料とし、何を合格とするかまでを書き、検査の実装は変更ごとの作業へ渡す。

## CIの順序

既定の順序は、静的検査、Small、Medium、Largeである。失敗を原因に近い場所で早く返し、後段ほど対象を少なくする。

対象リポジトリで次を観測して具体化する。

- 各段階の実行時間と変動
- 並列化できる単位
- 実サービス準備とデータ隔離の方法
- 失敗から原因特定までの情報
- 不安定なテストと、その依存
- 変更ごと、定期、リリース前へ分ける条件

失敗したテストを無条件に再実行して緑にしない。再実行が必要な場合は、再試行対象となる外部境界と、最初の失敗を欠陥として追跡する方法を書く。

## 変更ごとの入口

全体戦略は、個別変更のシナリオ全件を所有しない。各変更では次を決めるよう戦略から要求する。

1. 増減する品質リスク
2. 根拠にした要件、業務知識、モデル、インターフェース定義
3. 入力同値クラスと境界値
4. 状態、再送、順序、競合を含む代表シナリオ
5. 主担当レベルとSmall・Medium・Large
6. 上位へ重複させなかった項目と理由
7. 変更後も残る未検証リスク

個別変更の境界シナリオやE2Eシナリオ資料を実際に作る仕事は、このskillの責務外である。

## 詳細を分ける品質領域

性能、セキュリティ、探索的テストは、通常の機能テストと目的、入力、環境、合否が異なる。利用者が今回の中心対象に指定しない限り、詳細戦略へ展開せず次だけを残す。

- なぜ別途検討するか
- 後続で必要な入力
- 現在の戦略が残す観測点または接続点
- 何を決めれば詳細戦略を開始できるか

認証・認可の機能的な振る舞いは通常の公開インターフェーステストに残せる。負荷条件による応答、攻撃的検証、探索チャーターは、それぞれの詳細戦略へ送る。
