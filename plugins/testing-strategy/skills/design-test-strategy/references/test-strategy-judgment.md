# テスト戦略の判断基準

この資料は、品質リスクをテストレベル、サイズ、CIへ配分する判断を一か所で持つ。最小の担当レベル、Small・Medium・Large、差し替えてよい境界の定義はここにだけ置く。テストシナリオと探索計画を作る入口は、この基準で作られた戦略資料を読み、定義を書き直さない。

戦略が決めるのは「どのテストを書くか」ではなく、「どの失敗を、どの境界で、どの速さで検出するか」である。機能一覧やファイル一覧から、テストを一対一で作らない。テストの件数比、層の名前、言語、テストツール、未計測の時間目標は、戦略の原則にしない。

## 差し替えてよいのは、制御できない外部の境界、時計、採番だけである

古典派を既定にする。公開された振る舞いと、外から観測できる結果を確かめ、内部の呼び出しの列を期待値にしない。差し替えてよいのは、制御できない外部の境界（外部組織のサービス、課金を伴う境界など）、時計、採番だけである。それ以外の内部の部品は、ストレージ、キャッシュ、メッセージング、別のプロセスも含めて、ローカルやCIで決定的に用意して実物を使う。ただし、フロントエンドから見た backend のように、別の配備単位にある境界は、その向こう側を向こう側のテストで確かめる前提で、要求と応答の形で差し替えてよい。

内部の部品を差し替えると、差し替えた偽物と実物の違いに欠陥が隠れ、テストは緑のまま本番で落ちる。速度を理由に実物を代替しない。遅さは、次のサイズとCIの段階で扱う。どう差し替えるか（gomock、MSW などの仕組み）と障害の起こし方は、実装言語のテスト規約が持つ。戦略には、差し替える境界とその理由、実物で確かめる協働先を書く。

外部サービスが公式のテスト用経路（テスト用の token、sandbox、開発用の instance）を持つなら、自作の代替より、それを使う実物の接続を既定にする。自作の代替では、提供者との token 交換や署名検証の配線が抜けるからである。

## 最小の担当レベル：同じ失敗を再現できる最小の境界に置く

テストピラミッドは、テスト数の割合ではない。同じ欠陥を、より小さく、決定的で、原因を特定しやすいテストへ移す規則である。主担当は、欠陥が混入した層ではなく、同じ失敗を公開された振る舞いとして再現できる最小の境界にする。

業務条件だけで差が出るなら、業務判断のレベルに置く。実ストレージの制約、問い合わせ、原子性で差が出るなら、模倣した単体テストではなく永続化のレベルに置く。認証主体、通信への変換、失敗の外部表現で差が出るなら、公開インターフェースのレベルに置く。提供者と利用者が共有する例や互換性なら、契約のレベルに置く。複数プロセスの配線、非同期の協調、実構成の協調が欠けると再現しない場合だけ、E2E に残す。

探索、運用、本番障害で高水準の操作から見つかった欠陥も、同じ規則で下げる。発見時の画面操作、API の列、E2E の経路を、そのまま回帰テストにしない。依存を一つずつ外し、欠陥が消えた境界が、その欠陥に要る最小の接続を示す。

同じ具体例を複数のレベルに残すのは、それぞれが別の欠陥を検出すると説明できるときだけである。たとえば下位が意味の正しさを、上位が接続の成立を確かめる。説明できなければ、下位へまとめる。

## サイズは、使う資源で決める

サイズはテストの種類の別名ではない。実際に使う資源と隔離の範囲で決める。

| サイズ | 使ってよい資源 | 代表的な対象 |
|---|---|---|
| Small | 単一プロセスの中だけ。ネットワーク、外部ストレージ、外部ファイルシステムを使わない | 業務判断、純粋な変換、局所的な調停 |
| Medium | 単一マシンの中。localhost、実ストレージ、実キャッシュ、エミュレーターを使える | 永続化、公開インターフェース、契約、単一ワーカー |
| Large | 複数プロセスやサービスの協調、または制御できない境界 | 主要な E2E、非同期経路、外部連携 |

同じ公開インターフェースのテストでも、単一プロセスの中で完結すれば Small、localhost の実ストレージを使えば Medium になる。E2E という名前だけで Large にしない。実行時間は結果として計測するもので、未計測の秒数をサイズの定義に使わない。

## テストレベルの責務

層の名前やアーキテクチャが違っても、観測する責務で対応させる。対象に該当する責務が無ければ、表を埋めるためにレベルを作らない。

| レベル | 主に確かめること | 主担当にしないこと |
|---|---|---|
| 業務判断 | 成立条件、拒否理由、不変条件、状態遷移、値の境界 | 永続化方式、通信表現、配線 |
| 永続化 | 実ストレージの制約、変換、原子性、競合、読み戻し | 業務条件の全組み合わせ |
| 調停 | 複数判断の調停、処理順、原子性の境界、外部境界への依頼 | 保存の詳細、通信形式の全項目 |
| 公開インターフェース | 認証主体、入力変換、成功と失敗の表現、冪等性、ページング | 業務条件の網羅、保存実装 |
| 契約 | 機械可読な定義の互換性、共有する具体例の意味 | 全体の配線、可用性 |
| E2E | 公開入口から実ストレージ、非同期処理、観測結果までの重要な接続 | 境界値の総当たり、全拒否理由 |
| 静的検査 | format、lint、型、生成差分、互換性、禁止依存 | 実行時の意味 |

業務判断はドメインモデルに限らず、業務上の結果を持つ関数、サービス、ルールエンジンにも対応させる。永続化も RDB に限らない。

## 異常系を含め、実行順に依るテストを作らない

品質リスクには、接続できない、期限が切れる、制約に反する、途中で取り消される、といった異常系も含め、それぞれ主担当のレベルを決める。異常系が抜けると、失敗したときの振る舞いをどのテストも守らない。

ロック待ちや並行処理の実行順で結果が変わるテストは作らない。落ちても原因が分からず、信頼されなくなるからである。競合を防ぐ仕組み（一意制約、条件付きの更新、版の不一致）は、順に実行できる制約違反と古い版のテストで確かめる。並行に動かす必要があれば、バリアなどで順序を固定する。

テストは固定の時間を待たず、外から観測できる条件（状態、event、応答、query）が成り立つまでを期限付きで待つ。固定の sleep は、待つ条件を観測できないか、時計を制御できていないことの症状なので、設計の不足として戦略に書く。

## テストのために実装を曲げず、業務の言葉で名付ける

テストから確かめるのは公開している振る舞いだけにする。テストのためだけに内部を公開したり、本番に要らない分岐を足したりしない。「すべての値が表にある」のような網羅は、一覧を公開してテストで回すのではなく、定義と表を突き合わせる静的な検査で守る。

テストの名前とテスト支援の部品の名前は、業務の資料にある言葉で付ける。業務の概念を持たない技術の部品（DB の起動など）だけを技術の言葉で名付ける。

## 境界シナリオと設計資料の点検

公開 API、CLI、イベント、ジョブのように他のコンポーネントが依存する境界があるなら、境界シナリオを、テストコードとも業務知識の写しとも別の設計資料として扱える。境界が無い対象には要求しない。入力の同値クラスと境界値は表へまとめ、状態、再送、順序、競合で初めて差が出るものは具体的なシナリオにする。「不正な値」とは書かず、外した条件と具体値を書く。

業務知識、データモデル、インターフェース定義などの設計資料は、書き換えない。資料を書き換えてよいのは、その資料を作る入口だけだからである。戦略は、資料の例がどのレベルで最も価値を持つかを仕分け、資料の持ち主への提案として書く。規則の意味を理解するための最小の例は資料に残るべきもので、網羅が目的の例は変更ごとのテスト設計へ送る。

## CI は、ローカルの完了判定と同じ入口を呼ぶ

「手元で通った」と「CI で通った」は、同じ検査の集合を指さなければならない。ずれていると、base は手元より弱い検査で緑になり、手元で見つかるはずの欠陥が入る。

そのため CI は、ローカルの完了判定の入口（`make verify` のような一つの command）をそのまま呼ぶ形を既定にする。工程を分けるなら、入口の構成要素と CI の工程の対応を書き、集合の一致を機械で検査する。秘密値や共有の外部環境が要る検査を CI から外すなら、理由と、代わりに実行する場所と時点を書く。build tag などで既定の実行から黙って外さない。外部の実物へ接続するテストは、利用者と repository の接続の許可に従うので、その許可が置かれた場所を書く。

段階の順は、静的検査、Small、Medium、Large を既定にし、観測した実行時間、並列化の単位、失敗の診断のしやすさで具体化する。観測値が無ければ時間の上限を決めず、何を計測して見直すかを書く。失敗したテストを無条件に再実行して緑にしない。

## 変更ごとの設計資料が決めること

全体の戦略は、個々の変更のシナリオを持たない。境界シナリオ、E2E シナリオ、探索計画は、変更ごとに次を決める。増減する品質リスク、根拠にした資料、既存テストが実際に保証していること、残るリスク、主担当のレベルとサイズ、上位へ重複させなかった項目とその理由、変更後も残る未検証のリスクである。

既存テストは、あるだけでは証拠にならない。対象のリスクに対する刺激、観測結果、使う依存を説明でき、実行した記録があって初めて、実行済みの証拠として数える。

## 詳細を分ける品質領域

性能、セキュリティ、探索的テストは、目的、入力、環境、合否が通常の機能テストと違う。利用者が中心の対象に指定しない限り、戦略では詳細化せず、別に扱う理由、後続に要る入力、今の戦略が残す観測点だけを書く。認証と認可の機能的な振る舞いは、公開インターフェースのテストに残せる。
