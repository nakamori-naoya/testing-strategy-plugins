# design-test-strategy

対象リポジトリで起こり得る品質上の失敗から、何をどの境界とサイズで確かめ、どこへ重ねないかを決め、変更ごとのテスト設計が従う戦略資料を1本保存する。

判断の中身は[テスト戦略の判断基準](references/test-strategy-judgment.md)が持つ。調べ始める前に全文読む。最小の担当レベル、サイズ、差し替えてよい境界の定義は、そこから戦略資料へ、対象リポジトリの言葉で書き写す。後続のシナリオ設計と探索計画は、この戦略資料だけを読んで配分を決めるからである。

## 入力

`target_repository`（戦略を適用するリポジトリの絶対パス）、`request`（目的、既知の制約、重視するテスト思想）、`document_destination`（新規は `{output_directory, name}`、更新は `{update_target}`、どちらも絶対パス）が要る。`references` は、追加で従う資料の絶対パスの配列で、任意である。

## 進め方

進める順は、隣の `playbook.yml` の工程に従う。各工程で外しやすい判断は次のとおりである。

**観測した事実だけを現状として書く。** コード、テスト、CI、設計資料、ローカルの完了判定の入口を調べ、観測できたものを現状、利用者と合意した方針を目標として分けて書く。存在しないテストや、計測していない実行時間を補わない。資料だけのリポジトリでも、現状と目標を分けて戦略は作れる。

**機能一覧ではなく失敗から始める。** 利用者から見た失敗、業務判断の誤り、状態の破壊、境界の不整合、プロセス間の接続の失敗、遅いフィードバックを品質リスクにし、それぞれに最小の観測境界と根拠資料を対応させる。

**既存テストは名前ではなく、使う資源で分類する。** 詳細な BDD や設計資料があっても書き換えず、どの例がどのレベルで最も価値を持つかを、資料の持ち主への提案として書く。

**問うのは、答えで戦略が変わることだけにする。** 古典派から外す境界、実物を使えない協働先、最重要のリスク、残す E2E、フィードバックの制約、今回切り離す品質領域のうち、調べても決まらないものを、観測した事実に基づく推奨と理由を添えて公開 playbook `grill` へ渡す。合意しなかった論点は、推奨を仮説として書き、見直す条件を添えて未決に残す。

**本文は判断を文章で書く。** 書き方は `write-doc` の書くときの規範（`references/writing-norms.md`）に従う。表は、テストレベルごとの責務やサイズの定義のように、同じ属性を行で比べる箇所だけに使う。図は、配置、依存、実行順が本文より明確になるときだけ使う。

**保存は `write-doc` に任せ、保存したものを読み戻す。** 本文を `material: [{kind: text, content: <本文>}]` として、`document_destination` と `references` とともに公開 playbook `write-doc` へ渡す。保存した資料を読み、実装者が新しい変更について「どの品質リスクを、どのレベルとサイズで確かめ、どこへ重複させないか」を判断できるかを確かめる。足りなければ直し、直せない不足は未決として残して `unresolved` にする。

## 止まるとき

欠けた情報が戦略の結論を変えるときは止まり、確かめた事実、必要な入力や許可、再開の条件を返す。たとえば、対象リポジトリや保存先を絶対パスで特定できない、クラウドや外部システムへ接続しなければ調べられず許可が無い、依頼がテストコードの実装や CI の変更だけを求めている、といった場合である。結論を変えない揺れや資料の不足では止まらず、最も筋の良い方針を仮説として置き、根拠と見直す条件を書いて進む。

## 出力

保存した戦略資料の絶対パスと、`status`（`ready` か `unresolved`）、合意した決定、仮説、未決を返す。テストコード、CI 設定、性能試験、セキュリティ診断は実行していないので、実施済みや合格とは報告しない。
