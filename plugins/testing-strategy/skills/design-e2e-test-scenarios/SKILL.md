# 重要価値経路のE2Eテストシナリオを設計する

このskillを読み終えたagentは、公開入口から複数の実コンポーネントを通り、外部から価値または結果を観測する重要経路について、どの接続を実構成で確かめるか判断できるMarkdownを1本保存できる。

E2Eは画面テストの別名ではない。入口は画面、API、CLI、イベント、ジョブのいずれでもよい。業務境界値、全拒否理由、入力形式の全組み合わせは下位の主担当へ置き、E2Eでは接続の成立を検証する代表例だけを扱う。

## 入力

- `target_repository`: 必須。調査対象の絶対path
- `request`: 必須。設計する理由、変更内容、重視する価値またはリスク
- `test_strategy_path`: 必須。確定済みテスト戦略Markdownの絶対path
- `scope`: 必須。対象価値経路、変更またはリリースの範囲
- `references`: 任意。要件、ユーザージャーニー、業務知識、データモデル、境界シナリオ、構成資料などの絶対path配列
- `document_destination`: 必須。新規は`{output_directory, name}`、更新は`{update_target}`のどちらか一方。pathは絶対pathとする

特定のUI、通信方式、データストア、言語、テストフレームワークを前提にしない。

## 判断根拠

シナリオを組み立てる前に、[E2Eシナリオの判断基準](references/e2e-scenario-judgment.md)を全文読む。

中心となる判定は次のとおりである。

| 観察対象 | 判定と行動 |
|---|---|
| 価値経路 | 利用者または外部利用者の重要な目的と最終結果を結ぶ経路なら候補にする |
| E2Eへ残す欠陥 | 複数構成の配線、非同期完了、実際の主体伝播、実構成の協調でなければ再現できない場合に残す |
| 下位へ移す欠陥 | 単一の業務判断、境界変換、永続化制約で同じ失敗を再現できれば、その最小レベルを主担当にする |
| 外部境界の代替 | 制御不能な外部境界だけを契約を保つ代替へ置き換え、制御可能な内部協働先は実物を優先する。外部サービスに公式のテスト用経路があればそれを使う |
| 共有の外部環境 | 作る主体に所有の印を付け、実行前に接続先を照合し、状態を変えるE2Eは自動再試行しない |
| サイズ | E2Eという名称ではなく、実際のプロセス、サービス、制御不能な依存の範囲で決める |

## 手順

### 1. 対象と規約を固定する

入力pathを検査し、対象リポジトリへ適用される規約と`references`を読む。戦略から品質リスク、重要経路、テストレベル、サイズ、実物境界、重複排除を抽出する。戦略を作り直さない。

### 2. coverage mapを作る

対象経路について、品質リスク、既存の検証証拠、残余リスク、同じ欠陥を再現できる最小の担当レベル、サイズ、意図した重複排除を対応付ける。下位で保証済みの意味と、E2Eに残る接続を分ける。

### 3. 価値経路と実構成を調べる

外部から観測できる開始状態、公開入口、通過するコンポーネント、同期・非同期境界、実際の主体、最終結果、失敗時の観測点をコードと資料から調べる。存在しない構成や未観測の経路を補わない。

### 4. E2E候補を絞る

重要度、障害影響、変更頻度、過去の接続不良、下位で得られない忠実度から候補を選ぶ。各候補について、同じ失敗をより小さい境界で再現できるか判定し、できる場合は下位へ送る。

上位に残す候補には、下位では失われる接続上の理由を必須とする。件数比率は固定しない。

### 5. 成果を変える未決をgrillへ渡す

調査しても決まらず、答えで重要価値経路、実物境界、最終oracle、外部代替、リリース判断が変わる問いだけを選ぶ。観測事実に基づく推奨と理由を付け、公開playbook `grill`へ渡す。

返った決定を本文へ反映する。残った未決は推奨を仮説として置き、採らなかった案、確認方法、見直し条件を書く。

### 6. E2Eシナリオを設計する

各シナリオに、達成する目的、開始状態、公開入口、経由する実コンポーネント、代替する制御不能な外部境界、価値へ到達する最小の操作列、完了を判断するoracle、最終結果、データ隔離と後処理、失敗時の観測点、下位で繰り返さない項目、サイズを含める。

非同期処理の完了を固定sleepで表さない。外部から観測できる状態、event、queryまたは通知を完了条件にする。観測方法が無い場合は、テスト手順で迂回せず診断可能性の不足として残す。

### 7. 資料を組み立てる

対象と選択理由、現在の検証証拠、価値経路、具体シナリオ、実物と代替の境界、データ隔離、失敗診断、下位との責務分担、仮説と未決を含む本文を作る。

同じ業務例を下位とE2Eに残す場合、下位が意味の正しさ、E2Eが接続の成立を担当するなど、異なる欠陥とoracleを明記する。

### 8. 保存して読み戻す

組み立てた本文を`material: [{kind: text, content: <本文>}]`、入力の`document_destination`、`references`として公開playbook `write-doc`へ渡す。失敗なら理由を変えず停止する。

保存した資料を全文読み、重要価値経路が選ばれていること、実構成でしか検出できない欠陥が示されていること、完了条件が観測可能であること、下位との重複理由があること、サイズが依存範囲と一致することを評価する。

欠落があれば修正前に欠落集合を固定し、その集合を解消する一度の更新を行う。再読後に同じ欠落または新たな重大欠落があれば、追加修正を反復せず`unresolved`として根拠と再開条件を残す。

## 停止条件

**止まる。** 必須pathを特定できないか読めない、保存先が不正、戦略資料が品質リスクと配分を定義していない、対象となる価値経路を特定できない、外部環境へ許可なく接続しなければ成果が無意味になる、`grill`または`write-doc`が失敗して回復できない場合である。

**仮説を明示して進む。** 重要経路、完了条件、実物境界、サイズが一意でない場合は、根拠の強い案を仮説として採り、採らなかった案、確認方法、見直し条件を資料へ書く。

## 出力

- 正式な定義: 保存したE2EシナリオMarkdown 1本の絶対path
- 公開結果: `status`（`ready`または`unresolved`）、扱った価値経路、仮説、未決、正式な定義のpath
- 報告: 調べた構成、既存証拠、下位へ移した項目、E2Eへ残した接続理由、実物と代替の境界、未検証範囲

E2Eテストコード、環境、CI設定は変更していないため、実装済みまたは実行済みと報告しない。
