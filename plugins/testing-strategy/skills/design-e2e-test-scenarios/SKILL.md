# 重要価値経路の E2E テストシナリオを設計する

公開入口から複数の実コンポーネントを通り、利用者か外部利用者が価値や結果を観測する重要な経路について、どの接続を実構成で確かめるかを判断できるシナリオ資料を1本保存する。E2E は画面テストの別名ではない。入口は画面、API、CLI、イベント、ジョブのどれでもよい。

入力は `target_repository`、`request`、`test_strategy_path`（確定済みのテスト戦略）、`scope`（対象の価値経路と変更の範囲）、`document_destination` と、任意の `references` である。戦略資料の読み方、既存テストの証拠の扱い、問い方、保存と読み戻しは、内部判断 `map-test-coverage` に従う。ここには、E2E に固有の判断だけを書く。

## E2E に残すのは、実構成でしか再現しない欠陥だけである

複数のプロセスやサービスの配線、非同期処理の受付から最終観測まで、実際の認証主体の伝播、下位では再現できない実構成の協調が本質のときだけ、E2E に残す。業務の境界値、全拒否理由、入力形式の組み合わせ、単一の adapter の保存制約は、下位のレベルへ送る。

候補は、目的を果たせないときの影響、下位では検出できない接続の数と重要さ、変更の頻度と過去の接続不良、リリース判断に要る代表性の順で比べる。件数やピラミッドの比率は決めない。追加する各シナリオに、下位へ移せない理由を求める。同じ業務例を下位にも残すなら、下位が意味の正しさを、E2E が接続の成立を確かめる、のように別の欠陥を書く。

## 外部は公式のテスト用経路を使い、共有の環境では自分の作ったものだけを触る

何を実物にし何を差し替えるかは、戦略資料の差し替えの境界に従う。外部サービスが公式のテスト用経路を持つなら、それを使う実物の接続を既定にし、代替は公式の経路でも自動化できない操作（外部の画面でのアカウント選択など）だけにする。代替したら、代替した境界と理由、実物との差、その差を確かめる場所を書く。

共有の外部環境（開発用の環境や共用のテストアカウント）に作る主体には、識別子の接頭辞のような所有の印を付け、後処理はその印を持つものだけに限る。実行の前に、接続先が意図した環境であることを識別子で照合する。外部環境への接続は利用者と repository の接続の許可に従うので、シナリオごとに、その許可が置かれている場所を書く。許可が無ければ、誰がいつ実行するかを書く。

共有の環境の状態を変える E2E は、自動で再試行しない。再試行すると最初の失敗の証拠が上書きされ、半端に作られた主体が残るからである。

## 開始状態は、本番と同じ書き込み経路で作る

生の行を直接入れると、本番の経路なら守られる不変条件を破った状態から始まる。開始状態は公開入口や usecase で作り、本番の経路に無い準備（テスト用の主体の登録など）だけを準備専用の経路にする。

## 各シナリオが持つもの

各シナリオには、達成する目的、開始時に外から観測できる状態、公開入口、経由する実コンポーネント、差し替える制御できない境界、価値へ届く最小の操作列、完了を判断する条件、最終的に観測する結果、データの隔離と後処理、失敗の原因を切り分ける観測点、下位で繰り返さない項目、実際に使う資源に基づくサイズを書く。非同期の完了は固定の sleep ではなく、外から観測できる状態、event、query、通知で判断する。観測する方法が無ければ、テストの手順で迂回せず、診断できないことを不足として残す。
