# 残余リスクに基づく探索的テストを計画する

このskillを読み終えたagentは、既知の回帰確認を繰り返さず、既存の自動テスト後に残る未知へ探索を配分し、発見を再現可能な欠陥シナリオ、自動チェック、TDDによる修正へ引き継げる計画Markdownを1本保存できる。

このskillは探索を実行せず、テストコードを書かず、バグを修正しない。探索の実施者が証拠を残し、後続のエンジニアが同じ欠陥を再現して最小レベルへ自動化できる条件までを計画する。

## 入力

- `target_repository`: 必須。調査対象の絶対path
- `request`: 必須。探索する理由、変更またはリリース、利用可能な情報
- `test_strategy_path`: 必須。確定済みテスト戦略Markdownの絶対path
- `scope`: 必須。対象変更、機能、価値経路またはリリースの範囲
- `references`: 任意。要件、ユーザージャーニー、業務知識、データモデル、境界・E2Eシナリオ、過去障害、テスト結果などの絶対path配列
- `document_destination`: 必須。新規は`{output_directory, name}`、更新は`{update_target}`のどちらか一方。pathは絶対pathとする

性能、負荷、セキュリティ、アクセシビリティの専門試験は、利用者がこの計画のscopeとして明示しない限り対象に含めない。認証・認可の機能的振る舞い、通常操作で観測できる回復性や診断可能性は扱える。

## 判断根拠

計画を組み立てる前に、[探索から再現・自動チェック・修正へつなぐ判断基準](references/exploratory-judgment.md)を全文読む。

中心となる判定は次のとおりである。

| 観察対象 | 判定と行動 |
|---|---|
| 既存自動テスト | 主要リスクへの刺激、観測結果、実行状態を確認できれば既知の回帰範囲とする。存在だけなら証拠不足として分ける |
| 探索対象 | 自動チェック済みの既知期待ではなく、状態系列、境界間の組み合わせ、人の判断、回復性、診断可能性などの残余リスクを選ぶ |
| 発見 | 観察事実、期待との差、再現した条件としなかった条件を分けて記録する |
| 欠陥化 | 別の実施者が同じ初期状態、入力、操作列で期待との差を観測できれば再現可能な欠陥とする |
| 自動化先 | 発見時の操作レベルではなく、同じ失敗を再現できる最小の担当レベルへ置く |
| 修正開始 | 未修正コードで自動チェックが意図した理由により失敗することをRedとして確認してから修正へ渡す |

## 手順

### 1. 対象と規約を固定する

入力pathを検査し、対象リポジトリへ適用される規約と`references`を読む。戦略から主要な品質リスク、テストレベル、サイズ、実物境界、重複排除、探索を別途扱う理由を抽出する。簡易戦略を作り直さない。

### 2. coverage mapを作る

品質リスクごとに、既存の検証証拠、実行状態、残余リスク、同じ欠陥を再現できる最小の担当レベル、サイズ、意図した重複排除を対応付ける。「SmallとMediumが十分にある」という申告だけを証拠にしない。

基礎的な自動テストが不足していても計画作成は続ける。ただし、探索で回帰保証を代替せず、「自動化の前提不足」と「それでも今回探索する理由」を分ける。

### 3. 変更と未知を調べる

変更差分、品質リスク、境界・E2Eシナリオで意図的に省略した項目、過去障害、不安定なテスト、ログと状態表示を調べる。既知の期待だけを再実行する候補と、探索で学ぶ価値がある未知を分ける。

### 4. charter候補を選ぶ

状態遷移、順序、割込み、回復、データ差、境界間の組み合わせ、利用者の判断、診断可能性などから、残余リスクを減らすcharterを選ぶ。固定テストケースのように逐次手順へ細分化しない。

探索中に派生し得る重要な問いは、元のmissionを失わないようthreadまたは後続charterへ分ける。時間枠は対象と利用可能時間から決め、固定の分数をハーネスに埋め込まない。

### 5. 成果を変える未決をgrillへ渡す

調査しても決まらず、答えでmission、優先する残余リスク、利用可能な環境、oracle、探索後の引継ぎ先が変わる問いだけを選ぶ。観測事実に基づく推奨と理由を付け、公開playbook `grill`へ渡す。

返った決定を計画へ反映する。残った未決は推奨を仮説として置き、採らなかった案、確認方法、見直し条件を書く。

### 6. 計画と記録契約を作る

計画には、Mission、根拠リスク、Charter、Setup、Heuristics、Oracle、Evidence、Finding disposition、Reproduction、Automation handoff、Debrief、Stopを含める。

発見記録には、元のcharter、環境と初期状態、具体入力、操作列、実際の結果、期待する結果と根拠、再現頻度、再現した条件、再現しなかった条件、関連するログや時刻を残すよう要求する。

### 7. 後工程への判定を設計する

各発見を、仕様どおり、要件またはoracleの不明、追加探索、再現可能な欠陥へ分類する条件を書く。再現可能な欠陥には、自動チェックにする理由、最小の担当レベル、Small・Medium・Large、保持する実物境界、上位で重複させない範囲を付ける。

自動チェックは、未修正コードで期待した理由により失敗することを修正開始の条件にする。修正後は同じチェックが通り、coverage mapへ回帰証拠として追加されることを引継ぎ完了条件にする。

### 8. 保存して読み戻す

組み立てた本文を`material: [{kind: text, content: <本文>}]`、入力の`document_destination`、`references`として公開playbook `write-doc`へ渡す。失敗なら理由を変えず停止する。

保存した資料を全文読み、残余リスクに集中していること、既知の回帰手順を探索へ置いていないこと、発見から再現への証拠が定義されていること、自動化先が最小の担当レベルであること、Redから修正へ渡す条件があることを評価する。

欠落があれば修正前に欠落集合を固定し、その集合を解消する一度の更新を行う。再読後に同じ欠落または新たな重大欠落があれば、追加修正を反復せず`unresolved`として根拠と再開条件を残す。

## 停止条件

**止まる。** 必須pathを特定できないか読めない、保存先が不正、戦略資料が品質リスクと配分を定義していない、探索対象となるscopeを特定できない、外部環境へ許可なく接続しなければ成果が無意味になる、`grill`または`write-doc`が失敗して回復できない場合である。

**仮説を明示して進む。** 自動テストの実行状態、残余リスク、oracle、環境、最小の自動化先が一意でない場合は、根拠の強い案を仮説として採り、採らなかった案、確認方法、見直し条件を計画へ書く。

## 出力

- 正式な定義: 保存した探索的テスト計画Markdown 1本の絶対path
- 公開結果: `status`（`ready`または`unresolved`）、対象mission、主要charter、仮説、未決、正式な定義のpath
- 報告: 確認した自動テスト証拠、選んだ残余リスク、探索から再現・自動チェック・TDDへ渡す条件、専門戦略へ分けた領域、未検証範囲

探索、テストコード実装、バグ修正は実行していないため、発見済み、再現済み、修正済みと報告しない。
