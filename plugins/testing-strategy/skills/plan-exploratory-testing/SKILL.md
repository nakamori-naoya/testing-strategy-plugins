# 残余リスクに基づく探索的テストを計画する

既知の回帰確認を繰り返さず、自動テストの後に残る未知へ探索を配分し、発見を再現できる欠陥、自動チェック、TDD による修正へ引き継げる計画を1本保存する。探索の実行、テストコードの実装、修正はしない。

入力は `target_repository`、`request`、`test_strategy_path`（確定済みのテスト戦略）、`scope`（対象の変更、機能、リリースの範囲）、`document_destination` と、任意の `references` である。戦略資料の読み方、既存テストの証拠の扱い、問い方、保存と読み戻しは、内部判断 `map-test-coverage` に従う。ここには、探索に固有の判断だけを書く。性能、負荷、セキュリティ、アクセシビリティの専門試験は、利用者が scope に指定したときだけ扱う。

## 探索するのは、自動テストが確かめていない未知である

探索は、既知の期待を同じ手順で確かめ直す回帰テストではない。単一の操作だけが確かめられていて別の状態の系列が分からない箇所、複数の境界の組み合わせ、利用者の判断や回復のしやすさ、変更差分と過去障害が交わる箇所、失敗したときの診断のしやすさ、シナリオ資料が意図して省いた残余リスクを選ぶ。

自動テストが足りないときも、探索で回帰の保証を代わりにしない。足りないことを別に記録し、それでも探索する理由を品質リスクから書く。

## charter は方向を示し、手順を固定しない

charter は、対象、試す方向、観察する品質を一文で表す。操作を逐次に固定せず、実施者が観察から次の行動を選べる余地を残す。探索中に重要な枝が出たら、元の目的を失わないよう thread として追うか、後続の charter へ分ける。時間枠は、対象と使える時間から決める。

異常を疑う根拠は一つに限らない。要件や業務知識との不一致、同じ目的を持つ別の経路や以前の版との不一致、順序を変えても保たれるべき関係、利用者が回復できない、状態を理解できない、原因を診断できない、といったことも根拠になる。期待の根拠が無ければ、欠陥と決めつけず、要件の持ち主へ判断を戻す。

## 発見は、証拠を残してから次へ渡す

発見の記録には、元の charter、環境と初期状態、具体的な入力と操作の列、実際の結果、期待と根拠、再現した回数と条件、再現しなかった条件、関連するログや時刻を残すよう求める。一度だけ起きた観察を、再現できる手順として清書しない。

発見は、仕様どおり、期待の根拠が不明、追加の探索が要る、再現できる欠陥、のどれかに分ける。再現できる欠陥とは、別の実施者が同じ初期状態、入力、操作列で期待との差を観測できるものである。

## 再現できる欠陥は、最小のレベルの失敗するチェックにして修正へ渡す

発見したときの操作のレベルではなく、戦略資料の規則に従い、同じ失敗を再現できる最小の担当レベルとサイズへ置く。依存を一つずつ外し、欠陥が消えた境界が、要る接続を示す。

修正を始める条件は、そのチェックが未修正のコードで、意図した理由により失敗することである。環境の不良、fixture の不備、別の既知の欠陥による失敗は、この失敗に数えない。修正後は同じチェックが通り、新しい回帰の証拠になることを、引き継ぎの完了とする。期待の根拠が決まらない、再現の条件を絞れない、欠陥ではなく学びである、保守の費用が回帰のリスクを上回る、というときは自動化せず、状態、根拠、次の持ち主、再開の条件を残す。
