# プログラム境界のテストシナリオを設計する

このskillを読み終えたagentは、エンジニアが一つ以上のプログラム境界について、どの具体例をどのテストレベルとサイズで実装し、何を別レベルへ重複させないか判断できるMarkdownを1本保存できる。

ここでいうAPIは通信方式を限定しない。同期呼び出し、メッセージ、イベント、ジョブ、ライブラリ境界など、別のコンポーネントが契約へ依存するプログラム境界を扱う。業務規則の網羅、永続化方式の詳細、価値経路全体の接続は、それぞれの主担当へ戻す。

## 入力

- `target_repository`: 必須。調査対象の絶対path
- `request`: 必須。設計する理由、変更内容、重視するリスク
- `test_strategy_path`: 必須。確定済みテスト戦略Markdownの絶対path
- `scope`: 必須。対象境界、操作、メッセージ、変更またはリリースの範囲
- `references`: 任意。要件、業務知識、データモデル、機械可読なインターフェース定義、既存シナリオなどの絶対path配列
- `document_destination`: 必須。新規は`{output_directory, name}`、更新は`{update_target}`のどちらか一方。pathは絶対pathとする

入力に機械可読なインターフェース定義が無くても、コード上の公開境界を調べられる場合は継続する。特定のIDL、通信方式、データストア、言語、テストフレームワークを前提にしない。

## 判断の正本

シナリオを組み立てる前に、[プログラム境界シナリオの判断基準](references/api-scenario-judgment.md)を全文読む。

中心となる判定は次のとおりである。

| 観察対象 | 判定と行動 |
|---|---|
| 境界で検証する意味 | 認証主体、入力変換、成功・失敗表現、互換性、再試行、冪等性など、境界を通すことで初めて観測できるなら残す |
| 業務条件 | 境界を通さず同じ欠陥を再現できれば業務判断レベルを主担当にし、境界では代表例だけを残す |
| 永続化詳細 | 実ストレージの制約、原子性、問い合わせが本質なら永続化レベルへ置く |
| 入力差 | 同じ結果になる値は同値クラスへまとめ、結果が切り替わる境界値を具体化する |
| 操作列 | 状態、再送、順序、競合で結果が変わる場合だけ複数ステップにする |
| サイズ | 名前ではなく実際の依存範囲からSmall・Medium・Largeを決める |

## 手順

### 1. 対象と規約を固定する

入力pathを検査し、対象リポジトリへ適用される規約と`references`を読む。`test_strategy_path`から品質リスク、テストレベル、サイズ、実物境界、重複排除の方針を抽出する。戦略を簡易的に作り直さない。

### 2. coverage mapを作る

対象範囲について、品質リスク、既存の検証証拠、残余リスク、同じ欠陥を再現できる最小の担当レベル、サイズ、意図した重複排除を対応付ける。既存テストの存在と実行済みの証拠を分ける。

### 3. 境界の正本を調べる

対象操作、入力、出力、失敗表現、認証主体、状態変化、副作用、再試行意味を、コード、インターフェース定義、要件、業務知識、データモデルから調べる。機械可読な定義から分かる構造と、人が判断する意味を混ぜない。

### 4. シナリオ候補を絞る

入力同値クラス、境界値、状態、再送、順序、競合を調べる。「不正な値」「成立条件を満たさない」のような抽象入力は、外した条件、具体値、対照となる成立値、期待結果まで具体化する。

各候補について、同じ欠陥をより小さい境界で再現できるか判定する。下位で再現できる場合は下位を主担当にし、境界でしか観測できる欠陥だけをこの資料の中心へ残す。

### 5. 成果を変える未決をgrillへ渡す

調査しても決まらず、答えで対象境界、期待結果、再試行意味、互換性、主担当レベルが変わる問いだけを選ぶ。各問いへ観測事実に基づく推奨と理由を付け、公開playbook `grill`へ渡す。対話の作法はgrillへ委ねる。

返った決定を本文へ反映する。残った未決は推奨を仮説として置き、採らなかった解釈と見直し条件を書く。

### 6. シナリオ資料を組み立てる

資料には、対象と変更理由、品質リスクとの対応、境界inventory、入力区分、具体シナリオ、テスト配分、意図した省略、インターフェース定義との同期、仮説と未決を含める。

各具体シナリオは、安定した識別子、対象境界、検証するリスク、事前状態、具体入力、行為、観測結果、担当レベル、サイズ、使う実物境界、意図した省略を持つ。応答だけでなく、外部から観測可能な状態と副作用を書く。

### 7. インターフェース定義との同期を決める

機械可読な定義がある場合、操作、入力、出力、列挙値などの構造変化を決定論的に検出する処理と、その変化を具体シナリオへ反映する意味判断を分ける。資料には参照した定義の対象リポジトリ相対path、安定した項目識別子、確認時のdigestを記録する方針を示す。

CIはdigest差分を「意味の更新が必要」と検出できるが、本文を自動生成しただけで意味の更新済みとは扱わない。機械可読な定義が無ければ、コード上の公開境界との対応を記録し、存在しない生成基盤を要求しない。

### 8. 保存して読み戻す

組み立てた本文を`material: [{kind: text, content: <本文>}]`、入力の`document_destination`、`references`として公開playbook `write-doc`へ渡す。失敗なら理由を変えず停止する。

保存した資料を全文読み、抽象入力が残っていないこと、具体値と対照値があること、観測結果が境界から確認できること、担当レベルが最小の再現境界であること、意図した省略に理由があることを評価する。

欠落があれば修正前に欠落集合を固定し、その集合を解消する一度の更新を行う。再読後に同じ欠落または新たな重大欠落があれば、追加修正を反復せず`unresolved`として根拠と再開条件を残す。

## 停止条件

**止まる。** 必須pathを特定できないか読めない、保存先が不正、戦略資料が品質リスクと配分を定義していない、対象となるプログラム境界を特定できない、外部環境へ許可なく接続しなければ成果が無意味になる、`grill`または`write-doc`が失敗して回復できない場合である。

**仮説を明示して進む。** 期待結果、境界所有者、定義との対応、サイズが一意でない場合は、最も根拠の強い案を仮説として採り、採らなかった案、確認方法、見直し条件を資料へ書く。

## 出力

- 正本: 保存したプログラム境界シナリオMarkdown 1本の絶対path
- 公開結果: `status`（`ready`または`unresolved`）、対象境界、シナリオ数ではなく扱った品質リスク、仮説、未決、正本path
- 報告: 調べた定義とコード、既存証拠、下位へ移した項目、境界へ残した理由、同期方針、未検証範囲

テストコードとCI設定は変更していないため、実装済みまたは実行済みと報告しない。
