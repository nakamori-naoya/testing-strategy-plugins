# 業務の公開契約と API テストシナリオを設計する

一つの業務について、外へ公開する操作の契約と、それを確かめる具体シナリオを1本の資料に決めて保存する。この資料は、受け入れテストを最初に赤で置き、入口を実装するときの写し元になる。契約をどの資料も持たないと、受け入れテストは内側の層を作った後にしか書けず、入口の形を実装者が推測することになるからである。

入力は `target_repository`、`request`、`test_strategy_path`（確定済みのテスト戦略）、`crosscutting_design_path`（呼び手の識別と権限とエラーの分類を決めた横断的関心事の設計か、それを定めた要求）、`scope`（対象の業務と変更の範囲）、`document_destination` と、任意の `references` である。戦略資料の読み方、既存テストの証拠の扱い、担当レベルの配分、問い方、書き方は、内部判断 `map-test-coverage` に従う。ここには、この資料に固有の判断だけを書く。

## 公開契約は、この資料が決める

公開契約は、公開する操作（RPC、メッセージ、ジョブのように別のコンポーネントが呼ぶもの）、要求と応答の項目、操作ごとに返す Code と、その Code を受けた呼び手が同じ要求を再試行してよいかである。操作と項目の意味は業務知識とユーザージャーニーから、返す Code は業務知識の拒む理由と横断的関心事のエラーの設計から導き、拒む理由の一つずつがどの Code と公開の文言になるかを対応させる。業務知識に無い拒否や、業務知識と食い違う結果が要ると分かったら、契約に足さずに業務知識への提案として返す。資料から導けない値（項目の名前、一覧の件数、続きの読み方）は、推奨を仮説として置き、根拠と見直す条件を添える。

再試行の可否は、同じ要求を送り直して結果が変わりうるかと、変更が確定したかを呼び手が区別できるかで決める。時間切れや通信の断のように確定したか分からない Code には、再試行の前に何で今の状態を確かめるかまで書く。ここを書かないと、呼び手は二重の成立か取りこぼしのどちらかを選ぶしかない。

呼び手を誰と識別し、何を許すか（認証と認可）は、横断的関心事の設計が持つ。この資料はそれを指し、要求の項目で呼び手を名乗らせない。契約に書くのは外から観測できることだけで、内部の状態の表し方、処理の順、保存先は書かない。

## 境界を通して初めて観測できることだけを、中心に残す

境界が持つのは、呼び出し主体と認証・認可の結果、wire 表現から内部入力への変換、成功・拒否・競合・未検出・再試行可否の外部表現、冪等性と再送、ページングや順序、互換性、操作後に外から観測できる状態と副作用である。契約に載せた Code には、どれも一つ以上の代表のシナリオを置く。

業務の成立条件そのものは、境界を通さず同じ失敗を再現できるので、業務判断のレベルを主担当にする。上限の前後のような境界値の網羅はそちらへ送り、この資料には Code と文言を確かめる代表例だけを残す。保存の制約、原子性、同時に起きたときとやり直しを使い切ったときの結果が本質なら、永続化のレベルへ送る。

送るときは、観測するレベルを一つに決め、そこで何を起こして何を観測するかまで書く。送り先の資料にその BDD があれば番号で指し、無ければ送り先の資料の持ち主への提案にする。送り先を二つ並べたり、送り先の規約が確かめないと定めた観点を送ったりすると、どのテストもその結果を観測しないまま残るからである。公開の操作だけでは起こせない結果（やり直しを使い切ったときの Code）も、省く理由だけでなく、この観測する先を書く。

## 入力は、結果が切り替わる境界で具体化する

同じ結果になる値は同値クラスにまとめ、最小、有効な最大、上限超過のような差は表にする。「不正な値」「成立しない入力」で済ませず、外した条件、それを外す具体値、対照となる成立値、外へ返る結果、状態や副作用が起きないことまで書く。直交する入力を総当たりにしない。

一回の呼び出しでは差が出ず、状態、再送、順序、競合で結果が変わるときだけ、操作の列にする。完了は固定の sleep ではなく、外から観測できる条件で書く。

## 各シナリオが持つもの

各シナリオは、業務知識の BDD と同じ形の見出し（`### [BDD-<3桁以上の連番>] 見出し`）と、`Given:`、`When:`、`Then:` の具体例を持つ。実装はこの番号でシナリオをテストへ写し、業務知識と同じ検査で、どのシナリオもちょうど一つのテストが確かめたかを辿れるからである。結果が変わる例は、表の行に分けずに一つずつシナリオにする。各シナリオには、確かめる操作と品質リスク、主担当のレベルとサイズ、別のレベルへ送った項目とその理由も書く。観測結果は、応答の Code と項目に加えて、続けて呼んだ公開の操作から見える状態と副作用で書き、内部の表を直接見る形にしない。件数は決めない。同じリスクと結果を説明する例はまとめ、条件の差で結果か配置が変わる例だけを分ける。

## 機械可読な定義との同期は、構造と意味を分ける

機械可読なインターフェース定義があるなら、操作、項目、型、必須性、列挙値の差分は定義から機械で検出できる。成立条件、状態変化、再試行、冪等性、失敗の表現は、読んで判断する意味である。資料には参照した定義のパスと項目の識別子を記録し、構造の差分を直しただけで意味を更新したとは扱わない。定義がまだ無ければ、この資料の公開契約が定義の元になる。無い定義のパスや digest を事実として書かない。

## 保存する

本文を `material: [{kind: text, content: <本文>}]` として、`document_type: api-test-scenarios`、`document_destination`、`references` とともに `write-doc` へ渡す。節の構成と、検査が読む目印（シナリオの見出しと gherkin のブロック、Code の表の見出し行）は、その型のテンプレートに従う。保存した資料を読み戻し、実装者がこの資料だけから、受け入れテストの要求と期待する Code を書けるかを確かめる。足りなければ直し、直せない不足は未決として残して `status` を `unresolved` にする。

## 止まるとき

欠けた情報が契約か期待結果を変えるときは止まり、確かめた事実と再開の条件を返す。対象の業務の業務知識が無い、保存先を特定できない、外部環境へ許可なく接続しなければ調べられない、といった場合である。必須の入力のうち、テスト戦略が無いとき、または呼び手の識別と権限とエラーの分類を決める横断的関心事の設計（それを定めた要求でもよい）が無いときも、止まって、無い資料と、それで決まらない契約の箇所（レベルとサイズ、Code、呼び手の識別）を返す。テスト戦略は `design-test-strategy` が作る。結論を変えない揺れでは止まらず、仮説を明示して進む。テストコードは書いておらず実行もしていないので、実装済み、実行済みとは報告しない。

## 出力

保存した資料の絶対パス、`status`（`ready` か `unresolved`）、公開契約に載せた操作、合意した決定、仮説、未決、業務知識への提案を返す。
