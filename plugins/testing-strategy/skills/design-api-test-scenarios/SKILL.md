# プログラム境界のテストシナリオを設計する

一つ以上のプログラム境界について、どの具体例をどのレベルとサイズで実装し、何を別のレベルへ重ねないかを、エンジニアが判断できるシナリオ資料を1本保存する。API は通信方式を限らない。同期の呼び出し、メッセージ、イベント、ジョブ、ライブラリの関数のように、別のコンポーネントが依存する境界を扱う。

入力は `target_repository`、`request`、`test_strategy_path`（確定済みのテスト戦略）、`scope`（対象の境界と変更の範囲）、`document_destination` と、任意の `references` である。戦略資料の読み方、既存テストの証拠の扱い、問い方、保存と読み戻しは、内部判断 `map-test-coverage` に従う。ここには、境界シナリオに固有の判断だけを書く。

## 境界を通して初めて観測できることだけを、中心に残す

境界が持つのは、呼び出し主体と認証・認可の結果、wire 表現から内部入力への変換、成功・拒否・競合・未検出・再試行可否の外部表現、冪等性の key と再送、ページングや順序、互換性、操作後に外から観測できる状態と副作用である。

業務の成立条件そのものは、境界を通さず同じ失敗を再現できるので、業務判断のレベルを主担当にする。境界に残すのは、変換や外部表現を確かめる代表例だけである。保存の制約や原子性が本質なら、永続化のレベルへ送る。

## 入力は、結果が切り替わる境界で具体化する

同じ結果になる値は同値クラスにまとめ、最小、有効な最大、上限超過のような差は表にする。「不正な値」「成立しない入力」で済ませず、外した条件、それを外す具体値、対照となる成立値、どの境界が拒むか、外へ返る結果、状態や副作用が起きないことまで書く。直交する入力を総当たりにしない。組み合わせで結果が変わる根拠があるときだけ、組み合わせを独立させる。

一回の呼び出しでは差が出ず、状態、再送、順序、競合で結果が変わるときだけ、操作の列にする。同じ依頼の再送、成功後や拒否後の再試行、順序の入れ替え、同じ対象への競合、非同期の受付後の重複配送がこれに当たる。完了は固定の sleep ではなく、外から観測できる条件で書く。

## 各シナリオが持つもの

各シナリオには、通信方式に依らない安定した識別子、対象の境界、確かめる品質リスク、事前状態、具体入力、行為、応答だけでなく状態と副作用を含む観測結果、主担当のレベルとサイズと実物で使う境界、別のレベルへ送った項目とその理由を書く。件数は決めない。同じリスクと結果を説明する例はまとめ、条件の差で結果か配置が変わる例だけを分ける。

## 機械可読な定義との同期は、構造と意味を分ける

機械可読なインターフェース定義があるなら、操作、field、型、必須性、列挙値の追加や変更は、定義と digest から機械で検出できる。成立条件、状態変化、再試行、冪等性、失敗の表現、配置の判断は、読んで判断する意味である。資料には、参照した定義のパス、項目の識別子、確認したときの digest を記録する方針を書く。構造の差分を直しただけで、意味を更新したとは扱わない。定義が無ければ、コード上の公開境界との対応を記録し、無い生成基盤を求めない。
