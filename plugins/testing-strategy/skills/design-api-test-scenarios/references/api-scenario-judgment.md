# プログラム境界シナリオの判断基準

このreferenceは、APIを含むプログラム境界のどの具体例を資料へ残し、どの欠陥をより小さい担当レベルへ送るかを決める。特定の通信方式、IDL、言語、フレームワーク、データストアは所有しない。

## 境界で所有する意味

境界を通ることで初めて生じる変換と観測を扱う。

- 呼び出し主体と認証・認可の機能的な結果
- wire表現、message、引数から内部入力への変換
- 成功、拒否、競合、未検出、再試行可能性の外部表現
- 冪等性key、再送、重複配送の意味
- pagination、順序、cursor、streamの意味
- version、必須性、列挙値、互換性
- 操作後に外部から観測できる状態または副作用

業務上の成立条件や不変条件そのものは業務判断の正本から参照する。同じ条件の全組み合わせを境界シナリオへ複製しない。代表例を境界へ残す場合は、変換または外部表現を検証する例として残す。

## 入力区分

入力値は、結果が同じになる同値クラスと、結果が切り替わる境界で整理する。最小、有効最大、上限超過など、単一入力の差で表せるものは表へまとめる。

「不正」「成立しない」「形式が悪い」だけでは完成ではない。次を具体化する。

- 外した条件
- その条件を外す具体値
- 対照となる成立値
- どの境界が拒むか
- 外部へ返る結果
- 外部から観測できる状態または副作用の有無

複数項目の組み合わせは、組み合わせで結果が変わる根拠がある場合だけ独立させる。直交する入力を全組み合わせにしない。

## 状態を持つシナリオ

一回の呼び出しだけでは差が出ず、状態、再送、順序、競合で結果が変わる場合は操作列として表す。

- 同じ依頼の再送
- 成功後、拒否後、取消後の再試行
- 順序を入れ替えた操作
- 同じ対象への競合
- 非同期受付後の重複配送または再処理

固定sleepを完了条件にしない。状態、event、応答、queryなど、外部から観測可能な完了条件を書く。

## 最小の担当レベル

発見時または利用者の操作レベルを、そのままテスト配置にしない。同じ失敗を再現できる最小の境界を選ぶ。

- 業務条件だけで差が出るなら業務判断
- 実ストレージの制約や原子性で差が出るなら永続化
- 境界変換、認証主体、外部失敗表現で差が出るなら公開インターフェース
- 提供者と利用者が共有する例や互換性なら契約
- 複数構成の接続でなければ差が出ない場合だけE2E

上位に同じ値を残す場合は、下位と異なる欠陥またはoracleを説明する。

## シナリオの構造

| 要素 | 内容 |
|---|---|
| 識別子 | 通信方式やHTTP動詞に依存しない安定したID |
| 対象境界 | 操作、message、関数などの安定した識別子と定義の所在 |
| 検証するリスク | テスト戦略上の品質リスク |
| 事前状態 | 主体、対象状態、必要な既存データ |
| 具体入力 | 外した条件や同値クラスが分かる値 |
| 行為 | 一回の呼び出し、または順序に意味がある操作列 |
| 観測結果 | 応答、外部状態、副作用、非発生を含むoracle |
| 配分 | 主担当レベル、Small・Medium・Large、実物境界 |
| 意図した省略 | 別レベルへ置いた項目と重複させない理由 |

シナリオ件数は固定しない。同じ品質リスクと結果を説明する例は統合し、条件差で結果または配置判断が変わる例だけを分ける。

## 定義との同期

機械可読な定義がある場合、構造変化の検出と意味更新を分ける。

- 構造変化: 操作、field、型、必須性、列挙値、入出力の追加・削除・変更
- 意味更新: 成立条件、状態変化、再試行、冪等性、失敗表現、観測結果、配置判断

前者は定義とdigestから決定論的に検出できる。後者は要件、戦略、実装を読んで判断する。構造差分の解消だけで、意味上のシナリオを更新済みとしない。
