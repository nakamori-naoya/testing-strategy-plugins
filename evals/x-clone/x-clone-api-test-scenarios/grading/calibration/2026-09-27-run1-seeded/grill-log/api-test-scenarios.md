# grill の記録: フォローする・フォローを外すの境界シナリオ

この実行には問いに答える利用者がいないため、design-api-test-scenarios の agent が利用者の代わりに答えた。対象リポジトリの要件と設計資料、確定済みのテスト戦略（`test-strategy/test-strategy.md`）に書いてある事実で決まる論点は、問いにせず前提として示した。資料に無い論点だけを問い、推奨を仮置きした。仮置きした答えは決定ではない。資料の本文では「未決と仮説」に書く。

## 調べて決まったので問わなかった論点（この前提で進める）

- 公開 API の操作名は、フォローの業務知識「ユビキタス言語」のコマンドの英名に従い `FollowUser` と `UnfollowUser` とする。業務知識は「実装の名前はこれに従う」と書いている。
- 応答が届かずに再送した要求に、冪等キーは無い。フォローの業務知識 BDD-014 と BDD-016 は、後から届いた要求を拒むと決めている。バックエンド要件「ポストできる」は、ポストの冪等キーを初期リリースの対象外にしている。したがって、再送は「フォロー中の相手をフォローする」または「フォローしていない相手のフォローを外す」として拒まれる。
- フォローを外すときの拒否理由は、「他人として」と「フォローしていない相手」の二つだけである（フォローの業務知識「フォローを外す」）。
- 操作回数の上限は、フォローとフォロー解除の合計で20回/分と100回/日である。判定が止まったときは、フォローとフォロー解除を安全側へ拒否する（非機能要件「負荷保護」「信頼性」）。
- API はタイムライン用の Redis へ書き込まない（バックエンド要件「操作の成功境界」、非機能要件「整合性と鮮度」）。
- 回収のリースは5分、調停の対象は5分間進捗が無い要求、構造化 Error ログの対象は成立から30分を超えて未完了の要求である（フォローのコマンドデータモデル、非機能要件「データの保持」「運用性と観測」）。
- 反映は、同じ要求IDで再び処理できる（非機能要件「整合性と鮮度」）。古い更新は、現在のフォロー関係と一致しなければ拒む。フォロー解除の後に件数が足りなくなっても、キャッシュを補充しない（バックエンド要件「成立した事実の説明と回復」）。
- キャッシュが無い利用者は、次に閲覧したときに一次データから作り直す（非機能要件「整合性と鮮度」）。
- Clerk Backend API が止まっていても、登録済みの利用者は、保存済みのひも付けを使って業務 API を使える（非機能要件「信頼性」）。
- レベルとサイズと差し替えの線は、テスト戦略に従う。反映の担い手はテストのプロセス内で呼び、Pub/Sub の再配送を待たない（テスト戦略「非同期の冪等性と調停は…」）。

## 問いと答え（出た順）

### Q1 反映の要求は、どこまでをこの資料の境界にするか

- 問い: scope の「非同期の反映の要求まで」は、API が同じトランザクションで要求を積むところまでか。それとも、担い手がその要求を回収し、反映し、成功を記録し、調停が拾い直すところまで含むか。
- 推奨: 回収、反映、成功、重複配送、順序の入れ替え、リース、調停までを含める。ポストの配信と、キャッシュ全体の作り直しは含めない。
- 理由: テスト戦略の R8 と R9 は、フォロー解除の後に古い更新やポストが残る失敗を重い失敗に挙げている。これは要求を積んだ後の処理でしか起きない。テスト戦略「境界シナリオは、公開 API、配信のメッセージ、調停と作り直しに作る」も、メッセージの二度の到着とリース切れをシナリオにすると決めている。
- 答え（推奨を仮置き）: 推奨どおり。回収から調停までを含め、ポストの配信と作り直しは含めない。
- 根拠: 資料に、scope の範囲を決める記述は無い。推奨を仮置きした。採らなかった案は、要求を積むところまでに限る案である。

### Q2 失敗を、呼び出し側へどう表現するか

- 問い: 認証の失敗、未登録者、入力の誤り、各拒否理由、操作回数の上限、依存の停止を、gRPC のどの status と、どの理由の識別子で返すか。
- 推奨: 未認証は `UNAUTHENTICATED`、未登録者は `PERMISSION_DENIED` と `USER_NOT_REGISTERED` にする。入力の誤りは `INVALID_ARGUMENT` と `INVALID_USER_ID`、自分へのフォローは `INVALID_ARGUMENT` と `CANNOT_FOLLOW_SELF` にする。未登録の相手は `NOT_FOUND` と `USER_NOT_FOUND`、フォロー中の相手は `ALREADY_EXISTS` と `ALREADY_FOLLOWING` にする。上限は `FAILED_PRECONDITION` と `FOLLOW_LIMIT_REACHED`、フォローしていない相手の解除は `FAILED_PRECONDITION` と `NOT_FOLLOWING` にする。未登録の相手や自分を外そうとしたときも `NOT_FOLLOWING` にする。操作回数の上限は `RESOURCE_EXHAUSTED` と `RATE_LIMITED`、レート制限の判定の停止は `UNAVAILABLE` と `RATE_LIMIT_UNAVAILABLE`、一次データへ届かないときは `UNAVAILABLE` と `PRIMARY_DATA_UNAVAILABLE` にする。理由は `google.rpc.ErrorInfo` の `reason` で運ぶ。
- 理由: ユーザージャーニーは、利用者が「5,000人に達しているため」「操作回数の上限に達した」「フォローしていないため外せない」と、理由を見分けて知らされることを求めている。status だけでは、上限と操作回数を見分けられない。フォロー上限を `RESOURCE_EXHAUSTED` にしない理由は、時間をおいて再試行しても解けず、状態を変えなければ通らないからである。フォローを外すときの拒否理由は業務知識に二つしか無いので、未登録の相手も自分も `NOT_FOLLOWING` にそろえる。
- 答え（推奨を仮置き）: 推奨どおり。
- 根拠: 公開 API の契約（Protocol Buffers の定義、失敗の表現）はリポジトリに無い（テスト戦略「資料の持ち主への提案」）。推奨を仮置きした。採らなかった案は、上限を `RESOURCE_EXHAUSTED` にする案と、未登録の相手の解除を `NOT_FOUND` にする案である。

### Q3 「他人として」の要求は、呼び出しの上でどういう形をとるか

- 問い: 要求にフォロワー（操作する本人）の利用者IDの欄を置き、JWT の主体と食い違えば拒むのか。それとも、要求には相手の利用者IDだけを置き、本人は JWT だけから決めるのか。
- 推奨: 要求には相手の利用者ID（`followee_user_id`）だけを置く。本人は JWT の主体にひも付く利用者だけから決める。metadata などで自己申告された利用者IDは無視する。シナリオでは、U-0003 の JWT に `x-user-id: U-0001` を添えた要求が U-0003 の操作として扱われ、U-0001 のフォローが変わらないことを確かめる。
- 理由: バックエンド要件「利用者と権限の範囲」と非機能要件「セキュリティ」は、自己申告の利用者IDを根拠にしないと決めている。本人を名乗る欄が無ければ、照合を忘れる欠陥そのものが起きない。
- 答え（推奨を仮置き）: 推奨どおり。
- 根拠: API の契約が無いので、推奨を仮置きした。採らなかった案は、フォロワーの欄を置いて、食い違えば `PERMISSION_DENIED` にする案である。この案を採るなら、FU-04 と UF-03 の該当行の期待結果が拒否に変わる。

### Q4 拒まれた要求も、操作回数に数えるか

- 問い: 20回/分と100回/日の数え方に、入力の誤りや業務の理由で拒まれた要求を含めるか。
- 推奨: 認証済みで登録済みの利用者による `FollowUser` と `UnfollowUser` の呼び出しは、入力の誤りや業務の理由で拒まれても数える。認証で拒まれた要求は、利用者IDが決まらないので数えない。操作回数の上限で拒まれた要求も数えない。
- 理由: 操作回数の上限は、一人の利用者の短時間の集中から、ほかの利用者の操作を守るためのものである（バックエンド要件「負荷から必要になる性質」）。拒まれる要求も API と一次データを使う。上限で拒まれた要求まで数えると、送り続ける利用者が窓から出られなくなる。
- 答え（推奨を仮置き）: 推奨どおり。
- 根拠: 非機能要件「負荷保護」は、上限の値と時間窓を決めているが、何を一回と数えるかは書いていない。推奨を仮置きした。採らなかった案は、成功した操作だけを数える案である。

### Q5 現在のフォロー関係と合わなくなった反映の要求を、どう終わらせるか

- 問い: 古い更新として反映を拒んだ要求（フォローの後にフォロー解除が確定してから届いた、フォローの反映の要求など）は、成功として記録するか、未完了のまま残すか。
- 推奨: キャッシュを変えずに成功として記録し、以後は回収しない。
- 理由: フォローのコマンドデータモデルは、要求、回収、成功の三つの表だけを持ち、諦めた事実の表を置いていない。未完了のまま残すと、同じ要求をいつまでも回収し直し、30分を超えた時点で構造化 Error ログの対象になってしまう。本当の遅延と、反映が不要になった要求を見分けられなくなる。
- 答え（推奨を仮置き）: 推奨どおり。
- 根拠: 要件にも設計資料にも、この終わらせ方は無い。推奨を仮置きした。採らなかった案は、未完了のまま残す案と、「反映が不要になった」という事実の表を新しく置く案である。
