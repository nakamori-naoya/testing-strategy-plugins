# フォローする・フォローを外すの境界シナリオ

この資料は、X クローンのバックエンドを Go で実装する3〜6人のチームのためのものです。フォローする（`FollowUser`）、フォローを外す（`UnfollowUser`）の二つの公開 API と、その変更が積む反映の要求（Outbox）について、どの具体例をどのレベルとサイズでテストにし、何を別のレベルへ重ねないかを決めるときに読みます。

結論は次のとおりです。公開 API のテストは、Medium で次のことだけを確かめます。誰の操作として扱うか、相手の利用者IDの変換、拒否理由ごとの外部表現の一例、応答が届かなかったときの再送と同時要求の負け側の表現、操作回数の上限、依存が止まったときの表現です。フォローできるかの条件の組み合わせは業務判断の Small に置きます。行の形と同時実行の保証は、永続化の Medium に置きます。反映の正しさは、反映の担い手をテストのプロセス内で呼ぶ Medium で確かめ、ホームタイムラインの読み取りで観測します。公開 API から Pub/Sub をまたいで届くかは、テスト戦略の E2E に任せます。

失敗の表現、要求の形、拒まれた要求の数え方は、公開 API の契約がまだ無いため仮説で置いています。この資料の状態は unresolved です。契約ができて「未決と仮説」の各項目が確定したら、期待結果の該当する行を直して ready にします。

## 前提: 定義もコードも無く、要件と設計資料だけから組んだ

対象リポジトリ `target-repo` の履歴は、commit 8a351c1「docs: 要件と設計資料」だけです。テスト戦略は同じ題名の commit を 858a38b と記録しています。この食い違いは確かめていません。リポジトリには、Go のコード、Protocol Buffers の定義、テストのどれもありません。そのため、どのリスクにも既存テストの証拠はありません。以下のシナリオは、すべて残余リスクを補うための目標です。どれも実装も実行もしていません。

この資料が扱う境界は三つです。

- `FollowUser`: 認証済みの利用者が、相手の利用者ID（`followee_user_id`）を渡してフォローする。名前は、フォローの業務知識「ユビキタス言語」のコマンドの英名に従う。
- `UnfollowUser`: 同じく、相手の利用者IDを渡してフォローを外す。
- フォロー変更の反映の要求: 上の二つが成功すると、同じトランザクションで `follow_change_reflection_requested_events` に一行が積まれる。反映の担い手はそれを要求IDで回収し、ホームタイムラインへ反映して、成功を積む。調停処理は、止まった要求を拾い直す（フォローのコマンドデータモデル、非機能要件「整合性と鮮度」）。

ポストの配信、キャッシュ全体の作り直し、利用者一覧とタイムラインの読み取りの境界は扱いません。ただし、フォローの状態と反映の結果を外から観測するために、利用者一覧（`FindUsersToFollow`）とホームタイムラインの読み取り（`ReadHomeTimeline`）を、プロセス内のハンドラーとして呼びます。

## 共通の事前状態と、値の決め方

どのシナリオも、localhost の PostgreSQL と Redis（レート制限用とタイムラインキャッシュ用の2用途）を実物で使います。差し替えるのは、Clerk、時計、ポストIDの採番の三つだけです（テスト戦略「差し替えるのは…」）。時計は、特に書かない限り 2026-10-01T10:00:00Z に固定します。

利用者IDは UUID で、資料では U-nnnn と略します。U-nnnn は `00000000-0000-7000-8000-00000000nnnn` を指します（例: U-0001 は `00000000-0000-7000-8000-000000000001`）。ポストIDは P-nnnn と略し、採番の差し替えで `00000000-0000-7000-9000-00000000nnnn` を渡します。番号が大きいほど新しい順の先に並びます。

| 利用者 | 状態 | Clerk ユーザーID（JWT の `sub`） |
|---|---|---|
| U-0001 | 登録済み。特に書かない限り、誰もフォローしていない | `user_test_0001` |
| U-0002 | 登録済み | `user_test_0002` |
| U-0003 | 登録済み | `user_test_0003` |
| U-9999 | 登録されていない | なし |
| （未登録の利用希望者） | Google で本人確認済みだが、どの利用者にもひも付いていない | `user_test_4004` |

JWT は、テスト用に生成した鍵（`kid: test-key-1`）で署名します。発行者は `https://clerk.x-clone.test`、authorized party は `http://localhost:3000` とします。有効な JWT の `exp` は 2026-10-01T10:01:00Z です。発行者と authorized party の値はテスト用に仮に置いたもので、Clerk の実際の値ではありません。

5,000人のフォローや1万人のフォロワーのような事前状態は、API を呼んで作りません。操作回数の上限に当たるからです。コマンドデータモデルの行の形どおりに、テストの準備で直接積みます。「フォロー中か」を観測するときは、利用者一覧で本人から見た区別を読みます。ただし利用者一覧の件数と続きの読み方が決まっていないため、利用者が50人を超える場面では、`follows` の現在状態を読んで確かめます。

## フォローする（FollowUser）

### FU-01 有効な相手の利用者IDでフォローすると、成功が返り、本人から見てフォロー中になる

wire の文字列が内部の利用者IDへ正しく変わり、成功が成功として返ることを、代表の一例で確かめます。フォローできる条件の組み合わせ（4,999人目、外した相手の再フォローなど）は、業務判断の Small に置き、ここでは繰り返しません。

```text
事前状態: U-0001 は誰もフォローしていない。U-0001 の有効な JWT がある
入力:     followee_user_id = "00000000-0000-7000-8000-000000000002"（U-0002）
行為:     U-0001 の JWT で FollowUser を呼ぶ
観測:     status OK が返る
          U-0001 の利用者一覧で、U-0001 は本人、U-0002 はフォロー中、U-0003 はフォローしていない
```

反映の要求が一件積まれたかは、ここでは見ません。FR-01 で確かめます。

### FU-02 利用者IDとして読めない入力は、業務の判断に入る前に引数の誤りとして拒む

外した条件は「相手の利用者IDが UUID として読める」ことです。proto3 では、欄を送らないことと空文字を送ることが区別できないので、空文字を一つの区分にしました。UUID として読めない文字列は、長さや文字の種類が違っても同じ結果になるので、一つの区分にまとめます。

| 区分 | 具体値 | 返る結果 | 状態 |
|---|---|---|---|
| 成立する値（対照） | `00000000-0000-7000-8000-000000000002` | OK | U-0002 がフォロー中になる |
| 欄が無い | `""` | `INVALID_ARGUMENT` / `INVALID_USER_ID` | U-0001 のフォローは増えない |
| UUID として読めない | `"U-0002"` | `INVALID_ARGUMENT` / `INVALID_USER_ID` | U-0001 のフォローは増えない |

どちらの拒否も、公開インターフェースの入力の変換で起き、一次データを読みません。Clerk、時計、JWT は FU-01 と同じです。

### FU-03 業務の拒否理由は、理由ごとに一例ずつ外部表現を確かめる

フォローの業務知識には、フォローを拒む理由が五つあります。そのうち「他人として」は FU-04 で扱います。残りの四つについて、業務の判断の結果が、正しい status と理由の識別子へ変わるかを一例ずつ確かめます。どの行も、拒否の後に本人から見て相手がフォロー中になっていないことを観測します。何も行が増えないことの詳しい確認は、永続化の Medium（フォローのコマンドデータモデル BDD-002、BDD-005〜007）に置きます。

| 外した条件 | 事前状態 | 入力の相手 | 返る結果 | 対照 |
|---|---|---|---|---|
| 自分ではない | U-0001 は誰もフォローしていない | U-0001 | `INVALID_ARGUMENT` / `CANNOT_FOLLOW_SELF` | FU-01 |
| 登録済みの利用者である | 同上 | U-9999 | `NOT_FOUND` / `USER_NOT_FOUND` | FU-01 |
| まだフォロー中でない | U-0001 は U-0002 をフォロー中 | U-0002 | `ALREADY_EXISTS` / `ALREADY_FOLLOWING` | FU-01 |
| フォロー中が5,000人未満 | U-0001 は U-1001〜U-6000 の5,000人をフォロー中 | U-0002 | `FAILED_PRECONDITION` / `FOLLOW_LIMIT_REACHED` | 4,999人なら OK（Small） |

上限の行は、5,000件の `follows` を準備で直接積みます。U-0001 から U-0002 へのフォローが無いことは、`follows` の現在状態で確かめます。4,999人と5,000人の境目そのものは、業務判断の Small（フォローの業務知識 BDD-002、BDD-003）が主担当です。

### FU-04 誰の操作かは JWT の主体だけから決め、自己申告の利用者IDは効かない

テスト戦略は、認証と認可を業務 API ごとに一度ずつ確かめると決めています。この API では、次の四つの区分を確かめます。署名、発行者、authorized party の検証の組み合わせは、すべての業務 API に共通する認証の入口のシナリオに置き、ここでは繰り返しません。

| 区分 | 具体値 | 返る結果 | 状態 |
|---|---|---|---|
| JWT が無い | `authorization` metadata を送らない | `UNAUTHENTICATED` | 誰のフォローも増えない |
| 期限切れ | `exp` = 2026-10-01T09:59:59Z（時計は 10:00:00Z） | `UNAUTHENTICATED` | 誰のフォローも増えない |
| 認証済みだが未登録 | `sub` = `user_test_4004` の有効な JWT | `PERMISSION_DENIED` / `USER_NOT_REGISTERED` | 誰のフォローも増えない |
| 他人の利用者IDを名乗る | U-0003 の有効な JWT に `x-user-id: 00000000-0000-7000-8000-000000000001` を添え、相手は U-0002 | OK | U-0003 から U-0002 がフォロー中になる。U-0001 から U-0002 へのフォローは無いまま |

最後の行は、仮説 H3（要求に本人の欄を置かない）に依存します。本人の欄を置く案に決まれば、この行の期待結果は `PERMISSION_DENIED` に変わります。期限切れの対照は、FU-01 の有効な JWT（`exp` = 10:01:00Z）です。`exp` がちょうど現在時刻の場合は、まだ決まっていないので確かめません。

期限切れの行では、テストのプロセス内でログを捕まえて、次の二つも観測します。一つは、ログに JWT 検証失敗の理由分類（期限切れ）が構造化されて残ることです。もう一つは、ログと応答のどちらにも、JWT の文字列、Google アカウントID、メールアドレス、Clerk secret が含まれないことです（非機能要件「セキュリティ」「運用性と観測」）。

### FU-05 Clerk Backend API が止まっていても、登録済みの利用者はフォローできる

業務 API は、保存済みの Clerk ユーザーIDと利用者IDのひも付けだけで本人を決めます。Clerk Backend API を呼ぶのは初回登録のときだけです（非機能要件「信頼性」）。業務 API が Clerk Backend API に依存してしまう欠陥は、Clerk を差し替えた境界でしか再現できないので、ここに置きます。

```text
事前状態: Clerk Backend API の差し替えは、すべての要求に 503 を返す
          U-0001 は登録済みで、誰もフォローしていない
入力:     U-0001 の有効な JWT、followee_user_id = U-0002
行為:     FollowUser を呼ぶ
観測:     status OK が返り、U-0001 の利用者一覧で U-0002 がフォロー中になる
          Clerk Backend API の差し替えへの要求は0件である
```

この性質は、認証の入口が二つの API で共通なので、`UnfollowUser` では繰り返しません。

## フォローを外す（UnfollowUser）

### UF-01 フォロー中の相手を外すと、成功が返り、本人から見てフォローしていないになる

```text
事前状態: U-0001 は U-0002 と U-0003 をフォロー中
入力:     U-0001 の有効な JWT、followee_user_id = U-0002
行為:     UnfollowUser を呼ぶ
観測:     status OK が返る
          U-0001 の利用者一覧で、U-0002 はフォローしていない、U-0003 はフォロー中
```

### UF-02 外すフォローが無い相手は、どの理由でも「フォローしていない」で拒む

フォローの業務知識では、フォローを外すときの拒否理由は「フォローしていない相手」だけです（「他人として」は UF-03）。自分や未登録の相手を外そうとした場合を FollowUser と同じ検査で拒む実装は起こりやすいので、同じ結果になることを別の行で確かめます。どの行も、U-0001 の U-0003 へのフォローはフォロー中のまま変わりません。

| 区分 | 事前状態 | 入力の相手 | 返る結果 |
|---|---|---|---|
| 成立する値（対照） | U-0001 は U-0002 と U-0003 をフォロー中 | U-0002 | OK |
| UUID として読めない | U-0001 は U-0003 をフォロー中 | `"U-0002"` | `INVALID_ARGUMENT` / `INVALID_USER_ID` |
| 一度もフォローしていない | 同上 | U-0002 | `FAILED_PRECONDITION` / `NOT_FOLLOWING` |
| 自分 | 同上 | U-0001 | `FAILED_PRECONDITION` / `NOT_FOLLOWING` |
| 登録されていない | 同上 | U-9999 | `FAILED_PRECONDITION` / `NOT_FOLLOWING` |

外した後にもう一度外す場合（`follows` の行が `not_following` で残っている場合）も、外部表現は「一度もフォローしていない」と同じです。行が無いか `not_following` かの違いは、永続化の Medium（フォローのコマンドデータモデル BDD-007）で確かめます。自分と未登録の相手を `NOT_FOLLOWING` にすることは、仮説 H2 に依存します。

### UF-03 フォローを外すときも、誰の操作かは JWT の主体だけから決める

FU-04 と同じ四つの区分を、この API でも一度ずつ確かめます。JWT が無いとき、期限切れのとき、未登録の利用希望者のときは、FU-04 と同じ結果が返り、U-0001 から U-0002 へのフォローはフォロー中のまま変わりません。秘密を出さないことの観測は、FU-04 だけに置きます。

他人を名乗る行だけは、結果が FollowUser と違うので書いておきます。U-0001 は U-0002 をフォロー中で、U-0003 は U-0002 をフォローしていないとします。U-0003 の有効な JWT に `x-user-id: 00000000-0000-7000-8000-000000000001` を添え、相手を U-0002 として `UnfollowUser` を呼びます。要求は U-0003 の操作として扱われるので、`FAILED_PRECONDITION` / `NOT_FOLLOWING` が返ります。U-0001 から U-0002 へのフォローはフォロー中のまま変わりません。この行も仮説 H3 に依存します。

## 二つの API に共通すること

### CM-01 一次データへ届かなければ成功を返さず、タイムライン用 Redis が止まっていても成功する

API の成功は、一次データへ確定できたかだけで決まります（バックエンド要件「操作の成功境界」）。止める依存を一つずつ変えて、この線を確かめます。止め方は、その依存の接続先を、何も待ち受けていない localhost のポートに向けることです。

| 止めた依存 | 呼ぶ API と事前状態 | 返る結果 | 依存を戻した後の状態 |
|---|---|---|---|
| 一次データ（書き込みの接続先） | FollowUser、U-0001 は誰もフォローしていない | `UNAVAILABLE` / `PRIMARY_DATA_UNAVAILABLE` | U-0002 はフォローしていない |
| 一次データ（書き込みの接続先） | UnfollowUser、U-0001 は U-0002 をフォロー中 | `UNAVAILABLE` / `PRIMARY_DATA_UNAVAILABLE` | U-0002 はフォロー中 |
| タイムライン用 Redis | FollowUser、同上 | OK | U-0002 はフォロー中 |
| タイムライン用 Redis | UnfollowUser、同上 | OK | U-0002 はフォローしていない |

タイムライン用 Redis の行は、API がキャッシュへ書き込まないことを外から確かめるためのものです。とくに、フォロー解除のときに、同期でキャッシュから相手のポストを消したくなる実装を捕まえます。

### SQ-01 応答が届かずに同じ要求を再送すると、二回目は拒まれ、事実は一つだけ残る

冪等キーは無いので、再送は二回目の独立した要求として判断されます（前提の節）。応答が届かなかったことは、一回目の応答を捨てることで作ります。一回の呼び出しでは差が出ず、状態によって結果が変わるので、操作の列にしました。

| 境界 | 一回目 | 二回目（同じ入力、10:00:05Z） | 事実の数 |
|---|---|---|---|
| FollowUser | 相手 U-0002 で OK（応答を捨てる） | `ALREADY_EXISTS` / `ALREADY_FOLLOWING` | U-0001 から U-0002 の「フォローした」は1件、反映の要求は1件 |
| UnfollowUser | U-0002 のフォロー中から OK（応答を捨てる） | `FAILED_PRECONDITION` / `NOT_FOLLOWING` | 「フォローを外した」は1件、反映の要求は1件 |

この列で事実の数まで観測するのは、再送を成功として扱ったつもりで事実を二重に積む欠陥が、この境界で最も起こりやすいからです。呼び出し側が二回目の拒否を「すでに成功していた」と読むかは、フロントエンドの判断で、ここでは決めません。

### SQ-02 同時の要求で負けた側も、順に送ったときと同じ理由で拒む

同時の要求で先に記録された一つだけが成立することは、永続化の Medium が、実行順を固定して確かめます（フォローのコマンドデータモデル BDD-005〜007）。この境界に残すのは、負けた側の外部表現です。一意制約違反や直列化の失敗が、そのまま `INTERNAL`、`UNKNOWN`、`ABORTED` として外へ漏れる欠陥は、境界を通さないと見えません。二つの要求は、バリアで両方が判断を終えた後に記録へ進むよう、順序を固定します。

| 場面 | 二つの要求 | 勝った側 | 負けた側 |
|---|---|---|---|
| 同じ相手を二回 | U-0001 が U-0002 を FollowUser ×2 | OK | `ALREADY_EXISTS` / `ALREADY_FOLLOWING` |
| 4,999人から二人 | U-0001（U-1001〜U-5999 をフォロー中）が U-7001 と U-7002 を FollowUser | OK | `FAILED_PRECONDITION` / `FOLLOW_LIMIT_REACHED` |
| 同じフォローを二回外す | U-0001 が U-0002 を UnfollowUser ×2 | OK | `FAILED_PRECONDITION` / `NOT_FOLLOWING` |

どの場面でも、負けた側に `INTERNAL`、`UNKNOWN`、`ABORTED` が返らないことを観測します。

## 操作回数の上限

上限は、フォローとフォロー解除の合計で20回/分と100回/日です（非機能要件「負荷保護」）。時間窓を固定の区切りで数えるか、滑る窓で数えるかは決まっていません。そこで、どちらの数え方でも同じ結果になるように時刻を選びました。時計は差し替えで進め、固定の時間を待ちません。

### RL-01 分の窓では、二つの操作を合わせて21回目を拒み、ほかの利用者の操作は止めない

```text
事前状態: U-0001 は誰もフォローしていない。U-1001〜U-1011 は登録済み
行為:     時計 10:00:00.000Z のまま、U-0001 が U-1001〜U-1010 を FollowUser（10回）、
          続けて U-1001〜U-1010 を UnfollowUser（10回）
          時計を 10:00:59.999Z に進め、U-0001 が U-1011 を FollowUser（21回目）
          同じ時刻に U-0003 が U-1011 を FollowUser
          時計を 10:01:00.001Z に進め、U-0001 が U-1011 を FollowUser
観測:     20回はすべて OK
          21回目は RESOURCE_EXHAUSTED / RATE_LIMITED で、U-0001 から U-1011 はフォローしていないまま
          同じ時刻の U-0003 の FollowUser は OK
          10:01:00.001Z の U-0001 の FollowUser は OK
```

20回をすべて同じ時刻に置いたので、固定の区切りでも滑る窓でも、10:01:00.001Z には窓が空きます。

### RL-02 日の窓では、分の窓に余裕があっても101回目を拒む

```text
事前状態: U-0001 は誰もフォローしていない。U-1001 は登録済み
行為:     2026-10-01T10:00Z から 10:19Z まで、毎分の0秒から5回、U-0001 が U-1001 を
          FollowUser と UnfollowUser で交互に呼ぶ（計100回。最後の10:19Z の5回目は UnfollowUser）
          10:20:00Z に101回目として U-1001 を FollowUser
          2026-10-02T10:20:00.001Z に102回目として U-1001 を FollowUser
観測:     100回はすべて OK
          101回目は RESOURCE_EXHAUSTED / RATE_LIMITED で、U-1001 はフォローしていないまま
          102回目は OK
```

102回目の時刻では、暦日（UTC でも日本時間でも）の区切りも、24時間の滑る窓も過ぎています。日の区切り方は未決なので、どちらの数え方でも結果が変わらない時刻を選びました。

### RL-03 拒まれた要求も数え、上限で拒まれた要求は数えない（仮説 H4）

```text
行為:     時計 10:00:00.000Z のまま、U-0001 が自分を相手に FollowUser を10回（どれも CANNOT_FOLLOW_SELF）、
          U-1001〜U-1010 を FollowUser で10回（OK）
          U-1011 を FollowUser（21回目）を、10:00:30Z に3回
          時計を 10:01:00.001Z に進め、U-1011 を FollowUser
観測:     21回目の3回は、どれも RESOURCE_EXHAUSTED / RATE_LIMITED
          10:01:00.001Z の FollowUser は OK
```

最後の観測は、上限で拒まれた3回が次の窓へ持ち越されないことを見ています。H4 が「成功だけを数える」に変われば、10:00:30Z の時点で数えるのは成功した10回だけなので、21回目の3回のうち最初の一回は OK になり、U-1011 はフォロー中になります。

### RL-04 レート制限の判定が止まったら、フォローもフォロー解除も安全側へ拒む

```text
事前状態: レート制限用 Redis の接続先を、何も待ち受けていないポートに向ける
          U-0001 は U-0003 をフォロー中
行為:     U-0001 が U-0002 を FollowUser、U-0003 を UnfollowUser
観測:     どちらも UNAVAILABLE / RATE_LIMIT_UNAVAILABLE
          U-0002 はフォローしていない、U-0003 はフォロー中のまま
```

判定が止まっている間も閲覧はプロセス内の上限で続けますが、それはタイムラインの境界で確かめます。

## フォロー変更の反映の要求

この節のシナリオは、非同期処理と調停の Medium に置きます（FR-01 だけは永続化）。反映の担い手と調停処理はテストのプロセス内で呼び、Pub/Sub の再配送は待ちません。担い手が受け取るのは要求ID（`request_id`）です。反映の結果は、ホームタイムラインの読み取りで観測し、キャッシュのキーの構造には触れません。ホームタイムラインキャッシュとフォロー関係の版の設計資料がまだ無いためです（テスト戦略の仮説 H6）。

### FR-01 反映の要求は、フォローの事実と同じ変更で確定し、確定できなければどちらも残らない

```text
事前状態: U-0001 は誰もフォローしていない
行為 1:   FollowUser（U-0002）を呼ぶ
観測 1:   OK。follow_base_events に followed が1件、それを source_event_id に持つ要求が1件
行為 2:   テストの準備で、follow_change_reflection_requested_events への INSERT を拒む
          トリガーを PostgreSQL に置き、U-0001 が U-0003 を FollowUser
観測 2:   OK 以外が返る。U-0001 から U-0003 の follows の行も、followed の事実も無い
```

UnfollowUser でも、同じ二つの行為を行います。U-0002 のフォロー中から外し、行為 2 で失敗したら、U-0002 はフォロー中、版は1のままです。失敗を起こすのにトリガーを使うのは、実物の PostgreSQL のトランザクションで、片方だけが残らないことを確かめるためです。

### FR-02 キャッシュがあるフォロワーでは、フォローの反映の後、フォロー前のポストが新しい順に並ぶ

```text
事前状態: U-0001 のポストは P-0105、P-0110。ホームタイムラインキャッシュは {P-0110, P-0105}
          U-0002 のポストは P-0101、P-0103、P-0107（どれもフォロー前）
行為:     FollowUser（U-0002）で要求 R を積み、担い手 W-1 が R を処理する
観測:     R に成功が1件積まれる
          U-0001 の ReadHomeTimeline の先頭ページは P-0110、P-0107、P-0105、P-0103、P-0101 の順
```

### FR-03 解除の反映の後は、キャッシュの範囲にも一次データの範囲にも、外した相手のポストが出ない

キャッシュの500件の境目をまたいで、外した相手のポストが残らないことを確かめます。境目より古いページを一次データで補うときに、外した相手のポストを拾う欠陥は、この組み合わせでしか見えません。

```text
事前状態: U-0001 は U-0002 と U-0003 をフォロー中
          U-0002 のポストは P-0001〜P-0599 の奇数（300件）、U-0003 は P-0002〜P-0600 の偶数（300件）
          U-0001 のキャッシュは直近500件（P-0101〜P-0600）
行為:     UnfollowUser（U-0002）で要求 R を積み、W-1 が R を処理する
          その後、U-0002 が P-0601 をポストしたことにする（posts に直接積む）
          U-0001 が ReadHomeTimeline を先頭から、カーソルで続きが無くなるまで読む
観測:     R に成功が1件積まれる
          6ページ、各50件で、P-0600〜P-0502、…、P-0200〜P-0102、P-0100〜P-0002（偶数だけ）が重ならずに返る
          どのページにも U-0002 のポスト（奇数と P-0601）は無い
          P-0002 の続きは0件で、続きが無いと分かる
```

1〜5ページ目はキャッシュから、6ページ目は一次データから読まれる並びにしてあります。続きが無いことの表現（空のページか、続きのカーソルが無いことか）は、API の契約で決まります。

### FR-04 キャッシュが無いフォロワーへの反映は、完了として記録し、次の閲覧で正しく作り直す

キャッシュが無い利用者は次の閲覧で作り直すので、反映の対象になりません（非機能要件「整合性と鮮度」）。担い手がキャッシュの出現を待って要求を未完了のまま残す欠陥と、相手のポストだけで部分的なキャッシュを作る欠陥を、ここで捕まえます。

```text
事前状態: U-0001 にホームタイムラインキャッシュは無い。U-0001 のポストは P-0105
          U-0002 のポストは P-0101、P-0103
行為:     FollowUser（U-0002）で要求 R を積み、W-1 が R を処理する。続けて ReadHomeTimeline を読む
観測:     R に成功が1件積まれる
          先頭ページは P-0105、P-0103、P-0101 の順（自分のポストも欠けない）
```

### FR-05 同じ要求を何度処理しても、ホームタイムラインには一件ずつしか並ばない

同じメッセージが複数回届く前提です（バックエンド要件「ポストできる」、非機能要件「信頼性」）。事前状態は FR-02 と同じで、観測はどの行も「先頭ページに P-0107 が一件だけ、全体が P-0110、P-0107、P-0105、P-0103、P-0101 の順」です。

| 場面 | 行為 | 要求の記録 |
|---|---|---|
| 成功の後に再配送 | W-1 が R を処理して成功。同じ R を W-2 が受け取る | W-2 は回収しない。回収は1件、成功は1件 |
| 二つの担い手が同時に回収 | W-1 と W-2 が同じ R を版1で回収しようとする。W-1 の記録をバリアで先にする | W-2 の回収は積まれず、W-2 は反映しない |
| 反映の後、成功の記録前に止まる | 成功の INSERT を一回だけ拒むトリガーを置き、W-1 が処理する（キャッシュへの反映は済む）。時計を 5分1秒進め、W-2 が R を処理する | W-2 の版2の回収と、それを指す成功が1件 |

三行目は、Redis への反映の後で一次データへ完了を記録する順序（非機能要件「整合性と鮮度」）のために、同じ要求が二度反映される場面です。

### FR-06 順序が入れ替わって届いた要求は、現在のフォロー関係に合わなければ反映しない

古い更新は、現在のフォロー関係と一致しなければ拒みます（バックエンド要件「成立した事実の説明と回復」）。事前状態は、U-0001 のポストが P-0110 でキャッシュが {P-0110}、U-0002 のポストが P-0101、P-0107 です。

| 場面 | 確定した変更 | 処理した順 | 先頭ページ | 要求の記録 |
|---|---|---|---|---|
| 解除の後にフォローの反映が届く | フォロー（版1、R1）、解除（版2、R2） | R2 → R1 | P-0110 | R1、R2 ともに成功（H5） |
| 再フォローの後に解除の反映が届く | フォロー（版1、R1 は処理済み）、解除（版2、R2）、再フォロー（版3、R3） | R3 → R2 | P-0110、P-0107、P-0101 | R2、R3 ともに成功（H5） |
| 順どおり（対照） | フォロー（版1、R1）、解除（版2、R2） | R1 → R2 | P-0110 | R1、R2 ともに成功 |

古い要求を成功として記録することは、仮説 H5 に依存します。未完了のまま残す案に決まれば、この列は「未完了で、次の回収の候補に残る」に変わります。

### FR-07 リースが切れるまでは別の担い手に回収させず、切れた後は回収させる

```text
事前状態: 要求 R は 10:00:00Z に積まれ、W-1 が 10:01:00Z に版1で回収したまま止まった
行為:     時計 10:05:59Z に W-2 が R を回収しようとする
          時計 10:06:01Z に W-2 が R を回収して処理する
観測:     10:05:59Z には回収は積まれない
          10:06:01Z には版2の回収が積まれ、成功はその回収を指す。先頭ページに相手のポストが並ぶ
```

ちょうど5分の扱いは決まっていないので、境目の1秒前と1秒後で確かめます。三度目以降の回収（フォローのコマンドデータモデル BDD-010）は、回収の版の規則なので、永続化の側で確かめます。

### FR-08 5分進捗の無い要求を調停が拾い直し、30分を超えたら Error ログに出す

要求は積まれたのに、配信のメッセージが一度も届かない場面です。メッセージを発行しないことで作ります。

```text
事前状態: 要求 R は 2026-10-01T10:00:00Z に積まれ、回収も成功も無い
行為 1:   時計 10:04:59Z に調停を一回実行する
観測 1:   R は対象にならない
行為 2:   時計 10:05:01Z に調停を一回実行し、渡された R を担い手が処理する
観測 2:   R に成功が1件積まれ、先頭ページに相手のポストが並ぶ
行為 3:   別の要求 R' を 10:00:00Z に積み、担い手を動かさないまま、
          時計 10:29:59Z と 10:30:01Z に調停を実行する
観測 3:   10:29:59Z には R' の Error ログは出ない
          10:30:01Z には構造化 Error ログが1件出る。要求種別（フォロー変更の反映）、要求ID R'、
          成立日時 2026-10-01T10:00:00Z を持ち、JWT、Google アカウントID、メールアドレスを含まない
          R' は破棄されず、次の調停の対象に残る
```

### FR-09 高ファンアウト投稿者をフォローまたは解除すると、反映後の読み取りに従う

高ファンアウト投稿者のポストはフォロワーのキャッシュへ配らず、閲覧時に合成します（非機能要件「負荷保護」）。そのため、フォローの反映が何を変えるかは、通常の投稿者とは違います。内部の表現は決まっていないので、読み取りの結果だけを観測します。

```text
事前状態: U-0500 はフォロワー1万人（U-10001〜U-20000）を持ち、これまでの配信の要求の経路は high_fanout
          U-0500 のポストは P-0102、P-0108。U-0001 のポストは P-0105、P-0110、キャッシュは {P-0110, P-0105}
行為 1:   FollowUser（U-0500）で要求を積み、担い手が処理する
観測 1:   先頭ページは P-0110、P-0108、P-0105、P-0102 の順
行為 2:   UnfollowUser（U-0500）で要求を積み、担い手が処理する
観測 2:   先頭ページは P-0110、P-0105 の順
```

## 重ねないこと

次の項目は、この資料の境界シナリオには入れず、別のレベルで確かめます。同じ例を二つのレベルに置くのは、下位のレベルが意味を、上位のレベルが接続や表現を確かめると説明できるときだけです。

フォローできる条件の組み合わせ（フォローの業務知識 BDD-001〜013。4,999人と5,000人の境目、外した相手の再フォロー、上限に達した後に一人外して別の相手をフォローするなど）は、業務判断の Small に置きます。この資料では、拒否理由ごとの表現を一例ずつ確かめるだけです。

行の形と同時実行の保証（フォローのコマンドデータモデル BDD-001〜011）は、永続化と非同期処理の Medium に置きます。SQ-02 は負けた側の表現だけを見て、行の不変条件は繰り返しません。

JWT の署名、発行者、authorized party の検証の組み合わせは、すべての業務 API に共通する認証の入口で一度だけ確かめます。gRPC-Web の生成差分と、定義の互換性は、契約と静的検査に置きます。

ジャーニーの主経路は E2E の Large に置きます。「読みたい相手をフォローしてホームタイムラインで読む」の場面3→5→6と、「読まなくなった相手のポストをホームタイムラインから外す」の場面1→3です（テスト戦略「E2E に残すのは4本の接続だけ」）。この資料の Medium は Pub/Sub の到着を待たず、E2E も、この資料の拒否理由、上限、重複、順序を繰り返しません。

反映の前に「一時的に見えないこと」は、どのシナリオでも期待値にしません。要件は時間差を許しているだけで、見えないことを約束していないからです。

利用者一覧の件数と続きの読み方、キャッシュ全体の作り直し中にフォロー変更が成立したときのやり直し（非機能要件「負荷保護」）は、それぞれ利用者一覧の境界と、作り直しの境界で扱います。

## 定義との同期

公開 API の機械可読な定義（Protocol Buffers）は、まだリポジトリにありません。対応を記録するコード上の公開境界もありません。そのため、今は各シナリオの ID と、業務知識の英名（`FollowUser`、`UnfollowUser`）の対応だけを持ちます。定義を作る基盤は、この資料からは求めません。

定義ができたら、シナリオごとに次の三つを記録します。参照した `.proto` ファイルのパス、項目の識別子（サービスとメソッドの完全名、`followee_user_id` の field 番号、`ErrorInfo.reason` の列挙値）、確認したときの定義の digest（`buf build` の image の SHA-256 など）です。digest が変わったら、操作、field、型、必須性、列挙値の差分は機械で見つけられます。ただし、構造の差分を直しただけでは、シナリオを更新したことにはなりません。成立条件、状態の変化、再送と冪等性、失敗の表現、担当のレベルは、差分を読んで判断し直します。とくに `reason` の列挙値が変わったら、FU-03、UF-02、SQ-01、SQ-02、RL-01〜RL-04 の期待結果を読み直します。

反映のメッセージの形も、定義ができたら同じように記録します。今は、担い手が要求IDを受け取ることだけを前提にしています。

## 未決と仮説

grill の問いに答える利用者がいなかったため、次の H1〜H5 は推奨を仮置きしたものです。どれも決定ではありません。

- H1 反映の要求の境界を、回収、反映、成功、重複、順序、リース、調停までとし、ポストの配信と作り直しを含めない。根拠は、R8 と R9 の失敗が要求を積んだ後にしか起きないことである（テスト戦略「境界シナリオは…」）。採らなかった案は、要求を積むところまでに限る案である。scope の持ち主が範囲を示せば確定する。狭まるなら、FR-02〜FR-09 は非同期処理の別の資料へ移す。
- H2 失敗の表現を、gRPC の status と `ErrorInfo.reason` の組にする。組は FU-02〜FU-04、UF-02、CM-01、RL-01〜RL-04 の表のとおりである。根拠は、ジャーニーが利用者に上限と操作回数を見分けて知らせることを求めていることである。採らなかった案は、フォロー上限を `RESOURCE_EXHAUSTED` にする案と、未登録の相手の解除を `NOT_FOUND` にする案である。公開 API の契約が決まれば確定する。
- H3 要求に本人の欄を置かず、metadata などで自己申告された利用者IDは無視する。根拠は、要件が自己申告の利用者IDを根拠にしないと決めていることである。採らなかった案は、本人の欄を置いて、食い違えば `PERMISSION_DENIED` にする案である。契約が決まれば確定し、FU-04 と UF-03 の該当行を直す。
- H4 認証済みで登録済みの利用者の呼び出しは、拒まれても数え、上限で拒まれた呼び出しは数えない。根拠は、上限の目的が一人の集中からほかの利用者を守ることである。採らなかった案は、成功だけを数える案である。非機能要件の持ち主が数え方を決めれば確定し、RL-03 を直す。
- H5 古い更新として拒んだ反映の要求は、キャッシュを変えずに成功として記録する。根拠は、コマンドデータモデルに諦めた事実の表が無く、未完了のまま残すと30分の Error ログが本当の遅延と区別できなくなることである。採らなかった案は、未完了のまま残す案と、新しい事実の表を置く案である。フォローのコマンドデータモデルの持ち主が決めれば確定し、FR-06 を直す。

次の項目は、推奨を置かずに未決のまま残します。

- 日の時間窓の区切り方（暦日か24時間か、暦日ならどのタイムゾーンか）。RL-02 は、どちらでも結果が変わらない時刻で組んだ。値が決まったら、区切りの直前と直後の例を足す。
- 境目ちょうどの扱い（JWT の `exp` と現在時刻が等しいとき、回収からちょうど5分、成立からちょうど30分）。FU-04、FR-07、FR-08 は1秒前と1秒後で組んだ。
- 公開 API の契約が無い。「定義との同期」の記録は、定義ができるまで埋められない。この資料を unresolved にしている主な理由である。
- ホームタイムラインキャッシュ、高ファンアウト投稿者の合成、フォロー関係の版の設計資料が無い（テスト戦略の仮説 H6）。FR-02〜FR-09 は読み取りだけで観測するので、主担当は変わらないと見込む。資料ができたら、FR-06 と FR-09 の事前状態の作り方を見直す。
