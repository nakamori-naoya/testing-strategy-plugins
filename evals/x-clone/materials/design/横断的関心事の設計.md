# 横断的関心事の設計

どの業務の公開の操作にも共通する、呼び手の識別、権限、失敗の分類と、それぞれを呼び手へ返す Code を決める。業務ごとの公開契約は、ここを指し、要求の項目で呼び手を名乗らせない。根拠は、要件の「利用者と権限の範囲」（バックエンド要件）と「セキュリティ」（非機能要件）である。

## 呼び手の識別

呼び手は、要求の `Authorization: Bearer <セッションのトークン>` で識別する。トークンは Clerk が発行するセッション JWT で、署名、発行者、authorized party、有効期限を確かめ、主体として Clerk のユーザーID（例: `user_2abcDEF123`）を得る。トークンが無いか確かめられないときは「認証されていない」で拒み、理由は応答で区別しない。

## 利用者への解決と権限

確かめた主体を、アカウントの業務が持つひも付けから、このサービスの利用者ID へ一度だけ解決する。解決できない（ログインはできたが利用者として登録されていない）ときは「許可されていない」で拒む。操作の主体は解決した利用者で、利用者が操作できるのは自分自身のポストとフォロー関係だけである。要求に含まれる利用者IDを主体として扱わないので、他人として操作する要求は公開の操作の上では組めない。

## 失敗の分類と Code

失敗は次のどれか一つの分類に入れ、分類から Code を決める。業務知識の拒む理由をどの分類に入れるかは、業務ごとの公開契約が決める。

| 分類 | Code |
|---|---|
| 入力が不正 | InvalidArgument |
| 認証されていない | Unauthenticated |
| 許可されていない | PermissionDenied |
| 存在しない | NotFound |
| すでに存在する | AlreadyExists |
| 業務ルールに反する | FailedPrecondition |
| 利用上限に達した | ResourceExhausted |
| 同時更新で競合した | Aborted |
| 時間切れ | DeadlineExceeded |
| 依存先が利用できない | Unavailable |
| 回復不能 | Internal |

回復不能の応答は固定の文言だけを返し、原因はログにだけ残す。JWT、Google アカウントID、メールアドレスは、どの分類の応答にも出さない。
