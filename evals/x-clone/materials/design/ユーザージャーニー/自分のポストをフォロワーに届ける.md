# 自分のポストをフォロワーに届けるユーザー目的達成BDD

利用者が、自分のポストをフォロワーに読んでもらうため、ポストしてからフォロワーのホームタイムラインに届くまでのJourneyである。投稿者は登録済みでログインしており、投稿者をフォローしている利用者が少なくとも一人いるところから始める。目的を達したと言えるのは、フォロワーが自分のホームタイムラインを読んだとき、投稿者のポストが本文を変えられずに一件だけ並んでいるのを確かめられたときである。

# Journey概要

投稿者は、伝えたいことをプレーンテキストの本文にしてポストする。ポストはその時点で成立し、投稿者は自分のユーザータイムラインを読めば、ポストが成立したことを確かめられる。フォロワーのホームタイムラインへの反映は、ポストの成立とは別に時間差をおいて進む。反映が済んだ後、フォロワーがホームタイムラインを先頭から読むと、投稿者のポストが並んでおり、そこで目的を達する。

投稿者自身が観測できるのは、自分のユーザータイムラインでポストが成立したことまでである。届いたことを観測できるのはフォロワーだけなので、最後の場面ではフォロワーが読む。

# 場面

この資料では、次の一件を最後まで追う。投稿者は利用者A、フォロワーは利用者Fで、FはAをフォローしている。Aがポストする本文は「今日の勉強会の資料を公開しました」の17文字である。

## 場面 1: 本文を書いてポストする

```gherkin
Given: 利用者Aが登録済みでログインしており、利用者FがAをフォローしている
  And: 利用者Aが、本文「今日の勉強会の資料を公開しました」（17文字）を用意している
When: 利用者Aがこの本文でポストする
Then: 利用者Aが、ポストが成功したことを知らされる
  And: 本文を変えずに、利用者Aのポストが一件成立している
```

**接続**: 成立したポストを、投稿者が自分で確かめる場面の前提として受け取る。

## 場面 2: 本文が決まりに合わないとポストできない

場面1と同じ前提から、本文が1文字以上280文字以下で空白だけではないという条件だけを外した失敗の場面である。

```gherkin
Given: 利用者Aが登録済みでログインしており、利用者FがAをフォローしている
  And: 利用者Aが、281文字の本文を用意している
When: 利用者Aがこの本文でポストする
Then: 利用者Aが、本文が280文字を超えているためポストできないことを知らされる
  And: 利用者Aのポストは一件も成立していない
  NOTE: Rule: ポストの本文は、Unicodeコードポイントで数えて1文字以上280文字以下で、空白だけの本文は受け付けない
    Source: [../../input/バックエンド要件.md](../../input/バックエンド要件.md)
    Reason: 決まりに合わない本文をポストとして成立させないため
```

**接続**: 最終地点へは届いていない。利用者Aが本文を280文字以下に直すと、場面1へ戻る。

## 場面 3: 自分のユーザータイムラインでポストを確かめる

```gherkin
Given: 利用者Aのポスト「今日の勉強会の資料を公開しました」が成立している
When: 利用者Aが自分のユーザータイムラインを先頭から読む
Then: 利用者Aが、そのポストを先頭に、本文を変えられずに一件だけ見られる
  And: 利用者Aが、ポストが成立しており、送り直す必要が無いと判断できる
```

**接続**: 成立したポストを、フォロワーが読む場面の前提として受け取る。投稿者自身のホームタイムラインへの反映にも時間差があり、その見え方は既知の分岐に書く。

## 場面 4: フォロワーがホームタイムラインでポストを読む

```gherkin
Given: 利用者Aのポスト「今日の勉強会の資料を公開しました」が成立している
  And: そのポストが、利用者Fのホームタイムラインへ反映されている
When: 利用者Fが自分のホームタイムラインを先頭から読む
Then: 利用者Fが、Aのポストを本文を変えられずに見られる
  And: 利用者Fが、同じポストが一件だけ並んでいることを確かめられる
```

反映の処理が同じポストについて何度繰り返されても、フォロワーのホームタイムラインに同じポストが二件以上並ぶことはない。

**接続**: 最終地点に着いた。フォロワーFがAのポストを自分のホームタイムラインで読めたので、完了条件を満たす。

# 既知の分岐

分岐は4つある。表の後に、分岐ごとの成り行きを書く。

| 分かれる場面 | きっかけ | 戻る先 |
|---|---|---|
| 場面 1 | 応答が返らない | 場面 3 |
| 場面 1 | 操作回数の上限 | 場面 1 |
| 場面 3 | 自分のホームタイムラインにまだ無い | 場面 3 |
| 場面 4 | 反映がまだ済んでいない | 場面 4 |

場面1で、ポストした後に応答が返らなかったときは、ポストが成立したかを利用者Aは知らされていない。利用者Aは場面3のとおり自分のユーザータイムラインを読み、ポストが並んでいれば送り直さない。並んでいなければ場面1へ戻って送り直す。確かめずに同じ本文を送り直すと、両方が成立したときに別のポストが二件並ぶ。同じ本文の再送を一件にまとめる仕組みは初期リリースに無いからである。この流れは、要件の「同じ本文を再び要求した場合も別のポストとして扱う」と「成功したポストは、投稿者本人が次にユーザータイムラインを閲覧したときに含める」から置いた仮説である。

場面1で、ポストの回数が1秒に5回、1時間に60回、1日に300回のいずれかに達しているときは、ポストは拒否され、利用者Aは操作回数の上限に達したことを知らされる。ポストは成立しない。時間をおいて場面1へ戻ればポストできる。この上限は[../../input/非機能要件.md](../../input/非機能要件.md)の負荷保護が定める暫定値である。

場面3の後に利用者Aが自分のホームタイムラインを読むと、ポストがまだ並んでいないことがある。投稿者本人のホームタイムラインへの反映も、ポストの成立とは別に時間差をおいて進むからである。自分のユーザータイムラインにはポストが並んでいるので、利用者Aは送り直さずに待てる。時間をおいて読み直すと、自分のホームタイムラインにも並ぶ。

場面4で、反映がまだ済んでいないときは、利用者Fがホームタイムラインを読んでもAのポストは並んでいない。反映は大半が5分以内に済む見込みだが、一件ごとの期限ではない。反映の処理が止まっても、成立したポストは取り消されず、止まった処理が再開した後に反映される。利用者Fが後で先頭から読み直すと、場面4へ戻って最終地点に着く。

# まだ決まっていないこと

投稿者が、自分のポストがフォロワーのホームタイムラインへ反映されたかを知る手段は、要件に書かれていない。利用者Aは、ポストが成立したことは自分のユーザータイムラインで確かめられるが、フォロワーに届いたかは確かめられない。届いたかを知りたいときに何を見ればよいかは、バックエンド要件の持ち主に確かめる。

場面1で応答が返らなかったときに、自分のユーザータイムラインで確かめてから送り直すという流れは、この資料が置いた仮説である。利用者へこの確かめ方を示すかどうかも、バックエンド要件の持ち主に確かめる。
