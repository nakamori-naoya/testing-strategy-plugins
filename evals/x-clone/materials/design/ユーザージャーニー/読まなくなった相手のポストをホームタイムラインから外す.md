# 読まなくなった相手のポストをホームタイムラインから外すユーザー目的達成BDD

利用者が、もう読まなくなった相手のフォローを外し、その相手のポストを自分のホームタイムラインに並ばないようにするまでのJourneyである。利用者は登録済みでログインしており、その相手をフォロー中で、ホームタイムラインに相手のポストが並んでいるところから始める。目的を達したと言えるのは、ホームタイムラインを読んだとき、外した相手のポストが、外す前のものも外した後のものも並ばず、自分とほかのフォロー中の相手のポストは残っているのを確かめられたときである。

# Journey概要

利用者は、読まなくなった相手のフォローを外す。外すことはその時点で成立し、利用者一覧ではその相手がフォローしていない相手として見える。ホームタイムラインへの反映には時間差があり、その間は相手のポストが残ることがある。反映が済んだ後にホームタイムラインを先頭から読むと、外した相手のポストは過去のものも新しいものも並ばず、そこで目的を達する。

# 場面

この資料では、次の一件を最後まで追う。主たるユーザーは利用者Aで、利用者Bと利用者Cをフォローしている。ホームタイムラインには、Aのポスト3件、Bのポスト20件、Cのポスト10件が並んでいる。AはBのポストを読まなくなったので、Bのフォローを外す。

## 場面 1: 読まなくなった相手のフォローを外す

```gherkin
Given: 利用者Aが登録済みでログインしており、BとCをフォローしている
  And: 利用者Aのホームタイムラインに、Aのポスト3件、Bのポスト20件、Cのポスト10件が並んでいる
When: 利用者AがBのフォローを外す
Then: 利用者Aが、Bのフォローを外せたことを知らされる
  And: 利用者Aが、一覧でBをフォローしていない相手、Cをフォロー中の相手として見分けられる
```

**接続**: フォローしていない相手になったBを、ホームタイムラインを読む場面の前提として受け取る。外せたことは、ホームタイムラインへの反映が済んだことを意味しない。反映を待つ間の見え方は、既知の分岐に書く。

## 場面 2: フォローしていない相手は外せない

場面1と同じ前提から、Bをフォロー中であるという条件だけを外した失敗の場面である。たとえば、ほかの端末ですでにBのフォローを外していたときに出会う。

```gherkin
Given: 利用者Aが登録済みでログインしており、Cだけをフォローしている
  And: Bはフォローしていない相手である
When: 利用者AがBのフォローを外す
Then: 利用者Aが、Bをフォローしていないため外せないことを知らされる
  And: 利用者Aが、一覧でBをフォローしていない相手、Cをフォロー中の相手として、外す前と同じ状態で見分けられる
  NOTE: Rule: 現在フォローしていない相手のフォローを外す要求は拒否し、状態を変えない
    Source: [../../input/バックエンド要件.md](../../input/バックエンド要件.md)
    Reason: フォローしていない相手には、外すべきフォローが無いため
```

**接続**: Bはすでにフォローしていない相手なので、利用者Aは場面3へ進んでホームタイムラインを確かめられる。

## 場面 3: ホームタイムラインに外した相手のポストが並ばない

```gherkin
Given: 利用者Aのフォロー中の相手がCだけで、Bのフォローを外したことがホームタイムラインへ反映されている
  And: Bが、フォローを外された後に新しいポストを1件している
When: 利用者Aが自分のホームタイムラインを先頭から読む
Then: 利用者Aが、Aのポスト3件とCのポスト10件の計13件を新しい順に読める
  And: 利用者Aが、外す前のBのポスト20件も、外した後のBの新しいポスト1件も並んでいないと確かめられる
```

**接続**: 最終地点に着いた。外した相手Bのポストが過去のものも新しいものも並ばず、自分とCのポストが残っていることを利用者Aが確かめたので、完了条件を満たす。

# 既知の分岐

分岐は3つある。表の後に、分岐ごとの成り行きを書く。

| 分かれる場面 | きっかけ | 戻る先 |
|---|---|---|
| 場面 1 | 操作回数の上限 | 場面 1 |
| 場面 3 | 反映がまだ済んでいない | 場面 3 |
| 場面 3 | もう一度フォローする | 別の終わり方 |

場面1で、フォローとフォローを外す操作が合わせて1分に20回、または1日に100回に達しているときは、外す操作は拒否され、利用者Aは操作回数の上限に達したことを知らされる。Bはフォロー中の相手のままである。時間をおいて場面1へ戻れば外せる。この上限は[../../input/非機能要件.md](../../input/非機能要件.md)の負荷保護が定める暫定値である。

場面3で、外したことの反映がまだ済んでいないときは、利用者Aがホームタイムラインを読んでも、Bのポストが残っていることがある。要件は、反映までの間に相手のポストが一時的に残ることを許容している。反映は大半が5分以内に済む見込みだが、一件ごとの期限ではない。利用者Aが時間をおいて先頭から読み直すと、場面3のとおりBのポストは並ばなくなる。

場面3の後で、利用者Aがもう一度Bのポストを読みたくなってBをフォローすると、それは新しいフォローとして扱われ、このJourneyとは別の終わり方になる。その流れは[読みたい相手をフォローしてホームタイムラインで読む.md](読みたい相手をフォローしてホームタイムラインで読む.md)の場面3から続き、反映が済むとBのポストは過去のものも含めて再び並ぶ。

# まだ決まっていないこと

フォローを外した直後にホームタイムラインへBのポストが残っているとき、利用者Aが「反映を待っている」のか「反映に失敗した」のかを見分けられるかは決まっていない。要件は反映の時間差を許容しているが、利用者へ反映の進み具合を示すかどうかを書いていない。見分けられないと、利用者Aは待つか外す操作をやり直すかを決められない。やり直すと場面2のとおり拒否される。確認先は、バックエンド要件の持ち主である。
