# 読みたい相手をフォローしてホームタイムラインで読むユーザー目的達成BDD

利用者が、読みたい相手を見つけてフォローし、その相手のポストを自分のホームタイムラインで読めるようになるまでのJourneyである。利用者はGoogleアカウントで登録を済ませてログインしており、まだ誰もフォローしていないところから始める。相手のポストが、フォローする前に作られたものも含めて、自分のホームタイムラインに新しい順に並び、最初のポストまで読み進められたら、目的を達したと言える。

# Journey概要

利用者は、ポストを読みたい相手を探すため、登録済み利用者の一覧を開く。一覧から候補を選び、その相手のユーザータイムラインでどんなポストをしているかを確かめてから、フォローする。フォローが成功しても、ホームタイムラインへの反映には時間差がある。反映が済んだ後にホームタイムラインを先頭から読むと、相手のポストが自分のポストと一緒に新しい順に並び、続きを読み進めると相手の最初のポストに届く。

相手を確かめてからフォローするという場面の並びは、要件が決めたものではなく、この資料が置いた仮説である。要件が定めているのは、ユーザータイムラインをフォロー関係にかかわらず読めることであり、読む順番ではない。

# 場面

この資料では、次の一件を最後まで追う。主たるユーザーは利用者A、読みたい相手は利用者Bである。登録済みの利用者はA、B、Cの3人で、Aはまだポストをしておらず、誰もフォローしていない。Bは、Aがフォローする前にポストを120件している。

## 場面 1: 利用者一覧で読みたい相手を見つける

```gherkin
Given: 利用者Aが登録済みでログインしており、フォロー中の相手が0人である
  And: 登録済みの利用者がA、B、Cの3人である
When: 利用者Aが登録済み利用者の一覧を開く
Then: 利用者Aが、A、B、Cの3人を利用者ID順に並んだ一覧として見られる
  And: 利用者Aが、一覧でAを本人、BとCをフォローしていない相手として見分けられる
  And: 利用者Aが、Bを読みたい相手の候補として選べる
```

**接続**: 利用者Aが、フォローしていない相手としてBを選び、Bのポストを確かめる場面の前提として受け取る。

## 場面 2: 相手のユーザータイムラインでポストを確かめる

この場面は、要件が順番を決めていない仮説の場面である。

```gherkin
Given: 利用者Aが、フォローしていない相手としてBを選んでいる
  And: 利用者Bのポストが120件ある
When: 利用者AがBのユーザータイムラインを先頭から読む
Then: 利用者Aが、Bの新しい方から50件のポストを新しい順に読める
  And: 利用者Aが、続きを読み進めて、残りの70件をBの最初のポストまで読める
  And: 利用者Aが、Bをフォローしていないままで、Bのポストを読みたいかを判断できる
```

**接続**: 利用者AがBのポストを読みたいと判断したことを、フォローする場面の前提として受け取る。

## 場面 3: 相手をフォローする

```gherkin
Given: 利用者Aが、Bのポストを読みたいと判断している
  And: 利用者Aのフォロー中の相手が0人で、Bはフォローしていない相手である
When: 利用者AがBをフォローする
Then: 利用者Aが、Bのフォローが成功したことを知らされる
  And: 利用者Aが、一覧でBをフォロー中の相手として見分けられる
  And: Bのポストを自分のホームタイムラインで読む前提として、Bがフォロー中の相手になっている
```

**接続**: フォロー中の相手になったBを、ホームタイムラインを読む場面の前提として受け取る。フォローの成功は、ホームタイムラインへの反映が済んだことを意味しない。反映を待つ間の見え方は、既知の分岐に書く。

## 場面 4: フォロー中の上限に達しているとフォローできない

場面3と同じ前提から、フォロー中の相手の数が上限より少ないという条件だけを外した失敗の場面である。

```gherkin
Given: 利用者Aが、Bのポストを読みたいと判断している
  And: 利用者Aのフォロー中の相手が5,000人で、Bはフォローしていない相手である
When: 利用者AがBをフォローする
Then: 利用者Aが、フォロー中の相手が上限の5,000人に達しているためフォローできないことを知らされる
  And: 利用者Aが、一覧でBをフォローしていない相手として見分けられる
  And: 利用者Aが、フォロー中の誰かのフォローを外せば、Bをフォローできるようになると判断できる
  NOTE: Rule: 一人が同時にフォローできる利用者は最大5,000人で、上限を超える要求は拒否する
    Source: [../../input/バックエンド要件.md](../../input/バックエンド要件.md)
    Reason: フォロー中の関係を5,000件以下に保つため
```

**接続**: Bはフォローしていない相手のままで、最終地点へは届いていない。利用者Aがフォロー中の誰かのフォローを外した後に、場面3へ戻る。

## 場面 5: ホームタイムラインで相手のポストを読む

```gherkin
Given: 利用者Aのフォロー中の相手がBの1人である
  And: Bのフォローがホームタイムラインへ反映されている
  And: 利用者Aのポストは0件で、Bのポストはフォローする前に作られた120件である
When: 利用者Aが自分のホームタイムラインを先頭から読む
Then: 利用者Aが、Bの新しい方から50件のポストを、新しい順に読める
  And: 利用者Aが、フォローする前に作られたBのポストも、ホームタイムラインに含まれていると確かめられる
  And: 利用者Aが、続きがあることを知り、読み進められる
```

「新しい順」は、このサービスではポストIDの大きい順を指す。ポストが作られた時刻の順とは一致しないことがある。

**接続**: 先頭の50件を読んだ位置を、続きを読み進める場面の前提として受け取る。

## 場面 6: 続きを読み進めて相手の最初のポストに届く

```gherkin
Given: 利用者Aが、ホームタイムラインの先頭の50件を読み終えている
  And: まだ読んでいないBのポストが70件ある
When: 利用者Aが、ホームタイムラインの続きを最後まで読み進める
Then: 利用者Aが、次の50件と、その次の20件を、前のページと重ならずに新しい順に読める
  And: 利用者Aが、Bの最初のポストまで読み終え、ホームタイムラインに続きが無いことを確かめられる
```

**接続**: 最終地点に着いた。Bのポストが、フォローする前のものも含めて利用者Aのホームタイムラインに新しい順に並び、最初のポストまで読めたので、完了条件を満たす。

# 既知の分岐

分岐は4つある。表では、分かれる場面ときっかけと戻る先だけを示し、その後の成り行きは表の後に分岐ごとに書く。

| 分かれる場面 | きっかけ | 戻る先 |
|---|---|---|
| 場面 3 | フォロー中の上限 | 場面 3（フォローを外した後） |
| 場面 3 | 操作回数の上限 | 場面 3 |
| 場面 5 | 反映がまだ済んでいない | 場面 5 |
| 場面 5・場面 6 | ホームタイムラインを読めない | 場面 5 |

場面3で、フォロー中の相手がすでに5,000人いるときは、場面4のとおりフォローできない。利用者Aがフォロー中の誰かのフォローを外すと、場面3へ戻ってBをフォローできる。フォローを外さないなら、このJourneyは最終地点へ届かずに終わる。

場面3で、フォローとフォローを外す操作が合わせて1分に20回、または1日に100回に達しているときは、フォローは拒否され、利用者Aは操作回数の上限に達したことを知らされる。Bはフォローしていない相手のままである。時間をおいて場面3へ戻れば、Bをフォローできる。この上限は[../../input/非機能要件.md](../../input/非機能要件.md)の負荷保護が定める暫定値であり、不正利用の認定ではない。

場面5で、フォローの反映がまだ済んでいないときは、利用者Aがホームタイムラインを先頭から読んでも、Bのポストが無いか、一部しか並ばないことがある。ポストが0件のホームタイムラインも正常な結果である。利用者Aが時間をおいて先頭から読み直すと、反映が済んだ後は場面5のとおりBのポストが並ぶ。反映は大半が5分以内に済む見込みだが、一件ごとの期限ではない。

場面5か場面6で、ホームタイムラインに表示すべきポストの全体をそろえられないときは、利用者Aは一部だけのホームタイムラインを見せられず、読めなかったことを知らされる。利用者Aが読み直すと、場面5へ戻る。また、場面6で読み進めている間にBが新しいポストをしても、すでに読んだページには加わらない。新しいポストを読むには、場面5のとおり先頭から読み直す。

# まだ決まっていないこと

フォローが成功した直後にホームタイムラインへBのポストが並ばないとき、利用者Aが「反映を待っている」のか「反映に失敗した」のかを見分けられるかは決まっていない。要件は反映の時間差を許容しているが、利用者へ反映の進み具合を示すかどうかを書いていない。見分けられないと、利用者Aは待つか操作をやり直すかを決められない。確認先は、バックエンド要件の持ち主である。

場面2で、フォローする前に相手のユーザータイムラインを確かめるという並びは、この資料が置いた仮説である。利用者一覧から直接フォローする流れを主な流れとするかは、同じくバックエンド要件の持ち主に確かめる。
