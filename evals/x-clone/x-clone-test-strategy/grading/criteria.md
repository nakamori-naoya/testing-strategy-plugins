# X のクローンのテスト戦略に固有の条件

X のクローンの要件は、ポストとフォローの変化をデータベースへ確定した時点で成功とし、ホームタイムラインへの反映を非同期に行う。要件には、実ストレージ、キャッシュ、メッセージングの製品と、ログインを担う外部の認証サービスが書かれている。フォロー上限や同じ相手の重複のように、同時の要求でも破れてはいけない決まりも混ざる。この条件は、その題材で戦略が外しやすい判断を型にしたものである。

### xs-internal-stores-real

重み: 3

PASS：要件に現れるデータベース、キャッシュ、メッセージングは、対象リポジトリが制御できる協働先として、ローカルや CI で用意する実物（エミュレーターを含む）で確かめる方針になっている。差し替えるのは外部の認証サービスのような制御できない境界だけで、その理由が書かれている。

FAIL：データベース、キャッシュ、メッセージングのどれかを、偽物やモックに差し替える方針にしている。

### xs-async-reflection

重み: 3

PASS：ポストやフォローの成功と、ホームタイムラインへの反映が別の時点になることを品質リスクとして扱い、反映の欠けや重複、止まった反映の再開を、どの最小の境界で確かめ、何を E2E に残すかを分けている。反映を待つ方法は、外から観測できる条件を期限付きで待つ形である。

FAIL：非同期の反映を品質リスクとして扱っていない、反映の業務上の正しさまで E2E に主担当として置いている、または固定の時間を待って確かめる方針にしている。

### xs-concurrent-rules

重み: 2

PASS：同時の要求でも破れてはいけない決まり（フォロー上限、同じ相手の重複、同じ外部アカウントからの二重登録のうち、設計資料にあるもの）を、実ストレージを使う永続化のレベルで、実行順に依らない形で確かめる方針にしている。

FAIL：これらの決まりに主担当が無い、業務判断のレベル（Small）だけで確かめられるとしている、または実行順任せの並行テストで確かめる方針にしている。

### xs-docs-no-code-yet

重み: 2

PASS：コードもテストもまだ無いことを現状として書いたうえで止まらずに戦略を作り、設計資料の BDD の例をどのレベルで確かめると価値が高いかを、資料の持ち主への提案として仕分けている。

FAIL：コードが無いことを理由に止まった、コードが無いことに触れていない、または設計資料の例の仕分けが無い。
