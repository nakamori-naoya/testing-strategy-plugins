# grill ログ: X クローン バックエンドのテスト戦略

この grill では、問いに答える利用者がいない。依頼の決まりに従い、呼び出し元（design-test-strategy を実行したエージェント）が利用者の代わりに答えた。答えが対象リポジトリの要件と設計資料で決まるものは、その事実で答えた。決まらないものは推奨を仮置きした。仮置きした答えは決定として扱わず、戦略資料の「未決と仮説」に書いた。

## 問う前に調べた事実

対象は `target-repo/`（commit 858a38b「docs: 要件と設計資料」）である。`docs/requirements/` に要件3本（バックエンド要件、非機能要件、利用規模と負荷モデル）、`docs/design/` にアカウント、ポスト、フォロー、ホームタイムライン、ユーザータイムラインの業務知識と、コマンドデータモデル3本、クエリデータモデル4本、ユーザージャーニー3本がある。Go のコード、Protocol Buffers の定義、テスト、Makefile などの完了判定の入口、CI 設定、docker compose の定義は無い。

## 問わずに前提にした論点

次の論点は資料で答えが決まるので、問いにせず前提として示した。誤りがあれば利用者が直せるように、根拠を添える。

- ホームタイムラインの表示対象と、成立した変更の反映を失わないことを最重要の失敗にする。根拠は、ホームタイムラインの業務知識「概要」（コアで、閲覧はポストの約100倍）、バックエンド要件「初期完了の判断」の「失敗と回復」、非機能要件「整合性と鮮度」「信頼性」である。
- PostgreSQL、2用途の Redis、Pub/Sub エミュレーター、API と非同期処理は実物をローカルで使う。根拠は、非機能要件「移植性と開発環境」の「ローカルではDocker ComposeでAPI、非同期処理、PostgreSQL、2用途のRedis、Pub/Subエミュレーターを本番と同じプロセス境界で起動できる」と、テスト戦略の判断基準の「差し替えてよいのは、制御できない外部の境界、時計、採番だけ」である。
- 本番の AlloyDB と Cloud Run の構成は、初期の戦略では確かめない。根拠は、バックエンド要件「初期リリースの対象範囲」が本番クラウド構築を初期完了に含めていないことである。
- 同時実行の保証（フォロー上限、重複フォロー、同時登録、回収の競合）は、実行順に依るテストにせず、制約違反と古い版を順に起こすテストで確かめる。根拠は、テスト戦略の判断基準「異常系を含め、実行順に依るテストを作らない」と、各コマンドデータモデルの「並行実行で必要な保証」が競合する行を明示していることである。

## 問いと答え（出た順）

### Q1 詳細化せずに切り離す品質領域

```text
❓ 詳細化しない品質領域: 性能（負荷試験）、セキュリティ診断、探索的テストを、この戦略では詳細化せず、観測点だけを残しますか
➡️ 推奨: はい。三つとも別に扱い、戦略には別に扱う理由、後続に要る入力、今の戦略が残す観測点だけを書く
   理由: 負荷試験はバックエンド要件で初期完了に含めないと決まっている。セキュリティ診断と探索は、目的・環境・合否が機能テストと違う。認証と認可の機能的な振る舞いは公開インターフェースのテストに残せる
```

- 答え: 性能は、事実で決まる。バックエンド要件「初期リリースの対象範囲」の「初期完了に含めないもの」に「日間利用者150万人を再現する負荷試験」があり、非機能要件「性能」も「応答時間の目標値と負荷試験は初期完了条件に含めない」と書いている。セキュリティ診断と探索的テストを切り離すことは、資料に書かれていないので推奨を仮置きした。
- 根拠: バックエンド要件「初期リリースの対象範囲」、非機能要件「性能」「まだ決まっていないこと」。セキュリティ診断と探索については推奨を仮置きした。
- 区分: 性能は決定（事実）、セキュリティ診断と探索は仮説。

### Q2 Clerk と Google の境界の扱い

```text
❓ Clerk と Google の境界: 通常の自動テストでは Clerk を差し替え、Clerk の開発用 instance への接続は別枠の契約テストにしますか
➡️ 推奨: Small と Medium では、ローカルで生成した鍵で署名した JWT と、Clerk Backend API の要求・応答の形の差し替えを使う。Clerk の開発用 instance に接続する契約テストを Large として別に持ち、秘密値が要るので既定の完了判定からは外し、Clerk の SDK か版を変える変更のときと定期に実行する
   理由: Clerk は制御できない外部の境界である。非機能要件は GoogleアカウントIDと検証済み状態の正確な項目を「公式仕様と契約テストで確定する」としており、自作の差し替えだけでは項目名の誤りと鍵の取得の配線が抜ける
```

- 答え: 契約テストで Clerk の項目を確定することは、事実で決まる（非機能要件「まだ決まっていないこと」）。差し替えてよい境界が Clerk であることも、判断基準と非機能要件「セキュリティ」から決まる。一方、契約テストを既定の完了判定から外すこと、実行の時点（SDK や版を変えるときと定期）、開発用 instance で Google の外部アカウントを持つ試験用の利用者を用意できるかは、資料に無いので推奨を仮置きした。
- 根拠: 非機能要件「セキュリティ」「まだ決まっていないこと」、判断基準「差し替えてよいのは…」。実行の枠と時点は推奨を仮置きした。
- 区分: 契約テストを置くことは決定（事実）、実行の枠と時点は仮説。

### Q3 ホームタイムラインの正しさを何と突き合わせるか

```text
❓ ホームタイムラインの判定基準: キャッシュと高ファンアウトの合成を通った結果を、クエリデータモデルが定める「posts と follows だけで決まる結果」と突き合わせて判定しますか
➡️ 推奨: はい。ホームタイムラインのクエリデータモデルの論理定義を判定基準にする。設計資料の例は固定の場面として使い、加えて、固定の種で生成したフォローとポストの状態で、キャッシュ経路の結果と論理定義の結果が一致するかを Medium で確かめる
   理由: 要件は、キャッシュ、高ファンアウトの閲覧時合成、キャッシュより古いページの一次データ読み取りという複数の経路を一つの並びに統合することを求めている。経路の組み合わせは例だけでは覆えない。クエリデータモデルはキャッシュに依らない表示対象を定めているので、判定基準として使える
```

- 答え: 推奨を仮置きした。クエリデータモデルが論理定義を持つことは事実（ホームタイムラインのクエリデータモデル冒頭と「ホームタイムラインを読む」）である。これをテストの判定基準にし、生成した状態で突き合わせるという方針は、資料に無い。
- 根拠: ホームタイムラインのクエリデータモデル、非機能要件「整合性と鮮度」（異なる経路を同じ順序で統合）、利用規模と負荷モデル「キャッシュ容量の暫定仮定」。方針は推奨を仮置きした。
- 区分: 仮説。

### Q4 E2E に残す経路

```text
❓ 残す E2E: Large の E2E を、三つのユーザージャーニーの主経路と、配信が止まった後の再開の、計4本に限りますか
➡️ 推奨: はい。「自分のポストをフォロワーに届ける」の場面1→4、「読みたい相手をフォローしてホームタイムラインで読む」の場面3→5→6、「読まなくなった相手のポストをホームタイムラインから外す」の場面1→3、配信の担い手を止めてポストし再開後に届くことの4本にする。拒否、上限、境界値、キャッシュの細部は下位へ置く
   理由: どれも API、Outbox、Pub/Sub、配信の担い手、Redis、読み取りのプロセスをまたぐ接続が欠けると再現しない。バックエンド要件「初期完了の判断」の「公開APIだけで…一連に実行できる」と「フォロワーへの反映が停止していても…復旧後に反映処理を再開できる」に対応する
```

- 答え: 推奨を仮置きした。要件は公開APIだけで一連に実行できることと停止後の再開を完了条件にしているが、どの経路を E2E に残すかは書いていない。
- 根拠: バックエンド要件「初期完了の判断」、3本のユーザージャーニー。本数と経路は推奨を仮置きした。
- 区分: 仮説。

### Q5 完了判定の入口と CI の段階

```text
❓ 完了判定の入口: ローカルの完了判定の入口を一つ作り、静的検査、Small、Medium、Large（Clerk の契約テストを除く）をこの順にすべて含め、CI はその入口をそのまま呼びますか
➡️ 推奨: はい。時間の上限は置かず、最初の実装で各段階の実行時間を計測してから見直す
   理由: 非機能要件は開発者のノートPCと Codespaces で本番と同じプロセス境界を起動できることを求めており、Large も秘密値なしでローカルに再現できる。手元と CI の検査の集合を一致させられる
```

- 答え: 推奨を仮置きした。要件はローカル起動を求めているが、完了判定の入口と CI の構成は書いておらず、実行時間の観測値も無い。
- 根拠: 非機能要件「移植性と開発環境」、バックエンド要件「技術と開発の制約」。入口と段階の構成は推奨を仮置きした。
- 区分: 仮説。

### Q6 足りない設計資料の扱い

```text
❓ 足りない設計資料: ホームタイムラインキャッシュと配信の設計資料と、API 契約（Protocol Buffers と失敗の表現）がまだ無いまま戦略を確定し、境界シナリオの設計の前にそれらの作成を資料の持ち主へ提案しますか
➡️ 推奨: はい。戦略は、要件が定める観測できる結果でリスクの主担当を決めて進める。キャッシュのキー、フォロー関係の版、作り直し中の保留、失敗の応答コードの具体は境界シナリオの設計で決めるので、その前に資料を用意するよう提案する
   理由: 主担当のレベルとサイズは観測できる結果で決まり、キーの構造には依らない。一方、境界シナリオは具体値を要するので、資料が無いと書けない
```

- 答え: 推奨を仮置きした。資料が無いことは事実（`docs/design/` にキャッシュと配信の物理設計、API 契約が無い）。資料が無いまま戦略を進めることと、提案の順序は資料に無い。
- 根拠: `docs/design/` の構成、ポストのコマンドデータモデル「テーブル定義」（範囲の区切り方は物理設計が決める）、フォローのクエリデータモデル「未決」（件数と続きの読み方は API の契約で決める）。方針は推奨を仮置きした。
- 区分: 仮説。

## 終わりの一覧

一覧は次のとおりである。取り下げた問いは無い。

決定（資料の事実で決まった）:

- D1: 性能（負荷試験と応答時間の目標）は、この戦略では詳細化しない（Q1）。
- D2: Clerk の GoogleアカウントIDと検証済み状態の項目は、Clerk に対する契約テストで確定する。通常の自動テストでは Clerk を差し替えてよい境界として扱う（Q2）。

仮説（推奨を仮置きし、戦略資料の未決に書く）:

- H1: セキュリティ診断と探索的テストも別に扱い、観測点だけを残す（Q1）。
- H2: Clerk の契約テストは Large として既定の完了判定から外し、SDK か版を変えるときと定期に実行する（Q2）。
- H3: ホームタイムラインの判定基準をクエリデータモデルの論理定義にし、固定の種で生成した状態でキャッシュ経路と突き合わせる（Q3）。
- H4: E2E は4本に限る（Q4）。
- H5: 完了判定の入口を一つにし、静的検査→Small→Medium→Large の順にすべて含め、CI はそれを呼ぶ。時間の上限は計測後に決める（Q5）。
- H6: キャッシュと配信の設計資料と API 契約が無いまま戦略を確定し、境界シナリオ設計の前に作成を提案する（Q6）。

未決（推奨も無いもの）: なし。
