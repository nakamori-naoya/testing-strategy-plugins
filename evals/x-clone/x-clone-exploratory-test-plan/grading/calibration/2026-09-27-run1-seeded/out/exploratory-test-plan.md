# ホームタイムラインへの反映の探索的テスト計画

この計画は、X クローンのバックエンドを実装するチームが、リリース前にホームタイムラインへの反映（ポストの配信、フォローとフォロー解除の反映、失った反映の回復）のどこへ探索の時間を使うかを決めるためのものです。例ごとの正しさは自動テストが受け持ちます。探索は、反映の途中で起きる出来事の順序と重なりに6本の charter で時間を配分します。例とは、フォローしている相手のポストが見える、同じメッセージの二度の処理で重ならない、といったことです。出来事とは、配信、フォロー変更、担い手の停止、キャッシュの欠損、読み進めを指します。自動テストは、実装者が思い付いた順序しか固定できないからです。

ただし、いまの対象リポジトリには要件と設計資料しかなく、コードも自動テストもありません。そのため、この計画の残余リスクは「テスト戦略が決めた主担当が、まだ実装も実行もされていない」という前提で配分しています。探索を始めるのは、反映の経路を受け持つ自動テストが緑になってからにします（仮説 H2）。そのとき証拠を対応付け直し、配分を見直します。この計画はまだ実行していません。発見はまだありません。

配分と置き場の規則は、確定済みのテスト戦略（`test-strategy/test-strategy.md`）に従います。この計画では作り直しません。

## 探索は、反映を受け持つ Medium と4本の E2E が緑になってから始める（仮説）

探索は、自動テストの代わりに回帰を保証するものではありません。テスト戦略は、反映の経路の失敗の主担当を次の二つに置いています。一つは Medium の「非同期処理と調停」と「読み取り」です（R8〜R12）。もう一つは Large の4本の E2E です（R16）。これらが無いまま探索を始めると、同じ例を手で確かめ直すことになり、未知へ使うはずの時間がなくなります。

そこで、探索を始める条件を次のように仮に置きます（仮説 H2）。R8〜R12 の Medium のテストと4本の E2E が実装され、完了判定の入口で緑になっていることです。始める前に、そのときあるテストを読み、次の節の表の「いまの証拠」の列を書き直します。テストがあるだけで実行結果を確かめられないものは「存在するが未実行」とし、証拠に数えません。

自動テストが足りないことは、探索では埋めません。条件がそろわないままリリースの日が来たら、足りない主担当を別に記録します。そのうえで、探索するのは、次の節の「探索に残す未知」の列だけにします。

## 例の網羅は自動テストが持ち、探索は出来事の順序の組み合わせを持つ

次の表は、scope に入る品質リスクごとに、テスト戦略が決めた主担当と、いまの証拠と、自動テストが緑になっても残る未知を並べたものです。表の読み方は、「探索に残す未知」の列が空でない行だけが探索の対象になる、というものです。

| リスク | 起こる失敗 | 主担当（戦略） | いまの証拠 | 探索に残す未知 |
|---|---|---|---|---|
| R7 | 配信経路を誤る | 業務判断 Small、永続化 Medium | なし（未実装） | 昇格の瞬間にほかの出来事が重なったとき |
| R8 | 要求を失う、二重に届ける、範囲を残して成功にする | 非同期処理と調停 Medium | なし（未実装） | リースが切れた後も元の担い手が動いている状態、停止の場所の違い |
| R9 | 同じポストが二件、古い更新が現在の関係と矛盾したまま入る | 非同期処理と調停 Medium | なし（未実装） | 配信、フォロー、フォロー解除の要求が処理される順序の置換 |
| R10 | 表示対象か並びを誤る | 読み取り Medium（固定の種で生成した状態） | なし（未実装） | 読み進める間に反映が進む時間の系列 |
| R11 | 一部だけを正常として返す | 読み取り Medium | なし（未実装） | キャッシュが途中で止まる、欠けるときの見え方 |
| R12 | 作り直しの結果が現在の関係と違う、同時に二つ進む | 非同期処理と調停 Medium | なし（未実装） | 作り直しと、進行中の配信と反映が重なるとき |
| R16 | プロセス間の接続が欠け、止まった後に再開しない | E2E Large（4本） | なし（未実装） | 停止する部品と場所の組み合わせ |

「いまの証拠」がすべて「なし」なのは、対象リポジトリの履歴が commit 8a351c1「docs: 要件と設計資料」の一つだけで、コード、テスト、CI の設定が無いためです。

未知が残る理由は、どの行も同じです。テスト戦略は、同時実行と非同期の失敗を「実行順を固定したテスト」で確かめると決めています（「同時実行の保証は、実行順を固定したテストで確かめる」）。これは再現性のために正しい決め方です。しかし、どの順序を固定するかは、テストを書く人が思い付いた範囲に限られます。反映の経路では、配信の要求、フォロー変更の反映の要求、担い手のリース、作り直しが、別々の担い手で別々の時間に進みます。そのため、順序の組み合わせを例として並べきれません。探索は、この組み合わせの中から、実装を見た人が危ないと感じた順序を試す役を持ちます。

## 設計資料から見つけた、探索の入口になる未知

charter を選ぶ根拠にした未知は、次の五つです。どれも設計資料に書かれているか、書かれていないことが確かめられたものです。どれも、まだ欠陥ではありません。

一つ目は、配信の範囲とフォロー変更の前後関係です。ポストのコマンドデータモデルは、フォロワーの範囲を要求ごとに一度だけ決めます。「範囲を決めた後にフォローした利用者は、決めた範囲のどこかに入るので、範囲の区切りで取りこぼしは起きない」と推定しています（「未決」）。しかし、その範囲がもう届け終えていた場合の成り行きは書かれていません。フォロー解除も同じです。範囲を読んだ後に解除が成立して反映されると、遅れて届く配信が、解除した相手のポストをキャッシュへ入れ直すかもしれません。要件は、古い更新が現在のフォロー関係と一致しなければ拒むと決めています（バックエンド要件「成立した事実の説明と回復」）。

二つ目は、リースが切れた後の元の担い手です。ポストのコマンドデータモデル BDD-011 では、担い手 W-1 が回収した要求を、W-2 が6分後に回収し直しています。W-1 が止まっておらず遅れていただけなら、W-1 と W-3 が同じ範囲へ同時に届けることがあります。範囲の完了の行は一意ですが、Redis への書き込みがどう重なるかはモデルの外にあります。

三つ目は、高ファンアウトの投稿者本人のホームタイムラインです。要件は、ホームタイムラインに自分のポストを表示すると決めています（バックエンド要件「ホームタイムラインを見られる」）。通常配信は投稿者本人へも届けます（ポストのコマンドデータモデル「`home_timeline_delivery_requested_events`」）。一方、`high_fanout` の要求は投稿者のユーザータイムラインへの反映だけで、閲覧時に合成するのはフォロー中の高ファンアウト投稿者です。投稿者本人の高ファンアウトのポストが本人のホームタイムラインへどう入るかは、どの資料にも書かれていません。

四つ目は、同じ投稿者の二件のポストが同時に昇格を選ぶ場面です。ポストのコマンドデータモデルの「未決」は、二件とも `high_fanout_promotion` を選びうるとし、二件目の経路を要件の回答責任者に確かめるとしています。

五つ目は、反映の遅れを診断できるかです。二つのジャーニーは、利用者が「反映を待っている」のか「反映に失敗した」のかを見分けられるかを未決にしています。運用者の側には、非機能要件「運用性と観測」が観測点を決めています。未発行と未処理の件数と最古の経過時間、5分を超えた遅延、30分を超えた要求の構造化 Error ログです。

## 探索しないこと

性能、負荷、セキュリティ、アクセシビリティは扱いません。scope に指定が無いためです。キャッシュ全体の欠損後に多数の利用者が同時に閲覧したときの処理量と同時実行数は、負荷試験で決める値なので扱いません（非機能要件「まだ決まっていないこと」）。探索では、作り直しの結果が正しいかだけを見ます（仮説 H1）。

既知の例は、自動テストが受け持つので探索では繰り返しません。本文の境界、フォローの拒否理由、5,000人の上限、レート制限、9,999人と1万人の経路の判定、500件の境界を一つずつ確かめること、E2E の4本の主経路がこれに当たります。これらは charter の途中で状態を用意する手段としては使いますが、観察の目的にはしません。

反映の途中で見える次の状態は、仕様どおりです。フォローの直後に相手のポストが無い、または一部しか並ばないこと。フォロー解除の直後に相手のポストが残ること。投稿者本人のホームタイムラインへの反映が遅れること。根拠は、バックエンド要件「フォローを外せる」「ポストできる」と、ジャーニーの既知の分岐です。反映の99%を5分以内とする運用 SLO も、探索の合否にしません。一件ごとの期限ではないからです（非機能要件「整合性と鮮度」）。

## 環境は E2E と同じ docker compose で、Outbox と Redis まで読む

探索は、Large の E2E と同じ構成を手元の docker compose で起動して行います。起動するのは、API、Outbox の発行、配信・反映の担い手、調停処理、PostgreSQL、2用途の Redis、Pub/Sub エミュレーターです。Clerk はテスト戦略どおり差し替えます。クラウドと外部のサービスへは接続しません。

操作は公開 API で行います。反映の途中の状態は公開 API からは見えません。そのため、観測には次のものを使ってよいことにします。PostgreSQL の Outbox の行（要求、回収、範囲、完了、成功）、Redis のキャッシュのキー、構造化ログ、担い手と発行と調停のプロセスの停止と再開です。ここまでは要件とテスト戦略で決まる事実です。

リースの5分と調停の5分は、設定で短くできることを前提にします（仮説 H3）。どちらもコマンドデータモデルが仮に置いた値で、実装がまだ無いため、設定で変えられるかは分かりません。変えられなければ、C4 と C5 の時間枠を延ばします。

## charter

charter は、対象、試す方向、観察する品質を一文で示します。操作の順は固定しません。「試す方向」は最初の足場の例で、実施者は観察した結果から次の一手を選びます。途中で重要な枝が出たら、その場で thread として短く追うか、振り返りで新しい charter に分けます。時間枠は一回90分です（仮説 H4）。

### C1 フォロー解除の後に届く古い配信が、解除した相手のポストを戻さないか

**charter**: 1. A が B をフォローする。2. B がポストする。3. 担い手を止める。4. A が B のフォローを外す。5. 担い手を再開する。6. A のホームタイムラインを読む。

最も重い失敗の一つは「外した相手を出す」ことです（テスト戦略の冒頭）。この charter を最初に行います。R9 の Medium は、配信とフォロー変更の要求の順序をいくつか固定して確かめます。しかし、要求は三つの経路で別々に届きます。配信の要求、フォロー変更の反映の要求、調停による拾い直しです。しかも Pub/Sub は届く順を保証しません。

試す方向は次のとおりです。相手 B のポストの配信が A の範囲を読んだ後で止まるよう、担い手を止めます。その間に A が B のフォローを外し、解除の反映だけを先に済ませます。そのあと配信を再開します。フォロー、解除、再フォローを短い間に行い、三つの反映の要求を逆の順や重複で処理させます。同じ配信のメッセージを、解除の反映の前後で二度処理させます。解除によってキャッシュの件数が減ったとき、古いポストで補充されないかも見ます。

異常を疑う根拠は三つです。一つ目は、すべての要求に成功の行が積まれた後に、ホームタイムラインの表示対象がクエリデータモデルの論理定義と食い違うことです。二つ目は、同じ操作を別の順序で行ったときに、収束した結果が違うことです。三つ目は、件数不足を補充したことです。補充はバックエンド要件「成立した事実の説明と回復」で禁止されています。反映の途中で B のポストが残ることは、仕様どおりです。

### C4 担い手が止まる場所を変えても、反映を失わず、止まった要求を特定できるか

**charter**: 配信・反映の担い手、Outbox の発行、調停処理を、処理の途中の異なる位置で止めて再開し、反映が一件も失われず二重にもならないか、止まっている要求を運用者が観測点から特定できるかを観察する。

「反映を失うこと」は、もう一つの最も重い失敗です。E2E の4本目は、担い手を止めたままポストし、再開すると届く、という一つの経路だけを確かめます。止まる位置と止まり方の組み合わせは残ります。止まる位置は、回収の直後、範囲を決めた直後、範囲の途中、成功を積む直前です。止まり方は、プロセスの停止と、遅れて動き続けることです。

試す方向は次のとおりです。担い手を範囲の途中で強制終了し、別の担い手に回収させます。担い手を止めずに遅らせ、リースが切れて別の担い手が回収した後に、元の担い手を進めます（前の節の二つ目の未知）。発行だけを止める場合と、担い手だけを止める場合を比べます。非機能要件「信頼性」は、この二つを別の障害として扱っています。止めている間にポストの受け付けが続くかも見ます。

観察する品質は二つあります。一つは、再開した後に、すべての要求に成功が積まれ、ホームタイムラインに同じポストが一件だけ並ぶことです。もう一つは、診断のしやすさです。止めている間に、未発行と未処理の件数と最古の経過時間から、止まった要求を特定できるかを見ます。回収した担い手の `worker_id` から、止まった担い手を特定できるかも見ます。30分を超えた要求の構造化 Error ログに、要求種別、要求ID、成立日時があり、JWT やメールアドレスなどの秘密情報が無いかも見ます。これらは非機能要件「運用性と観測」「セキュリティ」が期待の根拠です。

### C3 高ファンアウトの経路へ移る瞬間に、ほかの出来事が重なっても表示対象がそろうか

**charter**: 投稿者が初めて高ファンアウトの経路へ移る前後に、フォロー、フォロー解除、次のポスト、担い手の停止を重ねて試し、移る前の通常配信のポストと移った後に合成されるポストが、現在のフォロー関係に合う一つの並びにそろうかを観察する。

昇格は、テスト戦略が探索の配分先に名指しした瞬間です（「詳細化しない品質領域」）。経路の判定は Small で、1万人ちょうどでの判定は Medium で確かめられます。しかし、昇格の fanout は一度だけです。全フォロワーの合成対象へ投稿者を加え、範囲ごとに最大500人のバッチで進みます。その途中にほかの出来事が重なる場面は、自動テストに残りにくいです。

試す方向は次のとおりです。まず、フォロワー9,999人の投稿者に一人がフォローし、1万人ちょうどにしてからポストします。昇格の範囲の途中で、まだ届いていない範囲のフォロワーが投稿者をフォロー解除します。すでに届いた範囲に入る利用者IDで、新しくフォローします。昇格の前に通常配信されたポストと、昇格の後のポストが、読み手のホームタイムラインでポストIDの降順に一つの並びになるかを見ます。フォロワーが1万人を下回った後も経路が戻らないかも見ます。投稿者本人が自分のホームタイムラインを読み、昇格の後のポストが並ぶかも見ます（前の節の三つ目の未知）。

異常を疑う根拠は、反映が済んだ後の結果と論理定義の食い違いです。もう一つは、同じフォロワーがユーザータイムラインで見る投稿者のポストとの食い違いです。これは、同じ目的を持つ別の経路との比較です。ただし、同じ投稿者の二件のポストを同時に受け付けた場面は、期待の根拠がありません（未決 O1）。そこで観測した結果を記録し、欠陥とは決めずに要件の持ち主へ渡します。観測するのは、合成対象への追加が一件に収束するか、範囲が二重に作られるか、並びが変わるか、です。投稿者本人のホームタイムラインに昇格後の自分のポストが並ばない場合も、要件には反するので欠陥の候補です。ただし、設計資料に仕組みが無いので、まず設計の持ち主へ戻します。

1万人のフォロワーを用意する作業は、探索の時間枠の外で行います。一次データへ直接入れて用意するなら、フォロー変更の反映の要求と成功も整合する形で入れます。そうしないと、調停が用意の途中の要求を拾い、観察を乱します。

### C2 フォローの反映が、途中の配信や500件より古いポストと重なっても取りこぼさないか

**charter**: フォローの反映を、相手のポストの配信が進行中のときや、相手に500件を超える過去のポストがあるときに試し、フォロー前のポストも後のポストも、一件も欠けず重ならずに読み進められるかを観察する。

フォローしてすぐ読むという主経路は、E2E の2本目が120件で確かめます。この charter が見るのは、フォローの反映と相手のポストの配信が同じ時間帯に進む場面です。前の節の一つ目の未知が、フォローの側で起きる形です。

試す方向は次のとおりです。相手のポストの配信で A の入る範囲がもう届け終わった後に、A がフォローし、そのポストが A のホームタイムラインに届くかを見ます。配信とフォローの反映の両方から同じポストが届き、二件にならないかを見ます。相手が600件をポストしているとき、キャッシュの500件とその先の一次データの境目で、フォロー前のポストが途切れないかを見ます。フォロー中の高ファンアウト投稿者をフォローしたときと、フォロー解除したときに、合成対象が追いつくかも見ます。

異常を疑う根拠は、反映が済んだ後の表示対象と論理定義の食い違いです。もう一つは、同じポストが二件並ぶことです。これは、バックエンド要件「フォロワーへの反映」が禁止しています。

### C5 キャッシュ全体を失った後の作り直しが、進行中の反映と重なっても現在の関係に戻るか

**charter**: ホームタイムラインキャッシュと高ファンアウトのユーザータイムラインキャッシュを失わせた直後に、ポスト、フォロー変更、進行中の配信、同じ利用者の同時の閲覧を重ねて試し、作り直した結果が現在の一次データに合うか、不完全な結果を正常として返さないかを観察する。

この charter は、作り直しの正しさだけを扱います。処理量は扱いません（仮説 H1）。R12 の Medium は、作り直し中に新しいポストかフォロー変更が成立した場合のやり直しを、境界シナリオとして確かめます（テスト戦略「境界シナリオは…」）。残るのは、作り直しと、キューに溜まった配信と反映の要求が重なる場面です。

試す方向は次のとおりです。担い手を止めて要求を溜めた状態でキャッシュを消します。A が読んで作り直しが起きた後に担い手を再開し、作り直しより古い更新が入らないかを見ます。同じ利用者の二つの閲覧を同時に出し、作り直しが二つ進まないかを見ます。作り直しの途中で A がフォローを外します。高ファンアウト投稿者の一覧を持つキーも失わせ、合成対象が戻るかを見ます。キャッシュ用の Redis そのものを止め、閲覧が一次データから続くか、失敗するなら一部の結果ではなく失敗として返るかを見ます。

異常を疑う根拠は四つです。作り直した結果と論理定義の食い違い、作り直した後に届いた古い更新による食い違い、表示対象の一部だけを正常な応答として返すこと、正しい0件と障害を区別しないことです。最後の二つは、バックエンド要件「不完全な読み取り」が禁止しています。

### C6 反映が進む間に読み進めても、前のページのポストが続きに再び現れないか

**charter**: ホームタイムラインを先頭から読み進める途中で、フォロー、フォロー解除、ポストの反映を進めて試し、カーソルの排他的な境界と並びが保たれるかを観察する。

R10 の Medium は、固定の種で生成した状態でキャッシュの経路と論理定義を突き合わせます。ただし、反映を済ませた一つの状態で比べます。この charter は、読み進める間に状態が変わる時間の系列を見ます。

試す方向は次のとおりです。1ページ目をキャッシュから読んだ後に、フォロー解除の反映を済ませ、2ページ目以降を読みます。500件の境目を越えて一次データから読むページで、キャッシュのページと食い違いが出ないかを見ます。通常配信の投稿者と高ファンアウト投稿者のポストが交互に並ぶ状態で、新しいポストを反映させながら読み進めます。

期待の根拠はバックエンド要件「ホームタイムラインを見られる」です。続きのページに、カーソルより新しいポストと、前のページで返したポストが現れないことを期待します。ページ間の欠落は保証されないので、読み進める間に反映が進んで欠けることは仕様どおりです。欠けたのか、並びを誤ったのかは、先頭から読み直した結果と比べて見分けます。

## 異常を疑う根拠は、要件だけでなく、別の経路と順序の入れ替えにも置く

どの charter でも、要件と業務知識に書かれた期待に加えて、次の四つを異常の根拠に使います。

一つ目は、クエリデータモデルの論理定義です。反映がすべて済んだ後（すべての要求に成功の行がある状態）のホームタイムラインは、`posts` と `follows` だけから論理定義で求めた結果と一致するはずです。テスト戦略も同じ基準を自動テストに使っています（仮説 H3）。二つ目は、同じ目的を持つ別の経路です。投稿者のユーザータイムラインは一次データから読むので、フォロー中の相手のポストの集合と照らし合わせられます。三つ目は、順序を入れ替えても保たれるべき関係です。「フォローしてから相手がポストする」と「相手がポストしてからフォローする」は、反映が済めば同じ結果になるはずです。同じメッセージを何度処理しても、結果は一度の処理と同じはずです。四つ目は、利用者と運用者が状態を理解し、原因を診断できることです。

期待の根拠が見つからないときは、欠陥と決めつけません。要件の持ち主（利用者）へ判断を戻します。利用者が反映待ちと反映の失敗を見分けられないことは、ジャーニーが未決にしているので、この扱いになります。一方、運用者が止まった要求を特定できないことは、非機能要件「運用性と観測」に根拠があるので、欠陥の候補にします。

## 探索中は、再現に要る証拠をその場で残す

非同期の食い違いは、後から同じ時間の並びを作り直すのが難しいです。そのため、証拠は観察したその場で残します。一つの発見につき、次を記録します。

- 元の charter と、探索中に追っていた thread
- 環境: 対象の commit、docker compose の構成、リースと調停の設定値
- 初期状態: 利用者、フォロー、ポストの用意の仕方と、用意した後の PostgreSQL の主なテーブルの件数
- 具体的な入力と操作の列: 公開 API の要求、担い手と発行と調停の停止と再開を、時刻と一緒に記録する
- 実際の結果: 公開 API の応答、関係する要求の Outbox の行（要求、回収、範囲、完了、成功）、Redis のキーの中身
- 期待と、その根拠の資料と節
- 再現を試した回数、再現した条件、再現しなかった条件
- 関係する構造化ログの行と時刻、ポストID、要求ID、`worker_id`

一度だけ起きた観察は、再現できる手順として清書しません。一度だけの観察は「追加の探索が要る」に分け、再現しなかった条件と一緒に残します。

記録を置く場所は、まだ決まっていません（未決 O3）。

## 発見は四つに分ける

振り返りで、発見を次の四つのどれかに分けます。

| 分類 | 当てはまるとき | 次の持ち主 |
|---|---|---|
| 仕様どおり | 要件か設計資料が、観察した振る舞いを許している | なし（学びとして charter の記録に残す） |
| 期待の根拠が不明 | 要件と設計資料に期待が無いか、未決になっている | 要件の持ち主（利用者）か、設計資料の持ち主 |
| 追加の探索が要る | 一度だけ起きた、または再現の条件を絞れていない | 次の探索の charter |
| 再現できる欠陥 | 別の実施者が、同じ初期状態、入力、操作列で期待との差を観測できる | 実装チーム（次の節の手順へ） |

表のうち、判断に迷いやすいのは「仕様どおり」と「再現できる欠陥」の境目です。反映の途中の見え方は仕様どおりで、反映が済んだ後に残る食い違いは欠陥の候補です。反映が済んだかどうかは、関係するすべての要求に成功の行があるかで判断します。時間が経ったかでは判断しません。

## 再現できる欠陥は、失敗を再現できる最小のレベルのチェックにしてから直す

見つけたときの操作は、docker compose の複数のプロセスをまたいでいます。発見した操作列を、そのまま Large の E2E の回帰テストとして固定します。見つけたときと同じ経路で確かめるのが、最も確実だからです。

反映の経路の発見なら、最初に試す置き場は次のようになる見込みです。どれも、テスト戦略の「テストレベルごとの責務」から導いたもので、実際の置き場は依存を外した結果で決まります。

| 発見の形 | 最初に試す置き場 | サイズ |
|---|---|---|
| 経路の判定の誤り（昇格、降格しない） | 業務判断 | Small |
| 古い配信が解除した相手のポストを戻す、要求の処理の順序で結果が変わる | 非同期処理と調停（担い手の処理をテストのプロセス内で順序を固定して呼ぶ） | Medium |
| リースが切れた後の元の担い手との重なり | 非同期処理と調停（時計を進める） | Medium |
| 作り直しと進行中の反映の重なり | 非同期処理と調停（バリアで順序を固定） | Medium |
| 読み進めの並びやカーソルの誤り、一部を正常として返す | 読み取り | Medium |
| 止まった要求を観測点から特定できない | 非同期処理と調停、または公開インターフェース（ログの出力を観測） | Medium |
| プロセスを分けたときだけ起きる（発行と購読の配線、再開の接続） | E2E | Large |

非同期の欠陥を Pub/Sub の再配送や実時間の待ちで再現しようとしないでください。テスト戦略は、担い手の処理を実物の PostgreSQL と Redis に対して順序を固定して呼べば再現できる失敗を、Medium に置くと決めています。

修正への引き継ぎは、次の順で進めます。

1. 最小の置き場に、発見の初期状態、入力、操作列を写したチェックを書く。
3. 意図した理由で失敗するチェックを添えて、修正を始める。
4. 修正後に同じチェックが通ることを確かめ、完了判定の入口に入れる。これで回帰の証拠になり、引き継ぎを完了とする。

次のときは自動化しません。期待の根拠が決まらない。再現の条件を絞れない。欠陥ではなく学びである。保守の費用が、回帰のリスクを上回る。このときは、状態、根拠、次の持ち主、再開の条件を記録に残します。たとえば、同じ投稿者の二件同時の昇格（未決 O1）は、要件の持ち主が二件目の経路を決めるまで、期待の根拠が不明のまま残します。

## 順番は、重い失敗に近い charter から

charter は次の順に行います。一つ目の基準は、テスト戦略が最も重いとした二つの失敗（外した相手を出す、反映を失う）に近いことです。二つ目の基準は、自動テストが順序を固定しにくいことです。

| 順 | charter | 主に関わるリスク | 時間枠 |
|---|---|---|---|
| 1 | C1 フォロー解除の後の古い配信 | R9 | 90分 |
| 2 | C4 担い手が止まる場所と診断 | R8、R16 | 90分 |
| 3 | C3 高ファンアウトへ移る瞬間 | R7、R8、R9 | 90分（用意は枠の外） |
| 4 | C2 フォローの反映と途中の配信 | R9、R10 | 90分 |
| 5 | C5 キャッシュ全体の欠損後の作り直し | R11、R12 | 90分 |
| 6 | C6 反映が進む間の読み進め | R10 | 90分 |

一回が終わるたびに振り返り、同じ charter を続けるか、thread を新しい charter に分けるかを決めます。C1 か C4 で再現できる欠陥が見つかったら、その周辺の順序をもう一回探索してから次へ進みます。同じ仕組みの欠陥は、近い順序に集まりやすいと推定するからです。

## 未決と仮説

次の仮説は、資料で答えが決まらず、利用者の確認も得られていないため、推奨を仮置きしたものです。どれも決定ではありません。

- H1 作り直しは、正しさだけを探索の対象に含め、処理量と同時実行数は除く。根拠は、作り直しが古い更新の拒否という配信と同じ判断を共有すること、処理量は負荷試験で決める値であることである。採らなかった案は、作り直しを scope の外に置く案である。依頼者が scope を配信とフォロー変更の反映だけに絞れば、C5 を外す。
- H2 探索を始めるのは、R8〜R12 の Medium と4本の E2E が緑になってからにする。根拠は、探索が回帰の代わりにならないことである。採らなかった案は、実装が動く箇所から先に探索を始める案である。リリースの日程と実装の進み具合が分かれば確定する。
- H3 リースと調停の間隔は、設定で短くできる前提にする。根拠は、実時間で5分と30分を待つと、90分の時間枠で試せる順序が数個に減ることである。採らなかった案は、実時間で待つ案である。実装の設定項目が分かれば確定する。変えられなければ、C4 と C5 の時間枠を延ばす。
- H4 時間枠は、一回90分とする。根拠は、状態を用意し、非同期の処理を待ち、Outbox と Redis を読むので、60分では一つの系列を追い切れないと推定したことである。採らなかった案は、60分の時間枠を多く回す案である。実施者と、リリースまでに使える延べ時間が分かれば確定する。

次の論点は、決まっていません。

- O1 同じ投稿者の二件のポストが同時に昇格を選んだときの期待。ポストのコマンドデータモデルの「未決」である。C3 では観測だけを記録して要件の持ち主へ渡す。二件目の経路が決まれば、期待が決まる。
- O2 自動テストの証拠。いまは一つも無いので、「残余リスク」の表は主担当の予定に基づいている。H2 の条件がそろった時点でテストを読み、証拠を対応付け直す。主担当が緑でも刺激か観測が足りないテストがあれば、その未知を探索に足す。
- O3 探索の記録と発見を置く場所と、実施者。資料に記述が無く、推奨も置けなかった。チームが決める。
- O4 高ファンアウトの投稿者本人のポストが、本人のホームタイムラインへどう入るか。要件は表示すると決めているが、設計資料に仕組みが無い。C3 の前に設計の持ち主へ確かめると、C3 の期待がはっきりする。

この計画の状態は、未完了（unresolved）とします。探索の配分と引き継ぎの形は決まりました。一方、配分の前提である自動テストの証拠がまだ無いこと（O2）が、計画の中では直せない不足として残ります。O2 の条件がそろい、証拠を対応付け直して配分が変わらないと確かめた時点で、完了にできます。
