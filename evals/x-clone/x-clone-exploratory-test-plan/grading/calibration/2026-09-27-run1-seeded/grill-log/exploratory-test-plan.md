# grill の記録: ホームタイムラインへの反映の探索的テスト計画

この実行には問いに答える利用者がいないため、指示に従い、エージェントが利用者の代わりに答えた。対象リポジトリの要件と設計資料、確定済みのテスト戦略（`test-strategy/test-strategy.md`）にある事実で答えが決まる論点は、その事実で答えた。資料に無い論点は、問いに添えた推奨を仮置きした。仮置きした答えは決定ではなく、計画の「未決と仮説」に、根拠、採らなかった案、確定の条件と一緒に書いた。

## 問う前に、資料で決まった前提（問いにしなかった論点）

次の論点は資料で答えが決まるので、問いにせず「この前提で進める」とした。

- 目的と読み手: 実装を始める Go のチーム（3〜6人）が、リリース前にホームタイムラインへの反映の経路のどこへ探索を配分するかを決める。根拠は依頼文と、テスト戦略の冒頭（「このあとのシナリオ設計と探索計画も、配分はこの資料で決めます」）。
- 性能、負荷、セキュリティは扱わない。依頼の scope に指定が無く、skill は指定があるときだけ扱うと決めている。テスト戦略も性能（決定 D1）とセキュリティ診断（H1）を別扱いにしている。キャッシュ全体の欠損後の「一斉閲覧」は、処理量と同時実行数の上限を負荷試験で決める論点（非機能要件「まだ決まっていないこと」）なので、探索では正しさの側だけを扱う。
- 反映の途中で許される見え方: フォロー後に相手のポストが無い、または一部しか並ばないこと（ジャーニー「読みたい相手をフォローして…」既知の分岐）、フォロー解除後に相手のポストが一時的に残ること（バックエンド要件「フォローを外せる」）、投稿者本人のホームタイムラインへの反映の遅れ（バックエンド要件「ポストできる」）は、仕様どおりである。反映が済んだ後に残る食い違いだけを異常の根拠にする。
- 反映後の判定の基準: ホームタイムラインのクエリデータモデルの論理定義（`posts` と `follows` だけで表示対象と並びが決まる）。テスト戦略が H3 として同じ基準を自動テストに使うので、探索でも同じ基準を使う。
- 期待の根拠が無い発見を戻す先: 要件の持ち主（利用者）。根拠は非機能要件「まだ決まっていないこと」の「回答責任者は利用者」と、各ジャーニーの「確認先は、バックエンド要件の持ち主」。
- 再現できる欠陥を置くレベルとサイズ: テスト戦略の「テストレベルごとの責務」と「重ねないこと」の規則に従う。探索計画では作り直さない。
- 自動テストの証拠: `target-repo` は commit 8a351c1「docs: 要件と設計資料」だけで、コード、テスト、CI が無い。自動テストの実行済みの証拠は一つも無い。

## 問いと答え（出た順）

### q1 探索の対象に、キャッシュ全体を失った後の作り直しを含めるか

```text
❓ 探索の範囲: 「反映の経路」に、キャッシュ全体を失った後の作り直しと、作り直し中に成立したポストやフォロー変更の扱いを含めますか。
➡️ 推奨: 含める。ただし、多数の利用者の同時閲覧で起きる処理量と同時実行数は扱わない。
   理由: 作り直しは、失った反映を一次データから取り戻す回復の経路で、古い更新を現在のフォロー関係と照合して拒む点で配信と同じ判断を共有する（バックエンド要件「成立した事実の説明と回復」、非機能要件「負荷保護」）。テスト戦略も探索の配分先に「キャッシュ全体を失った直後の一斉閲覧」を挙げている。一方、処理量の上限は負荷試験で決める値で、scope に性能の指定は無い。
```

- 答え: 推奨を仮置きする（作り直しの正しさを含め、処理量と同時実行数は除く）。
- 根拠: 依頼の scope は「フォローとフォロー解除の反映、ポストの配信」で、作り直しを含むかを明示していない。資料だけでは決まらないので推奨を仮置きした。採らなかった案は、作り直しを scope の外に置く案である。依頼者が scope を配信とフォロー変更の反映だけに絞ると確認すれば、charter C5 を外す。

### q2 探索を始める条件をどこに置くか

```text
❓ 開始の条件: リリース前の探索を、どの自動テストの証拠がそろった時点で始めますか。
➡️ 推奨: テスト戦略が R8〜R12 の主担当にした Medium のテストと、4本の Large の E2E が実装され、完了判定の入口で緑になった時点で始める。それまでは探索を回帰の代わりにしない。
   理由: 探索は、自動テストが確かめていない未知へ配分するもので、既知の期待の確認を肩代わりしない。いまはテストが一つも無いため、今の時点で探索を始めると、同じ場面を手で確かめ直すことになる。
```

- 答え: 推奨を仮置きする。
- 根拠: テスト戦略は「探索の計画は、自動テストの証拠がそろってから、残るリスクへ配分します」（詳細化しない品質領域）と書くが、どのテストがそろえば始めるかは書いていない。推奨を仮置きした。採らなかった案は、Medium がそろう前でも、実装が動く箇所から探索を始める案である（回帰の代わりになりやすいので採らなかった）。リリースの日程と、実装の進み具合が分かれば確定する。

### q3 探索の環境と、観測してよい範囲

```text
❓ 環境: 探索は、どの環境で、何を観測してよいことにしますか。
➡️ 推奨: Large の E2E と同じ docker compose の構成（API、Outbox の発行、配信・反映の担い手、調停処理、PostgreSQL、2用途の Redis、Pub/Sub エミュレーター、Clerk は差し替え）を手元に起動する。操作は公開 API で行い、観測には PostgreSQL と Redis の読み取り、構造化ログ、担い手プロセスの停止と再開を使ってよいことにする。リースと調停の間隔は、設定で短くできることを前提にする。
   理由: 非機能要件「移植性と開発環境」が、この構成を手元で本番と同じプロセス境界で起動できることを求めている。クラウドと外部サービスへは接続しない。反映の途中の状態は公開 API だけでは見えないので、Outbox の行と Redis のキーを読まないと、再現の証拠を残せない。
```

- 答え: 構成と観測の範囲は資料の事実で答える。リースと調停の間隔を設定で短くできることは、推奨を仮置きする。
- 根拠: 構成は非機能要件「移植性と開発環境」とテスト戦略「E2E に残すのは4本の接続だけ」で決まる。リース5分と調停5分は仮に置かれた値（ポストとフォローのコマンドデータモデル「未決」）で、設定で変えられるかは実装が無いので分からない。採らなかった案は、実時間で5分と30分を待つ案である。実装の設定項目が分かれば確定し、変えられなければ C4 の時間枠を延ばす。

### q4 利用者が「反映待ち」と「反映の失敗」を見分けられないことを、欠陥として扱うか

```text
❓ 診断のしやすさ: 探索で、利用者が反映待ちと反映の失敗を見分けられないと観測したら、どう分類しますか。
➡️ 推奨: 利用者の側は「期待の根拠が不明」として要件の持ち主へ戻し、欠陥にしない。運用者の側は、非機能要件「運用性と観測」が求める観測点（未発行と未処理の件数と最古の経過時間、5分超の遅延、30分超の構造化 Error ログ）を期待の根拠にし、そこから止まった要求を特定できなければ欠陥の候補にする。
   理由: 利用者向けの見分け方は、二つのジャーニーの「まだ決まっていないこと」が未決としており、期待の根拠が無い。運用者向けの観測点は要件にある。
```

- 答え: 資料の事実で答える（推奨どおり）。
- 根拠: ジャーニー「読みたい相手をフォローして…」と「読まなくなった相手の…」の「まだ決まっていないこと」、非機能要件「運用性と観測」。

### q5 一つの charter に使う時間枠

```text
❓ 時間枠: 一つの charter に、一回あたり何分を使いますか。
➡️ 推奨: 一回90分とし、終わるたびに振り返りをして、続けるか別の charter に分けるかを決める。高ファンアウトへの昇格（C3）は、1万人のフォロワーを用意するだけで時間がかかるので、用意を探索の時間枠の外に置く。
   理由: 使える時間を示す資料が無い。反映の経路は、状態を用意し、非同期の処理が進むのを待ち、Outbox と Redis を読むので、60分では一つの系列を最後まで追い切れないことが多いと推定する。
```

- 答え: 推奨を仮置きする。
- 根拠: 資料に探索の人員と時間の記述が無い。採らなかった案は、60分の短い時間枠を多く回す案である。実施者と、リリースまでに使える延べ時間が分かれば確定する。

### q6 同じ投稿者の二件のポストが、同時に高ファンアウトの経路へ移ったときの期待

```text
❓ 期待の根拠: フォロワー1万人以上の投稿者の二件のポストが同時に受け付けられ、どちらも high_fanout_promotion を選んだとき、探索では何を期待として観測しますか。
➡️ 推奨: 期待を決めず、「期待の根拠が不明」の場面として探索し、観測した結果（全フォロワーの合成対象への追加が一件に収束するか、配信の範囲が二重に作られるか、ホームタイムラインの並びが変わるか）を要件の持ち主へ渡す。
   理由: ポストのコマンドデータモデル「未決」が、二件目を high_fanout にすべきかを要件の回答責任者に確かめるとしている。結果は同じになると推定しているが、要件が場面を書いていない。
```

- 答え: 期待は未決として残す。探索の対象にすること自体は推奨を仮置きする。
- 根拠: ポストのコマンドデータモデル「未決」、テスト戦略「未決と仮説」（設計資料そのものの未決）。二件目の経路を要件の持ち主が決めれば、期待が決まり、再現できる食い違いは欠陥として扱える。
