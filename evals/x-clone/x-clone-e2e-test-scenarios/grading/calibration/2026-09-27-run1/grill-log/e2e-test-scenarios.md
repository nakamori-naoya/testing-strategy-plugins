# grill ログ: 「読みたい相手をフォローしてホームタイムラインで読む」の E2E シナリオ

この実行には問いに答える利用者がいないため、依頼の決まりに従い、問いを出した agent が利用者の代わりに答えた。資料の事実で決まる答えはその事実で答え、決まらない答えは推奨を仮置きした。仮置きした答えは決定ではなく、資料の「未決と仮説」に載せる。

## 問う前に示した前提（資料の事実で決まるため問わなかった論点）

grill の規律「調べれば分かることは問わない」に従い、次の論点は問いにせず、根拠を添えて前提として示した。

- P1 この経路の E2E は、ジャーニーの場面3→5→6（フォローの成功から、フォロー前のポストを含むホームタイムラインを最後まで読むまで）の一本にする。根拠: `test-strategy/test-strategy.md`「E2E に残すのは4本の接続だけ（仮説 H4）」の2。場面1（利用者一覧）と場面2（ユーザータイムライン）は非同期の接続を持たず、同戦略の R14、R13 で読み取りの Medium が主担当になっている。
- P2 既知の分岐（フォロー上限、操作回数の上限、反映がまだ済んでいない、読めない）は E2E に入れない。根拠: 同戦略「設計資料の例をどのレベルで確かめるか」の「ユーザージャーニー」節と R6、R15、R11。反映待ちは、期限付きで待つ条件としてだけ使う。
- P3 差し替えるのは Clerk だけにする。PostgreSQL、2用途の Redis、Pub/Sub エミュレーター、API、Outbox の発行、配信・反映の担い手、調停処理は実物を別プロセスで起動する。根拠: 同戦略「差し替えるのは Clerk と Google の境界、時計、ポストIDの採番だけにする」と「E2E に残すのは4本の接続だけ」。
- P4 操作と合否の観測は公開 API だけで行う。期限を過ぎたら、その時点の Outbox と回収の状態を診断用に出力する。失敗した E2E を無条件に再実行しない。根拠: 同戦略「E2E に残すのは4本の接続だけ」の最終段落。
- P5 サイズは Large にする。根拠: 同戦略「サイズは使う資源で決める」。docker compose で起動した API のプロセスへ要求を送り、別プロセスの担い手の結果を読むため。
- P6 外部のサービスへは接続しないので、共有環境の所有印や外部接続の許可は要らない。Clerk の実物との差は、Clerk の契約テスト（同戦略の決定 D2、仮説 H2）で確かめる。

## 問い

### Q1 開始状態: フォロー反映の配線が壊れたときに E2E が落ちるようにするか

```text
❓ 開始状態: ジャーニーの開始状態（A のポスト0件）をそのまま使うか。それとも、フォローする前に A の
   ホームタイムラインのキャッシュを1ページ分以上埋め、フォロー反映が届かなければ先頭ページが変わる
   状態から始めるか。
➡️ 推奨: A が先に自分のポストを50件して、フォロー前に一度ホームタイムラインを読み、キャッシュを
   A の50件で作り直させてから B をフォローする。
   理由: 利用規模と負荷モデル「キャッシュ容量の暫定仮定」は、キャッシュだけで要求ページを満たせない
   ときは一次データから表示資格のあるポストを読む、としている。バックエンド要件「操作の成功境界」は、
   キャッシュ全体が無い閲覧では API が一次データから作り直す、としている。ジャーニーの開始状態
   のままでは、A のキャッシュは無いか、あっても0件になる。すると、担い手が反映しなくても読み取りは
   一次データから B のポストを返すので、Outbox から Pub/Sub、担い手、Redis までの接続が欠けても
   E2E は緑になる。A の50件でキャッシュを満たしておけば、反映が届かないかぎり先頭ページは A の
   ポストのままなので、欠陥を検出できる。
```

- 答え: 推奨を仮置きした。
- 根拠: 要件と設計資料には、この E2E の開始状態を決める記述は無い。判断の材料にした事実は、`docs/requirements/利用規模と負荷モデル.md`「キャッシュ容量の暫定仮定」（キャッシュで満たせないページは AlloyDB から読む、キャッシュの終端付近も一次データから読む）、`docs/requirements/バックエンド要件.md`「操作の成功境界」（閲覧時にキャッシュ全体が無い場合の作り直しは API が行う）、`docs/requirements/非機能要件.md`「整合性と鮮度」（担い手はキャッシュが存在したフォロワーへだけ追加する）である。
- 採らなかった案: ジャーニーの開始状態をそのまま使う案（上の理由で担い手の欠陥を検出できない）。フォロー反映要求の成功記録を DB から読んで合否にする案（テストが内部の表の形に依存し、戦略の「公開 API だけで操作と観測」に反する）。

### Q2 件数: B のポストを何件にするか

```text
❓ 件数: B のポストを、ジャーニーと戦略にある120件のままにするか。それとも、本番と同じレート制限の
   もとで作れる件数に減らすか。
➡️ 推奨: B のポストを55件にし、E2E の環境でもレート制限の値を本番と同じにする。
   理由: 非機能要件「負荷保護」のポスト作成の上限は60回/時である。120件を公開 API で作ると上限に
   当たる。上限を設定で引き上げると、E2E の構成が本番と違う値で動く。55件なら上限の内側で作れ、
   A の50件と合わせて105件になり、B のフォロー前のポストが先頭ページを越えて2ページ目まで続く。
   カーソルによる続きの読み取りと、キャッシュから一次データへの移り目の接続は、それで確かめられる。
   120件でなければ見つからない接続の欠陥は無い。件数の境界（500件など）は Medium が主担当である。
```

- 答え: 推奨を仮置きした。
- 根拠: `docs/requirements/非機能要件.md`「負荷保護」（ポスト作成 5回/秒、60回/時、300回/日）。`test-strategy/test-strategy.md`「重ねないこと」（E2E ではキャッシュの500件境界を確かめない）。120件は、ジャーニーの場面2、5、6 と戦略の E2E の2に書かれた数である。E2E でその数を使う理由は、資料のどこにも書かれていない。
- 採らなかった案: 120件を保ち、E2E の環境でポスト作成の上限を設定で引き上げる案（本番と違う設定で動くうえ、上限を設定で変えられるかは設計に書かれていない）。開始状態を準備専用の経路（DB への直接挿入や usecase の直接呼び出し）で作る案（本番の書き込み経路が守る不変条件を迂回する）。

### Q3 完了の期限: 反映をどれだけ待つか

```text
❓ 完了の期限: フォローの成功から、ホームタイムラインの先頭ページに B のポストが並ぶまでを、
   どの期限と間隔で待つか。
➡️ 推奨: 2秒ごとに先頭ページを読み、60秒で打ち切る。
   理由: 調停処理は、5分間進捗が無い要求を拾い直す。期限を5分より長くすると、Outbox の発行が
   壊れていても調停が拾い直して間に合い、通常の経路の欠陥が隠れる。調停からの回復は別の E2E
   （戦略の E2E の4）が受け持つ。また、タイムライン閲覧の上限は120回/時なので、2秒間隔で60秒待つと
   最大30回になる。事前の1回と続きの2ページを足しても33回で、上限の内側に収まる。
```

- 答え: 推奨を仮置きした。
- 根拠: 期限の値は資料に無い。判断の材料にした事実は、`docs/requirements/非機能要件.md`「データの保持」（5分間進捗が無いものを調停対象にする）、「負荷保護」（タイムライン閲覧 10回/秒、120回/時）、「整合性と鮮度」（99%を5分以内とする運用 SLO は一件ごとの期限ではない）、`test-strategy/test-strategy.md`「E2E に残すのは4本の接続だけ」（固定の時間を待たず、期限付きで待つ）である。
- 採らなかった案: 5分の SLO に合わせて5分以上待つ案（調停による回復が通常経路の欠陥を隠し、閲覧の上限にも当たる）。固定の時間だけ待ってから一度だけ読む案（戦略が禁じている）。

### Q4 Clerk の差し替え: Large の構成で、認証をどう差し替えるか

```text
❓ Clerk の差し替え: 別プロセスで起動した API に対して、利用者 A と B の認証をどう用意するか。
➡️ 推奨: docker compose の中に Clerk の代わりを務めるスタブのプロセスを置く。スタブは、テストが
   ローカルの鍵で署名した JWT を検証するための公開鍵と、Clerk Backend API の利用者情報（検証済みの
   Google external account と Google アカウントID）の応答を返す。API は設定でスタブの URL を向き、
   JWT の署名、発行者、audience または authorized party、有効期限の検証は本番のコードを通す。
   A と B は、公開の登録 API で登録する。
   理由: 戦略は、E2E でも Clerk を差し替え、差し替えるときも JWT の検証はバックエンドの実物の
   コードを通すとしている。検証を迂回する方法（テスト用のヘッダーで利用者IDを渡すなど）では、
   認証主体が API のプロセスで決まり、フォローの行とホームタイムラインの持ち主へ伝わる接続を
   確かめられない。
```

- 答え: 推奨を仮置きした。差し替えること自体は戦略で決まっている。仮置きしたのは Large での差し替えの形である。
- 根拠: `test-strategy/test-strategy.md`「差し替えるのは Clerk と Google の境界、時計、ポストIDの採番だけにする」（Small と Medium での差し替え方）と「E2E に残すのは4本の接続だけ」（Clerk は差し替える）。Large での形は資料に無い。
- 採らなかった案: Clerk の開発用 instance に接続する案（秘密値とネットワークが要り、戦略の完了判定の入口に入れられない。実物との差は契約テストが受け持つ）。JWT の検証を迂回し、テスト用のヘッダーで利用者を指定する案（認証主体の伝播を確かめられない）。

## 終わりの一覧

grill の規律に従い、決定、仮説（推奨を仮置きした未決）、未決（推奨の無いもの）、取り下げを一覧にした。

決定（資料の事実で決まったもの）

- D1 この経路の E2E は、場面3→5→6 の一本（E2E-F1）にする（前提 P1、P2）。
- D2 差し替えるのは Clerk だけにし、ほかの部品は実物を別プロセスで起動する（前提 P3）。
- D3 操作と合否の観測は公開 API だけで行い、期限切れのときに Outbox と回収の状態を診断用に出す。自動で再実行しない（前提 P4）。
- D4 サイズは Large にする（前提 P5）。
- D5 外部のサービスへは接続せず、Clerk の実物との差は Clerk の契約テストで確かめる（前提 P6）。

仮説（推奨を仮置きしたもの）

- H-E1 A の50件のポストと事前の閲覧で、A のキャッシュを1ページ分以上埋めてからフォローする（Q1）。
- H-E2 B のポストを55件にし、レート制限は本番と同じ値にする（Q2）。
- H-E3 2秒ごとに先頭ページを読み、60秒で打ち切る（Q3）。
- H-E4 Clerk は docker compose の中のスタブのプロセスで差し替え、JWT の検証は本番のコードを通す（Q4）。

未決（推奨を出せないもの）

- U1 フォロー反映が通るプロセスの並びが、資料の間で一致していない。フォローのコマンドデータモデルでは、担い手が DB の要求を直接回収する。一方、戦略の構成図と利用規模と負荷モデルは、Outbox の発行と Pub/Sub を経由する形と、発行完了の記録を挙げている。どちらの形かで、失敗の切り分けに使う観測点が変わる。物理設計の担当が決める。
- U2 公開 API の契約（フォロー成功の表現、カーソル、続きが無いことの表現）が無い。最終観測は意味の水準で書き、契約ができたら具体的な項目に置き換える。API 契約の作成者が決める。

取り下げ: なし。
