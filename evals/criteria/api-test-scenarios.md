# API テストシナリオの資料に共通する条件

この条件は、実行の担当が design-api-test-scenarios で作った業務ごとの API テストシナリオの資料（以下、資料）と grill の記録（以下、記録）を判定するためのもので、どの業務の資料にも当てる。ケースに固有の条件は、この後ろに続く。条件は判断の型だけを書き、正しい資料の中身は書かない。どの条件も、ほかの条件の出来、文体、見出しの形では判定しない。各条件の「重み」は点数にまとめるときの値で、判定の厳しさは変えない。重み3は利用者の原則の芯（推測で埋めない、一つの判断は一か所が持つ、同じ欠陥を最小の境界へ移す）、重み2は資料の骨組み、重み1は細部である。資料や記録が存在しない、または空のときは、それを読む条件はすべて FAIL とする。

実行の担当は、対象リポジトリ（要件と設計資料だけの手元の git repository）、確定済みのテスト戦略（`materials/test-strategy/`）、依頼と scope を渡された。grill の問いには、資料と戦略から決まることで答え、決まらなければ推奨を仮置きして資料の未決に書くよう指示されていた。

## 公開契約を決める

### public-contract-decided

重み: 3

PASS：資料が、対象の業務の公開する操作、要求と応答の項目、操作ごとに返す Code と、その Code を受けた呼び手が再試行してよいかを決めている。返す Code は業務知識の拒む理由と一つずつ対応し、変更が確定したか呼び手が区別できない Code には、再試行の前に今の状態を何で確かめるかが書かれている。呼び手の識別と権限は横断的関心事の設計を指し、要求の項目で呼び手を名乗らせていない。

FAIL：公開する操作、項目、Code、再試行の可否のどれかが決まっていない。または、業務知識に無い拒否を Code として足している、確定したか分からない Code の扱いが無い、あるいは要求の項目で呼び手を決めている。

## 戦略に従い、最小の担当レベルへ置く

### follow-strategy-definitions

重み: 3

PASS：レベル、サイズ、差し替えてよい境界は、渡したテスト戦略の定義をそのまま使い、資料の側で定義し直したり、戦略に無いレベルや差し替えを足したりしていない。戦略と食い違う判断が要ると考えたなら、戦略の持ち主への提案として書いている。

FAIL：戦略と違うサイズの定義や差し替えの方針を資料の側で決めている、または戦略に無い差し替え（制御できる協働先の偽物など）を置いている。

### boundary-only-at-boundary

重み: 3

PASS：境界のシナリオとして中心に残すのは、境界を通して初めて観測できること（呼び出し主体と認証・認可の結果、wire 表現から内部入力への変換、成功・拒否・競合・未検出の外部表現、冪等性と再送、順序、操作後に外から観測できる状態と副作用）である。業務の成立条件と拒否理由の網羅は業務判断のレベルへ、保存の制約や原子性は永続化のレベルへ送り、境界には変換と外部表現を確かめる代表例だけを残している。送った項目とその理由が書かれている。

FAIL：業務の境界値や拒否理由を境界のシナリオで網羅している、または下位へ送った項目と理由が書かれていない。

## 具体性

### concrete-inputs

重み: 2

PASS：各シナリオに、事前状態、具体入力（具体値）、行為、応答と状態と副作用を含む観測結果、主担当のレベルとサイズがある。拒否のシナリオは、外した条件、それを外す具体値、対照となる成立値、どの境界が拒むか、外へ返る結果、状態や副作用が起きないことまで書いている。「不正な値」「成立しない入力」のような抽象で済ませていない。

FAIL：具体値の無いシナリオ、観測結果が応答だけで状態や副作用が無いシナリオ、または「不正な値」で済ませた拒否のシナリオがある。

### sequence-only-when-needed

重み: 2

PASS：操作の列にしたシナリオは、状態、再送、順序、競合で結果が変わるものだけで、完了は固定の sleep ではなく外から観測できる条件で書いている。直交する入力を総当たりにしていない。

FAIL：一回の呼び出しで差が出る例を操作の列にしている、固定の時間を待つ、または根拠なく入力を総当たりにしている。

## 推測で埋めない

### no-invented-interface

重み: 3

PASS：対象リポジトリにインターフェース定義もコードも無いことを踏まえ、存在しない定義のパス、digest、生成基盤を事実として書いていない。公開契約（操作、項目、Code）は、この資料が決める設計として書き、業務知識か要件から導けない値（項目の名前、件数、続きの読み方）は、仮説として根拠と確定の条件を添えている。定義ができたときに構造と意味をどう同期するかの方針を書いている。

FAIL：対象リポジトリに無いインターフェース定義や生成基盤を、あるものとして書いている。または、資料から導けない契約の値を、仮説の断りなく確定として書いている。根拠の欄に、その記述を引用する。

### hypothesis-marked

重み: 3

PASS：要件、設計資料、戦略から決まらない期待結果と、記録で推奨を仮置きした答えは、仮説と分かる語で書かれ、根拠、採らなかった案、見直す条件が添えられている。

FAIL：資料から決まらない期待結果が、断りなく確定の期待として書かれている。

### owner-not-rewritten

重み: 2

PASS：設計資料とテスト戦略を書き換えていない。設計資料の不足や食い違いは、持ち主への提案か未決として書いている。

FAIL：設計資料か戦略を書き換えた形跡がある、または設計資料の決まりをシナリオの側で変えている。

## 追跡できる形

### scenarios-traceable

重み: 2

PASS：各シナリオは、`### [BDD-<3桁以上の連番>] 見出し` の形の見出しと、`Given:`、`When:`、`Then:` の具体例を持ち、結果が変わる例を表の行に詰めずに一つずつシナリオにしている。別のレベルへ送った項目は、観測するレベルを一つに決め、送り先の資料の BDD の番号か、そこで何を起こして何を観測するかを書いている。

FAIL：シナリオの識別子が BDD の見出しの形でないか、Given、When、Then が無い。または、結果の違う例を一つのシナリオの表に並べている。または、送り先を二つ以上並べているか、送り先で何を観測するかが無い。

## 書き方と grill

### shape-headings

重み: 1

PASS：シナリオは一つずつ見出しを立て、何を確かめ、なぜそのレベルに置くのかを文章で書き、表は入力の区分のように同じ属性を比べる箇所にだけ使っている。

FAIL：シナリオの理由を表のセルか箇条書きの断片だけで済ませている。

### grill-only-outcome-changing

重み: 1

PASS：記録にある問いは、答えで期待結果、対象境界、互換性、再試行の意味、主担当のレベルが変わるものだけで、資料と戦略から決まることを問い直していない。問いが無いときは、問わなかった理由が記録か報告にある。

FAIL：資料から一つに決まることを問うている問いがある。または、問いが無く、その理由も無い。
